# 05. Reporting & Ops — 제보와 운영

발견에서 제보까지 하루의 흐름: ① 정찰·표면 매핑 → ② AI 선별 → ③ 검증·PoC → ④ 제보. 이 흐름에서 자주 막히는 지점: 표면 누락(입력 지점을 덜 찾으면 뒤 단계가 헛돈다), 재현 불안정(환경 차이로 크래시가 안 잡힘 → 시드 고정), 근거 부족(왜 취약한지 설명 못 하면 반려됨).

## 반려되는 리포트와 통과하는 리포트

**이렇게 쓰면 반려된다**: 스캐너 출력을 그대로 붙여넣은 리포트 / "취약해 보입니다"라는 추측성 서술.

**이렇게 쓰면 통과한다**:
- 요약 3줄 → 영향 → 재현 절차 → PoC → 완화안 순서로 구성
- 재현 절차에 요청 원문과 응답을 그대로 첨부
- 영향은 실제로 접근 가능한 데이터 기준으로 서술
- CVSS 벡터를 산정 근거와 함께 제시

리포트에 반드시 넣는 4가지: ① **재현성**(다른 사람이 그대로 따라 해서 재현되어야 함) ② **영향도**(무엇이 얼마나 위험한지 데이터로) ③ **증거**(요청·응답 원문, 스크린샷, 로그) ④ **완화안**(고칠 방법까지 제안하면 등급이 올라가기도 함). **같은 취약점이라도 리포트 품질이 보상 등급을 한 단계 바꾼다.**

### 반려된 리포트 vs 통과한 리포트 (실전 예시)

**반려 · 모호하고 재현 불가**
> 제목: "로그인 페이지에 취약점 있음" — 이것저것 만지다 남의 정보가 보였어요. 위험하니 빨리 고쳐주세요. (재현 절차·증거 없음)

**통과 · 명확하고 재현 가능**
> 제목: IDOR — `/api/orders/{id}`에서 타 사용자 주문 열람 (인증 우회 없음)
> 재현: ① A계정 로그인·토큰 획득 → ② `GET /api/orders/1002` 호출 → ③ B계정 주문·배송지 PII 응답 확인
> 영향: 인증된 임의 사용자가 전체 주문 PII 열람 · CVSS 6.5 (AV:N/PR:L/UI:N)
> 증거: 요청·응답 원문 + 스크린샷 + curl 재현 스크립트 첨부

통과 리포트의 4요소: 명확한 제목(취약점 유형과 위치를 한 줄로) · 재현 절차(단계별 + 실행 가능한 PoC) · 영향 산정(CVSS 벡터와 현실 공격 시나리오) · 증거(요청·응답 원문·스크린샷·재현 스크립트). **차이는 실력이 아니라 '재현 가능성과 근거'에서 갈린다.**

### IDOR을 재현하는 최소 PoC

```python
# poc_idor.py
import requests
A = login('userA')          # 내 계정 토큰
# 내 주문 번호는 1001
for oid in range(1000, 1010):
    r = requests.get(f'/api/orders/{oid}',
        headers={'Authorization': A})
    if r.status_code == 200:
        print(oid, r.json()['owner'])
# 출력 — 1002 userB, 1003 userC ... 타 사용자 주문 노출
```

PoC가 갖춰야 할 것: ① 단일 목적(한 취약점만 명확히 재현) ② 자동 확인(성공 조건을 코드로 판정) ③ 최소 의존(`requests` 하나로 누구나 실행) ④ 안전 범위(소수 ID만·데이터 변경 없이). 제보엔 이 스크립트 + 요청·응답 원문을 함께 첨부.

## 무인 자동화 — 자고 있는 동안에도 AI가 찾게 하기

탐색을 반복 작업으로 정의해 두면 사람 없이도 돌아감. 아침에는 걸러진 후보만 확인하면 됨. 위험한 동작은 스스로 못 하게 막아 둠.

① 대상·범위 스크립트화 → ② 반복 실행 스케줄 등록 → ③ 결과 자동 선별·기록 → ④ 아침에 후보만 검토

밤새 돌릴 때 필요한 3가지: **격리 환경**(컨테이너 안에서만 돌려 실서비스 영향 차단) · **중단 조건**(요청 수·시간 상한을 걸어 폭주 방지) · **결과 요약**(크래시와 로그를 한 파일로 모아 둠).

> 스케줄 등록은 CCR의 scheduled task(create_trigger 계열)로. 매 firing이 격리된 세션에서 실행되도록 구성.

## AI 검증보다 내 검증이 중요한 이유

1. **AI는 그럴듯하게 틀린다** — 근거 없이 취약해 보인다고 말하는 경우가 흔함.
2. **재현되지 않으면 제보가 아니다** — 플랫폼은 재현 절차가 없는 리포트를 받지 않음.
3. **책임은 제출한 사람이 진다** — 범위 위반과 오탐 남발은 계정 신뢰도로 돌아옴.

**AI는 후보를 좁히는 도구, 판정은 내 몫.** 내 손으로 재현한 것만 취약점이라고 부름.

## 토큰 사용량 줄이기 — 싸게 굴리는 법

| 전략 | 방법 |
|---|---|
| **SCOPE 넣는 것을 줄임** | 함수 단위로 잘라 넣기, 그래프로 후보만 추림, 헤더·주석 제거, 전체 파일 투입 금지 |
| **CACHE 한 번만 읽음** | 읽은 코드는 요약 저장, 요약본을 재사용, 고정 프롬프트는 캐시, 같은 질문 반복 금지 |
| **TRIM 출력을 자름** | 로그는 앞뒤만 전달, 크래시 스택은 상위 몇 줄, 바이너리 덤프 금지, 표 대신 요약 수치 |
| **ROUTE 모델을 나눔** | 선별은 값싼 모델, 판단만 큰 모델, 반복 작업은 로컬 모델, 실패 시에만 재질의 |

예시: 코드를 통째로 넣던 방식 = 토큰 100 → 좁혀서 필요한 부분만 = 토큰 35. **같은 작업, 토큰은 3분의 1.**

## AI로도 여전히 어려운 것들 (한계)

| 계열 | 이유 |
|---|---|
| **RACE 레이스 컨디션** | 타이밍 의존 버그, 동시성 경로 재현 난이도, 비결정적이라 놓치기 쉬움 |
| **STATE 복잡한 상태 전이** | 여러 단계 누적 조건, 긴 세션 문맥 초과, 경로 폭발 |
| **DOMAIN 깊은 도메인 로직** | 업무 규칙 이해 필요, 의도된 동작과 구분 난해, 맥락 없으면 오판 |
| **CHAIN 익스플로잇 체이닝** | 여러 버그의 창의적 결합, 환경별 우회 조합, 사람의 통찰 필요 |

그래서 사람이 필요하다: 최종 판단(취약 여부·심각도는 사람이 확정) · 책임 귀속(제출과 결과의 책임은 제출자에게) · **AI는 증폭기**(탐색을 넓히되, 결론은 검증으로 닫는다).

## 신뢰할 수 없는 코드를 AI에 물릴 때 (AI OpSec)

| 위협 | 내용 |
|---|---|
| **INJECTION 프롬프트 인젝션** | 코드·주석에 심은 지시를 모델이 실행, 대상 데이터를 '명령'과 분리, 시스템 프롬프트로 역할 고정 |
| **ESCAPE 샌드박스 탈출** | 도구 실행이 호스트로 샘, 네트워크 차단 컨테이너, 읽기전용 마운트로 격리 |
| **LEAK 데이터 유출** | 소스·키가 외부 API로 전송, 로컬·프라이빗 모델 사용, 비밀정보 마스킹 |
| **PRIVILEGE 과잉 권한** | 쓰기·삭제·네트워크 남용, 최소 권한 원칙 적용, 허용 도구 화이트리스트 |

붙이기 전에 세워둘 원칙: 격리 실행(네트워크 차단된 일회용 컨테이너) · 최소 권한(도구는 읽기 위주, 쓰기·실행은 화이트리스트) · 전 과정 로깅(어떤 도구를 어떤 인자로 호출했는지 모두 기록).

## 헌팅 프롬프트 패턴 — AI에게 잘 시키는 네 가지 틀

| 틀 | 내용 |
|---|---|
| **ROLE 역할 고정** | "너는 취약점 분석가", 출력 형식을 지정, 추측 금지를 명시 |
| **CONTEXT 문맥 주입** | 대상 코드·함수만 제공, 진입점·신뢰 경계 표시, 무관 코드는 제외 |
| **CHAIN 단계적 사고** | 먼저 입력을 추적, 그다음 위험 함수, 근거와 함께 결론 |
| **VERIFY 자기 검증 요구** | 도달 가능성 확인, 반례를 스스로 찾기, 파일:라인 근거 제시 |

프롬프트를 재사용하라: 템플릿화(잘 되는 프롬프트는 저장해 매번 재사용) · 고정 접두(시스템 프롬프트로 규칙을 매 호출 주입) · 출력 스키마(JSON 등 정형 출력으로 파싱·자동화).

## 실제 제보 사례 (강사 실적)

강사(MalHyuk / JongHyuk Kim)의 실제 제보 사례가 자료로 제시됨:

- **CVE-2026-59243** — Apache Airflow FAB auth manager JWT token verification disabled for Azure AD OAuth. Severity CRITICAL, CVSS 9.8/10. (`verify_signature` 기본값이 `False`라 위조 토큰으로 인증 우회) — finder: MalHyuk, remediation: Jarek Potiuk.
- **GHSA-9f3p-2jpg-3h95** — Centerd 내부 전용 IPC SOAP 엔드포인트(`127.0.0.1:3870/ipc`)를 gnrpcsvc(포트 9999)가 Apache ProxyPass로 외부 노출될 때 인증 없이 호출. Critical 9.3/10 (CVSS v4). 신고 2026-05-13 → 수정 05-26 → 공개 07-07.
- **KISA (비공개)** — 백엔드 API 디버그 키 인증 우회로 EncryptionKey 평문 노출(CRITICAL), `excuteWithPath` 인증 부재로 UID 501→root LPE, Anti-Ransomware 메서드 무력화, RSA/TLS 키 하드코딩, AES-256-CBC 정적 IV 재사용 등 다수.

> 핵심 교훈: 재현 가능한 근거 + CVSS 벡터 + 완화안이 있는 리포트가 실제 CVE/GHSA로 이어진다.

## 이 과정을 마치면 할 수 있는 것

1. **코드 읽는 시간을 절반으로 줄이기** — 수천 줄 디컴파일 결과를 요약해 의심 지점부터 봄.
2. **AI가 준 후보를 직접 재현해 검증하기** — PoC로 재현된 것만 취약점으로 인정하는 습관.
3. **탐색을 무인으로 굴려 두기** — 밤새 돌려 두고 아침에 걸러진 후보만 확인.

> "코드를 읽는 시간을 줄이면, 찾는 시간이 늘어난다." — AI 에이전트를 붙여야 하는 이유.

## 커뮤니티 — 헌터로 성장하기

실력은 결국 반복과 공유에서 온다. ① 시작(VDP·소액 프로그램으로 첫 제보) ② 학습(공개 리포트·라이트업 정독) ③ 훈련(CTF·워게임·PoC 직접 재현) ④ 평판(꾸준한 유효 제보로 신뢰 축적). 커뮤니티에서 얻는 것: 피드백(남의 리포트에서 표현·근거 방식) · 협업(콜라보 제보로 큰 버그) · 정보(새 기법·도구·프로그램 소식).
