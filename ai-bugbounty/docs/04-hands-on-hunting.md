# 04. Hands-on Hunting — How2exploit target

> 타겟 하나를 끝까지 밀어 보기.
> 목표 — 한 건을 발견부터 제보까지 끝낸다. 도구가 아니라 '워크플로'를 손에 익힌다.

공개 프로그램 하나를 정찰부터 제출까지 이어 간다. 정적 분석과 초안 작성에 AI를 투입하고, 판단과 최종 제출은 사람이 책임진다.

전체 흐름: ① 타겟·Scope 선정 → ② 에이전트·툴 연결 → ③ 취약점 후보 검증 → ④ 리포트 정리와 제출.

- 준비물: 타겟 계정, 프록시 도구, AI 에이전트 환경
- 프롬프트 원칙: 코드와 응답을 그대로 주고 판단 근거를 요구함
- 지켜야 할 선: Scope 밖 테스트와 실서비스 영향은 금지

## 기본으로 AI와 MCP에 붙이는 도구들

| 분류 | 도구 |
|---|---|
| **STATIC 정적 분석** | Ghidra MCP, IDA Pro MCP, LLM4Decompile, 디컴파일 결과 전달 |
| **DYNAMIC 동적·트래픽** | Burp Suite MCP, mitmproxy, Frida 후킹, 요청 재전송 |
| **SCAN 코드·스캔** | Semgrep MCP, CodeQL 쿼리, Nuclei 템플릿, 의존성 취약점 |

도구를 붙일 때 지키는 3가지: **권한은 최소로**(읽기 전용으로 붙이고 실행은 격리 환경에서만) · **컨텍스트는 좁게**(필요한 함수와 요청만 넘겨야 답이 정확) · **로그는 남긴다**(무엇을 시켰고 무엇이 나왔는지 기록).

### 정적·리버싱 도구

| 도구 | 역할 | 특징 |
|---|---|---|
| **Ghidra** | 바이너리 역공학 | 디컴파일·디스어셈블, 함수·xref 조회, MCP로 AI가 질의 |
| **Semgrep** | 패턴 정적 분석 | 룰 기반 코드 스캔, 다국어 지원, 빠른 1차 선별 |

AI가 쓰는 법: MCP로 호출(필요한 순간 도구 기능 직접 실행) · 결과 요약(방대한 출력을 사람이 읽을 형태로 압축) · 교차 검증(여러 엔진 결과를 겹쳐 오탐 감소).

| 도구 | 역할 | 특징 |
|---|---|---|

| **mitmproxy** | 스크립트 프록시 | 파이썬으로 트래픽 조작, 자동화 친화적, CLI 중심 |
| **AFL++** | 커버리지 퍼저 | 변이 기반 입력 생성, 크래시 자동 수집, 하네스 필요 |

동적 도구를 AI와 엮을 때: 관찰 자동화(AI가 트래픽·크래시를 읽고 다음 입력을 정함) · 격리 실행(실행형 도구는 컨테이너·VM 안에서만) · 증거 수집(재현 로그를 리포트용으로 자동 저장).

## 커스텀 룰 — AI가 못 잡는 건 직접 룰로 잡는다

```yaml
# Semgrep · 패턴 매칭 룰
rules:
  - pattern: strcpy($DST, $SRC)
    message: unsafe strcpy (WARNING)
```

```ql
// CodeQL · 데이터 흐름 쿼리
from Source s, Sink k
where TaintTracking::flow(s, k)
select k, "tainted input reaches sink"   // 외부 입력이 위험 함수까지 흐르는 경로
```

직접 룰을 쓰는 이유: ① 반복 패턴 자동화(같은 결함을 코드베이스 전체에서 한 번에) ② 프로젝트 특화(그 코드만의 위험 싱크·래퍼 함수 지정) ③ 오탐 필터(검증된 경로 제외해 노이즈↓) ④ 팀 공유(룰셋을 버전 관리해 재사용). **AI 선별 + 커스텀 룰을 함께 쓰면 놓치는 결함이 최소화된다.**

## RAPTOR — Claude Code를 공격·방어 에이전트로

| 단계 | 하는 일 |
|---|---|
| **UNDERSTAND 코드 지도** | 진입점·신뢰 경계·싱크 매핑, 위협 모델 자동 생성, 스캔 전에 문맥부터 |
| **SCAN 정적+동적** | Semgrep·CodeQL, AFL++ 바이너리 퍼징, 바이너리 그래프 질의 |
| **VALIDATE 오탐 걸러내기** | 도달 불가 결과 선차단, 익스플로잇 가능성 검증, Z3 기반 타당성 분석 |
| **OUTPUT PoC와 패치** | 익스플로잇 PoC 생성, 보안 패치 초안 작성, 증거 기반 리포트 |

RAPTOR를 쓰는 이유: 도구를 대신 굴려 줌(Semgrep·CodeQL·AFL++·Frida를 하나의 워크플로로 오케스트레이션) · 근거를 남김(사실·구조적 추론·미검증 가설을 분리해 리포트로) · 공격과 방어가 한 세트(익스플로잇만이 아니라 패치까지 뽑아내 제보 품질↑).

### 실제로는 터미널에서 이렇게 굴린다

```
> /understand --map ./target        진입점 12 · 신뢰 경계 4 · 싱크 37 매핑
> /scan --semgrep --codeql          후보 214건 → 중복 제거 후 88건
> /validate --threat-model          도달 가능한 9건만 남김
> /graph --edges --json             입력에서 파서까지 호출 경로 추적
> /fuzz --afl ./harness/parse_fuzzer  crash 3건 · 재현 스크립트 저장
> /exploit --poc crash_02           PoC 생성 → /patch 로 패치 초안까지
```

커맨드 이름은 RAPTOR 기준. 도구가 달라져도 **지도 → 스캔 → 검증 → 퍼징 → PoC** 순서는 그대로. 214건 → 9건, 볼 것만 남기는 게 이 순서의 목적.

## AI 헌팅 파이프라인 구조

```
INPUT(타깃·정찰) → ANALYZE(AI 분석기) → VERIFY(자동 검증) → OUTPUT(큐·사람 검토)
```

| 단계 | 내용 |
|---|---|
| INPUT | 소스·바이너리 수집, 공격 표면 매핑, 시드 코퍼스 준비 |
| ANALYZE | 모델 + MCP 도구, Ghidra·Semgrep·Burp, 후보 취약점 지목 |
| VERIFY | AFL++ 퍼징, ASAN 크래시 판독, 재현·최소화 |
| OUTPUT | 결과 저장·순위화, 사람이 최종 확인, 리포트·제보 |

파이프라인을 지탱하는 것: 오케스트레이션(루프가 계획→실행→관찰을 반복 구동) · 상태 저장(읽은 코드·요약을 캐시해 재사용) · 피드백 루프(검증 실패가 다음 탐색 입력으로 환류).

## 리버싱 — 코드를 열기 전에 공격 표면부터 그린다 (Recon)

헌팅의 첫 단추는 분석이 아니라 정찰이다. 어디로 입력이 들어오고 어디까지 신뢰되는지 먼저 지도로 그린다. 표면을 좁혀야 AI 분석도 노이즈 없이 깊어진다.

- 자산 열거(도메인·바이너리·엔드포인트) → 입력 지점 식별(네트워크·파일·IPC·사용자) → 신뢰 경계 표시(검증 없이 넘어오는 지점) → 우선순위 선정(도달성 높고 검증 약한 곳부터)

### 바이너리를 에이전트에게 읽히기 (Ghidra MCP)

```
> /mcp connect ghidra --project ./target   함수 1,842개 인덱싱 완료
> list_functions --imports recv,memcpy      외부 입력이 닿는 함수 27개 반환
> decompile FUN_00401a20                     지역 버퍼 256바이트 확인
> rename_symbol FUN_00401a20 parse_packet    심볼 정리 후 문맥 재요약
> xrefs_to parse_packet                       호출 4곳 · 모두 수신 스레드에서 진입
> ask 길이 검사가 빠진 구간은                 2곳 지목 · 파일:라인 근거 반환
```

이 순서로 붙이는 이유: ① 임포트부터 본다(외부 입력 API를 쓰는 함수가 곧 진입점 후보) ② 심볼을 먼저 고친다(`FUN_` 이름 그대로면 모델이 문맥을 못 잡음) ③ 호출 경로를 확인한다(어디서 불리는지 알아야 도달 가능성 판단) ④ 근거를 요구한다(주소·라인을 함께 받아야 검증으로 이어짐). **1,842개 → 2곳, 볼 함수만 남기는 게 목적.**

## 프롬프트 — 어떻게 시켜야 더 잘 찾는가

**이렇게 시키면 헛돈다**: "이 코드에서 취약점 좀 찾아줘" / "보안 문제 있으면 알려줘"

**이렇게 시키면 걸린다**:
```
@src/parser/ 에서 외부 입력이 닿는 함수만 추려라
각 후보를 입력 출처 → 도달 경로 → 위험 함수 표로
근거는 파일:라인으로 인용하고 추측은 '미검증' 표시
재현되는 PoC 입력까지 만들고, 안 되면 안 된다고 답해라
```

프롬프트에 꼭 넣는 4가지: ① **범위**(디렉터리·함수 단위로 못 박아야 환각↓) ② **형식**(표·JSON으로 받아야 검증 속도↑) ③ **근거**(파일:라인 인용 없는 주장은 버리는 규칙) ④ **실패 허용**('없으면 없다'고 답할 여지를 줘야 오탐↓). **같은 모델이라도 요청 한 줄 차이로 검증에 쓰는 시간이 몇 배 갈린다.**

## 하네스 엔지니어링 — 퍼저에 먹일 입구 만들기

| 요소 | 내용 |
|---|---|
| **ENTRY 진입점 고르기** | 파서·디코더 함수, 외부 입력 수신부, 상태 없는 함수 우선, 커버리지 넓은 곳 |
| **DRIVER 드라이버 작성** | `TestOneInput` 뼈대, 입력 구조 매핑, 초기화는 1회만, AI로 초안 생성 |
| **CORPUS 시드·사전** | 실제 트래픽 샘플, 포맷 규격 파일, 토큰 사전 정의, 코퍼스 최소화 |
| **SIGNAL 신호 확인** | 커버리지 증가 추적, 새 경로 없으면 수정, 크래시 중복 제거, 재현 스크립트 저장 |

```c
// fuzz_target.c
#include <stddef.h>
#include <stdint.h>
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    if (size < 4) return 0;
    parse_packet(data, size);   // 대상 함수 직결
    return 0;
}
// 빌드: afl-clang-fast -fsanitize=address fuzz_target.c
```

좋은 하네스의 조건: 진입점 직결(파서·디코더를 곧바로 호출) · 입력 그대로(data·size를 가공 없이 넘김) · 상태 초기화(매 호출 전 전역 상태 리셋) · 빠른 반환(조기 return으로 실행 속도↑). **입구를 얕게 잡을수록 커버리지가 넓어진다.**

### 더 빨리·깊이 크래시를 찾는 법 (퍼징 심화)

- **COVERAGE**: 실행 경로 계측, 새 경로 주는 입력 우선, edge coverage 추적
- **CORPUS**: 실제 샘플로 시드 확보, `afl-cmin` 최소화, 중복 입력 제거
- **DICTIONARY**: 매직바이트·키워드 제공, 포맷 토큰 사전, 구문 통과율 상승
- **STRUCTURE**: 문법 기반 생성, 체크섬·길이 자동 보정, 깊은 파서 도달

살리는 습관: 빠른 하네스(persistent mode) · 의미 있는 시드(작고 다양한 유효 입력이 커버리지↑) · 지표 관찰(exec/s·커버리지 정체 시 시드·사전 교체).

## 루프 엔지니어링 — 에이전트를 굴리는 방법

**계획 → 실행 → 관찰 → 수정**의 반복 사이클. 관찰한 결과를 다음 시도의 입력으로 넣고, 진척이 없으면 가설을 버리고 갈아탄다.

```
01 목표·정지 조건 → 02 도구 호출 → 03 관찰 요약 → 04 가설 교체 → (반복)
```

루프가 새면 비용만 남음: **상한을 먼저 건다**(토큰·시간·시도 횟수에 한계) · **중복 시도 차단**(같은 경로를 다시 파지 않게 기록) · **진척 없으면 종료**(커버리지가 안 늘면 루프를 끊는 것이 이득).

## 그래프 엔지니어링 — 코드를 질의 대상으로

```
recv() ──> parse() ──> validate_len() ──┐
      └──> copy_buf() ──> 검증 없음 ──────┴──> memcpy()
입력 → 복사 → 검증을 거치지 않고 memcpy 도달 = 후보 경로
```

- **콜그래프**: 어디서 어디까지 닿는지 · **데이터플로우**: 오염된 값이 어디로 흐르는지 · **CPG 질의**: 같은 패턴이 또 있는지

**그래프로 좁히고, AI로 읽고, 사람이 재현함.** 전체 코드를 다 읽는 대신, 질의로 후보를 뽑아 놓고 시작함.

## ASAN 크래시 판독

```
==1234==ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 8 at 0x60200000eff8
    #0 parse_packet packet.c:42
    #1 handle_conn conn.c:88
0x...eff8 is 0 bytes to the right of 64-byte region alloc'd by malloc
```

로그에서 읽어낼 것: ① 버그 종류(heap-buffer-overflow = 힙 경계 초과) ② 연산 방향(WRITE·8바이트 = 쓰기 오버플로) ③ 발생 지점(`packet.c:42` — 트레이스 최상단) ④ 할당 정보(64바이트 영역 바로 뒤 = 초과 지점). **이 로그를 AI에 주면 원인 함수·라인을 바로 지목한다.** 재현: `ASAN_OPTIONS=abort_on_error=1`로 결정적 크래시.

## 익스플로잇 개발 — 크래시에서 제어 획득까지

| 단계 | 하는 일 |
|---|---|
| ① 크래시 확보 | 퍼징으로 재현 입력, ASAN 로그 확인, 최소 입력 축약 |
| ② 원인 분석 | 어떤 객체·버퍼인지, 덮이는 값 추적, 크래시 지점 역산 |
| ③ 제어 확보 | RIP·객체 포인터 장악, 힙·스택 정렬, 완화 우회 검토 |
| ④ PoV 완성 | 안정적 재현 스크립트, 영향 입증(제어 흐름), 제보용 최소 PoC |

어디까지 갈지 정하기: 재현이 우선(제보엔 완전한 익스플로잇보다 안정적 재현이 먼저) · 완화가 벽(ASLR·CFI가 있으면 PoV 난이도 급상승) · 범위 준수(실제 제어까지는 Scope·법적 경계 안에서만).
