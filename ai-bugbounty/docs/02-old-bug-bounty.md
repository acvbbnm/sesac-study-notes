# 02. Old Bug Bounty — AI 없이 하던 방식

> 노가다…
> 목표 — AI가 대체하는 '옛 방식'을 몸으로 안다. 무엇이 느리고 반복적인지 알아야 자동화 지점이 보인다.

이 파트에서 배우는 것: ① 수작업 헌팅의 전 과정을 따라간다 ② Scope와 법적 경계를 읽는다 ③ 플랫폼과 트리아지 절차를 안다.

---

## Bug Bounty 제도

기업이 자사 서비스의 취약점 제보를 공개적으로 받고, 검증된 제보에 심각도에 따라 포상금을 지급하는 제도. 공격자보다 먼저 결함을 찾아내는 방식.

- 합법적 테스트 허용 범위 명시 · 유효한 제보에만 성과 보상 · 중복 제보는 최초 1건만 인정 · 상시 운영, 누구나 참여 가능

누가 참여하고 어떻게 맞물리나: **기업**(테스트 허용 범위·보상 기준 공개, 제보 검증) · **헌터**(범위 안에서 재현 가능한 형태로 제보) · **플랫폼**(HackerOne·Bugcrowd 등이 접수·보상 절차 표준화·중재).

---

## AI 없이 하던 버그 헌팅 4단계

| 단계 | 하는 일 |
|---|---|
| **① 정찰 Recon** | 정책·Scope 확인, 서브도메인 열거, 포트·서비스 스캔, 기술 스택 식별 |
| **② 분석 Analysis** | 요청·응답 흐름 추적, 인증·권한 로직 검토, 바이너리 정적 분석, 디버거로 내부 확인 |
| **③ 검증 Validation** | 파라미터 퍼징 반복, 크래시 재현 확인, PoC 코드 작성, 오탐 수동 제거 |
| **④ 제출 Report** | 재현 절차 정리, 영향도·CVSS 산정, 리포트 제출, 중복 판정 후 보상 |

모든 단계가 사람 손을 거친다 — **수작업의 한계**:
- 반복 작업에 시간 소모 (단순 열거와 퍼징에 대부분의 시간)
- 오탐 선별이 병목 (퍼저 크래시 대부분이 오탐, 일일이 재현)
- 리포트 작성 부담 (재현 절차·영향도 문서화에 또 한참)

---

## Scope 문서 읽는 법 — 허용된 범위 안에서만 하는 것이 실력

프로그램 정책은 계약서에 가깝게 읽어야 한다. 범위 밖 테스트는 보상은커녕 법적 책임으로 돌아온다. 금지 기법과 테스트 계정 규정을 먼저 확인.

- In-Scope 자산과 와일드카드 범위 · Out-of-Scope 도메인과 서드파티 · 금지 행위(DoS·스팸·사회공학) · 테스트 계정과 식별 헤더 규정

자주 놓치는 지점: **와일드카드의 함정**(`*.example.com`이어도 인프라 벤더 소유 자산은 제외되는 경우 많음) · **요청 속도 제한**(초당 요청 수 상한 위반 시 자동 차단) · **증거 보존**(테스트 시각과 요청 로그를 남겨야 분쟁 방어).

---

## 법적·윤리 경계 — 어디까지 허용되고 어디부터 범죄인가

**Scope와 Safe Harbor가 헌터를 지키는 유일한 근거.** 프로그램이 공개한 범위와 면책 조항이 곧 활동의 법적 근거다. 문서에 없는 자산·행위는 '허용'이 아니라 '금지'로 본다. 선을 넘는 순간 보상은커녕 관할법 위반이 된다.

- 명시된 범위·도메인·자산을 벗어나지 않는다
- 데이터 최소 접근 · 열람은 확인용, 유출·변조 금지
- 서비스 무해 · DoS·스팸·사회공학 금지
- 발견 즉시 보고 · 공개 전 제보, 합의 기간 준수

경계를 지키는 세 축: **Safe Harbor**(면책이 명시된 범위 안에서만 법적 보호) · **책임 공개**(제보 → 수정 → 합의된 공개, 통상 90일 기준) · **넘으면 범죄**(무단 접근·데이터 유출은 관할법 위반).

## 플랫폼 생태계

| 플랫폼 | 지역 | 특징 |
|---|---|---|
| **HackerOne** | Global | 최대 규모 프로그램, 포상 이력 공개, 트리아지 팀 1차 검증, 평판 기반 비공개 초대 |
| **Bugcrowd** | Global | VRT 심각도 기준표, 프로그램별 룰 상세, Kudos 포인트, 비공개 초대 비중 높음 |
| **Intigriti** | EU | 유럽권 기업 중심, 리포트 피드백 빠름, 응답 SLA 공개, 신규 헌터에게 유리 |
| **ZDI·직접 제보** | Broker | 제로데이 브로커, 벤더 직접 채널, 고액 보상 가능 |
| **국내·KISA** | KR | 취약점 신고 포상제, 기업 자체 프로그램, 금융·게임사 상시 운영 |
| **VDP** | 자체 | 기업 자체 채널, 보상 없는 공개, 법적 보호 먼저 확인 |

플랫폼 고를 때 실제로 보는 것: **Scope 넓이**(테스트 가능 자산이 많을수록 기회 총량↑) · **응답 속도**(트리아지 느린 곳은 중복으로 밀릴 위험↑) · **보상 정책**(심각도 기준·지급 이력 공개 여부).

## 트리아지 — 제보한 다음에 벌어지는 일

| 단계 | 하는 일 |
|---|---|
| **① 접수 New** | 자동 중복 검사, 형식 요건 확인, Scope 위반 필터링, 우선순위 큐 배정 |
| **② 검증 Triaged** | 트리아지 팀이 재현, 심각도 1차 산정, 추가 정보 요청, 중복 여부 판정 |
| **③ 수용 Resolved** | 개발팀 티켓 발행, 패치 배포 대기, 패치 후 재검증, 포상금 확정 지급 |
| **④ 종료 Disclosed** | CVE 발급 협의, 공개 시점 합의, 리포트 공개 전환, 명예의 전당 등재 |

이 흐름에서 헌터가 통제할 수 있는 것: **재현 품질**(한 번에 재현되면 Triaged까지 며칠 단축) · **응답 속도**(추가 질문에 빨리 답할수록 순번이 안 밀림) · **대응 태도**(반려에 항의하기보다 근거를 보강하는 편이 신뢰도에 유리).

### 트리아지 팀과 주고받기

제보는 끝이 아니라 대화의 시작. 트리아지 담당자는 매일 수십 건을 본다 — 명확하고 재현 가능한 제보가 먼저 처리된다. 질문에는 빠르게, 사실 위주로. 추측이나 과장은 신뢰를 깎는다. 반려·중복 판정에도 근거를 요청하고 정중히 재검토를 요청한다.

- 재현 정보 우선(환경·버전·단계를 처음부터 명확히) · 질문 응답 신속 · 심각도 근거(CVSS 벡터와 공격 시나리오로 설득) · 태도 유지(감정 대신 사실로 대응)
- 자주 겪는 상황: 재현 안 됨 → 도커 이미지·정확한 버전·영상 제공 / 중복(dupe) 판정 → 타임스탬프·차별점을 근거로 재검토 요청 / 심각도 하향 → 실제 공격 시나리오로 영향 재설명.

---

## 이 파트 요약

1. **시간의 대부분은 코드 읽기** — 정적 분석이 전체 진행 속도를 결정함.
2. **크래시 대부분은 오탐** — 재현 확인 반복이 체력과 시간을 갉아먹음.
3. **문서화까지 전부 수작업** — 제보 한 건 제출에 다시 며칠 듦.

그래서, 반복을 넘길 대상이 필요했다 → 다음 파트에서 같은 4단계에 AI 에이전트를 붙여 본다.
