# 07. 통합보안관제시스템 (ESM → SIEM)

---

## 1. 단위 보안장비 시스템의 한계

1990년대부터 보안장비가 지속적으로 지능화·전문화·고도화로 발전.

개별 장비별로 이벤트를 따로 확인해야 하는 문제:
- 관리하기 위한 많은 보안장비와 기술 혼재
- 실시간 탐지 어려움
- 이기종 장비 간 연계 분석 불가
- 보안 이벤트 폭증으로 인한 관제 요원의 피로도(Alert Fatigue) 증가
- 장비별 로그 형식이 상이하여 통합 분석 시 수작업 필요
- 공격 체인(Kill Chain) 전체를 한눈에 파악하기 불가능

```
IDS / Host / Anti-virus / Firewall / VPN / IPS / Devices / Servers
→ 모두 별도로 관리 → 통합 가시성 없음
```

> **예시**: 공격자가 외부에서 방화벽을 우회하고 → IDS에서 탐지되었으나 → IPS에서 차단하지 못한 경우,
> 각 장비 콘솔을 개별적으로 확인해야 하므로 전체 공격 흐름 파악에 수십 분~수 시간 소요.

## 2. 보안관제 세대 진화

### 1세대 — 단위 보안장비 (개별 관제)

각 장비(IDS, IPS, 방화벽, WAF, Anti-DDoS, Anti-Virus 등)를 개별로 운영. 보안담당자가 각 장비를 개별 모니터링.

- 장비마다 별도의 관리 콘솔 사용
- 장비 간 이벤트 연관성 파악 불가
- 숙련된 관제 인력에 대한 높은 의존도

### 2세대 — ESM (Enterprise Security Management)

통합 이벤트 수집·저장 시작.

| 기능 | 설명 |
|------|------|
| 로그/이벤트 통합 저장 | 이기종 장비 로그를 한 곳에 수집 |
| 주요 경보 모니터링 | 분석 룰에 의한 경보 발생 |
| 통합 이벤트 조회 | 한 화면에서 전체 이벤트 검색 |

### 3세대 — SIEM (Security Information and Event Management)

빅데이터 기반 차세대 통합보안관리시스템.

```
[위협 인텔리전스]         [네트워크 포렌식(DPI)]
Black IP/URL/Tor          Full Packet DATA
취약점 정보               Meta DATA / File DATA
        ↓                         ↓
              [빅데이터 기반 SIEM]
              ┌─────────────────────────┐
              │ 원본 로그 수집            │
              │ 실시간 분석 + 과거 분석   │
              │ 자산/취약점 정보          │
              │ 위협 분석                │
              │ 모니터링 및 사고 대응     │
              └─────────────────────────┘
                         ↑
        [네트워크 보안장비] [엔드포인트 보안장비]
        [네트워크/시스템 로그] [어플리케이션 로그]
```

## 2-1. ESM과 SIEM의 차이 상세

ESM과 SIEM은 모두 통합보안관제를 위한 시스템이지만, 근본적인 접근 방식과 처리 능력에서 큰 차이가 있다.

| 비교 항목 | ESM (2세대) | SIEM (3세대) |
|-----------|-------------|--------------|
| **분석 대상** | 보안장비 이벤트(경보) 중심 | 원본 로그 + 이벤트 + 패킷 + 위협정보 |
| **데이터 처리** | 관계형 DB(RDBMS) 기반 | 빅데이터 플랫폼(Hadoop, Elasticsearch 등) |
| **저장 용량** | 수 TB 수준 (DB 한계) | 수십~수백 TB 이상 (분산 스토리지) |
| **분석 방식** | 사전 정의 룰 기반 단순 매칭 | 상관분석 + 통계 분석 + 머신러닝 기반 이상 탐지 |
| **과거 데이터 분석** | 제한적 (DB 성능 한계) | 장기간 로그 대상 소급 분석(Retrospective Analysis) 가능 |
| **위협 인텔리전스** | 미지원 또는 수동 연동 | TI 피드 자동 연동 및 IOC 자동 매칭 |
| **처리 속도** | 수천 EPS | 수만~수십만 EPS |
| **확장성** | 수직 확장(Scale-up) 위주 | 수평 확장(Scale-out) 가능 |

### ESM에서 SIEM으로 진화한 이유

1. **데이터 폭증**: 클라우드, IoT, 모바일 등 인프라 확장으로 로그 양이 기하급수적 증가 → RDBMS 한계 도달
2. **APT 등 지능형 공격 대응**: 단순 룰 매칭으로는 탐지 불가한 저속·장기 공격(Low & Slow) 증가
3. **컴플라이언스 강화**: 개인정보보호법, 정보통신망법 등에서 장기 로그 보관 및 분석 의무화
4. **과거 데이터 소급 분석 필요**: 새로운 위협 지표(IOC) 발견 시 과거 로그에서 침해 여부 확인 필요

---

## 3. SIEM 주요 기능

- 다양한 보안장비 로그 수집 및 정규화 (파싱)
- 단일경보·상관분석 경보 생성
- 이상 그래프 시각화 (30분별·일일 그래프)
- Threat Intelligence 연동 (Black IP, URL, 취약점 정보)
- 실시간 분석 + 과거 데이터 분석
- 3D 분석, 통계·리포팅

## 3-1. SIEM 핵심 기능 상세

### (1) 로그 수집 (Log Collection)

다양한 소스에서 로그를 수집하는 방법:

| 수집 방식 | 설명 | 장점 | 단점 |
|-----------|------|------|------|
| **Agent 기반** | 대상 서버에 전용 에이전트 설치 | 안정적 수집, 로그 손실 최소화, 암호화 전송 | 에이전트 설치·관리 부담 |
| **Agentless** | WMI, WinRM, SSH 등 원격 프로토콜로 수집 | 에이전트 설치 불필요 | 네트워크 부하, 실시간성 저하 |
| **Syslog** | RFC 5424 표준 프로토콜(UDP 514 / TCP 514) | 대부분의 네트워크 장비 지원 | UDP 사용 시 로그 유실 가능 |
| **API 기반** | REST API, JDBC 등으로 수집 | 클라우드 서비스(AWS, Azure, GCP) 로그 수집에 적합 | API 호출 제한, 지연 발생 가능 |
| **파일 수집** | 로그 파일 직접 읽기(FTP, SFTP, NFS) | 레거시 시스템 대응 가능 | 실시간성 부족 |

### (2) 정규화 (Normalization)

서로 다른 형식의 로그를 **통일된 스키마(공통 필드)**로 변환하는 과정.

```
[원본 로그 - 방화벽]
Jul 29 10:23:45 FW-01 deny src=192.168.1.100 dst=10.0.0.5 port=443

[원본 로그 - IPS]
2026-07-29T10:23:45Z ALERT HIGH attack=SQL_Injection src_ip=192.168.1.100 dst_ip=10.0.0.5

              ↓ 정규화(Normalization) ↓

[정규화된 로그]
{
  timestamp: "2026-07-29T10:23:45Z",
  source_ip: "192.168.1.100",
  dest_ip: "10.0.0.5",
  device_type: "Firewall" / "IPS",
  action: "deny" / "alert",
  severity: "medium" / "high"
}
```

**정규화 공통 필드 예시**: timestamp, source_ip, dest_ip, source_port, dest_port, protocol, action, severity, device_name, device_type, event_category, raw_log

### (3) 집계 (Aggregation)

동일하거나 유사한 이벤트를 묶어서 중복을 제거하고 건수를 카운팅.

- **시간 기반 집계**: 동일 이벤트가 5분 내 100건 발생 → 1건으로 묶고 count=100 표시
- **필드 기반 집계**: 동일 출발지 IP에서 발생한 이벤트를 그룹핑
- **효과**: Alert Fatigue 감소, 저장 공간 절약, 분석 효율 향상

### (4) 상관분석 (Correlation)

여러 장비의 이벤트를 **시간 순서, 출발지/목적지 관계, 공격 시나리오** 기반으로 연계 분석.

| 상관분석 유형 | 설명 | 예시 |
|--------------|------|------|
| **룰 기반 (Rule-based)** | 사전 정의된 조건 조합으로 탐지 | "동일 IP에서 5분 내 로그인 실패 10회 + 성공 1회 → 브루트포스 의심" |
| **통계 기반 (Statistical)** | 평소 패턴 대비 이상치 탐지 | "평균 트래픽 대비 300% 이상 급증 → DDoS 의심" |
| **시나리오 기반 (Scenario)** | 공격 체인(Kill Chain) 단계별 매칭 | "스캐닝 → 취약점 공격 → 내부 확산 → 데이터 유출 순서 탐지" |
| **머신러닝 기반 (ML)** | 비지도학습으로 알려지지 않은 이상행위 탐지 | "UEBA(User Entity Behavior Analytics) 기반 내부자 위협 탐지" |

### (5) 대시보드 및 시각화

- **실시간 모니터링 대시보드**: 공격 현황, 장비 상태, 위협 레벨 실시간 표시
- **지리적 시각화(GeoIP)**: 공격 출발지를 세계지도에 표시
- **Top-N 차트**: 탐지 건수 상위 공격 유형, IP, 국가 등
- **트렌드 그래프**: 시간대별 이벤트 추이(30분별, 시간별, 일별)
- **드릴다운(Drill-down)**: 요약 화면에서 클릭하여 상세 원본 로그까지 추적

### (6) 리포팅 (Reporting)

- **정기 보고서**: 일간/주간/월간 보안관제 보고서 자동 생성
- **컴플라이언스 보고서**: ISMS-P, 개인정보보호법, 전자금융감독규정 등 대응
- **사고 대응 보고서**: 침해사고 타임라인, 영향 범위, 조치 내역 정리
- **맞춤형 보고서**: 경영진용 요약본, 기술진용 상세 분석 보고서 분리

## 3-2. 로그 수집 프로토콜 상세

| 프로토콜/방식 | 포트 | 대상 장비 | 특징 |
|--------------|------|-----------|------|
| **Syslog (UDP)** | UDP 514 | 방화벽, IDS/IPS, 스위치, 라우터 | 가장 보편적, 비연결형이라 로그 유실 가능성 있음 |
| **Syslog (TCP)** | TCP 514 / 6514(TLS) | 보안장비 전반 | 신뢰성 확보, TLS 암호화 지원(RFC 5425) |
| **SNMP Trap** | UDP 162 | 네트워크 장비(스위치, 라우터) | 장비 상태 변화(링크 다운 등) 알림 수신 |
| **NetFlow / sFlow** | UDP 2055(NetFlow) / UDP 6343(sFlow) | 라우터, L3 스위치 | 네트워크 트래픽 흐름 정보(5-tuple 기반) |
| **IPFIX** | UDP 4739 | 차세대 라우터 | NetFlow v10, 유연한 템플릿 기반 |
| **Windows Event Log** | WMI(TCP 135) / WinRM(TCP 5985/5986) | Windows 서버, AD | 로그온/로그오프, 정책 변경, 보안 이벤트 |
| **JDBC/ODBC** | 장비별 상이 | DB 서버 (Oracle, MySQL, MSSQL) | DB 감사 로그, 접근 이력 수집 |
| **REST API** | TCP 443 (HTTPS) | 클라우드(AWS CloudTrail, Azure Monitor, GCP Cloud Logging) | JSON 형태 로그, 페이지네이션 처리 필요 |
| **Kafka / Message Queue** | TCP 9092 | 대용량 로그 중계 | 고성능 로그 버퍼링, 로그 유실 방지 |

> **실무 팁**: 네트워크 장비는 Syslog, Windows 서버는 WinRM, 클라우드는 API, 대용량 환경은 Kafka를 중간 버퍼로 사용하는 것이 일반적이다.

## 3-3. Threat Intelligence 연동 상세

### Threat Intelligence(TI)란?

사이버 위협에 관한 수집·분석·가공된 정보. SIEM에 연동하면 알려진 위협 지표(IOC, Indicator of Compromise)를 기반으로 자동 탐지가 가능하다.

### TI 피드 종류

| 구분 | 소스 | 설명 |
|------|------|------|
| **오픈소스 (OSINT)** | MISP, AlienVault OTX, Abuse.ch, VirusTotal, Shodan | 무료, 커뮤니티 기반, 품질 편차 존재 |
| **상용 TI** | Recorded Future, Mandiant(구 FireEye), CrowdStrike Falcon Intelligence | 정제된 고품질 인텔리전스, 위협 행위자 프로파일링 |
| **국가기관 TI** | KISA(C-TAS), CISA(미국), NCSC(영국) | 국가 차원 위협 정보 공유 |
| **ISAC (업종별)** | 금융보안원(F-ISAC), 의료ISAC | 업종 특화 위협 정보 |

### IOC 자동 매칭 프로세스

```
[TI 피드 수신]
  │
  ├─ IP 주소 (악성 C2 서버, 봇넷 등)
  ├─ 도메인/URL (피싱, 악성코드 배포지)
  ├─ 파일 해시 (MD5, SHA256 - 악성코드)
  ├─ 이메일 주소 (피싱 발신자)
  └─ YARA 룰, STIX/TAXII 형식 데이터
  │
  ↓ SIEM에 자동 적재
  │
[실시간 로그와 IOC 매칭]
  │
  ├─ 방화벽 로그의 목적지 IP ↔ Black IP 리스트
  ├─ 프록시 로그의 URL ↔ 악성 URL 리스트
  ├─ EDR 로그의 파일 해시 ↔ 악성코드 해시 리스트
  └─ DNS 로그의 질의 도메인 ↔ 악성 도메인 리스트
  │
  ↓ 매칭 발생 시
  │
[경보 생성 및 자동 차단 연동]
```

### Black IP/URL 리스트 관리

- **자동 갱신**: TI 피드에서 주기적(1시간~24시간)으로 최신 리스트 다운로드
- **수동 등록**: 자체 분석으로 확인된 악성 지표 직접 등록
- **화이트리스트 관리**: 오탐 방지를 위한 예외 목록 관리
- **만료 관리(TTL)**: 오래된 지표는 자동 만료 처리하여 리스트 비대화 방지
- **신뢰도 점수(Confidence Score)**: 지표별 신뢰도를 부여하여 경보 우선순위 결정

## 4. 한눈에 보는 통합보안관제 흐름

```
[보안장비]
DDoS / F/W / IPS / WAF
         │
    장비별 이벤트 연동 및 파싱
         │
    로그별 유형 정리 및 특성 파악
         │
    단일장비별 경보룰 생성
         │
         ├──→ 시각화 지원
         ├──→ 자산 확인을 통한 RISK Intelligence 확보
         ├──→ 침투 시나리오 생성
         └──→ Threat Intelligence 연동
              │
         [SIEM] ──→ 알림 (SMS, E-mail)
              │
         관제 요원 → 분석·대응
```

## 5. SIEM 이후의 진화: SOAR

### SOAR (Security Orchestration, Automation and Response)

SIEM이 **탐지**에 집중한다면, SOAR는 **대응 자동화**에 집중하는 솔루션이다.

### SOAR의 3대 핵심 요소

| 요소 | 설명 |
|------|------|
| **Orchestration (오케스트레이션)** | SIEM, 방화벽, EDR, TI 등 다양한 보안 도구를 하나의 워크플로우로 연결·조율 |
| **Automation (자동화)** | 반복적인 보안 업무(티켓 생성, IP 차단, 악성코드 분석 요청 등)를 자동 수행 |
| **Response (대응)** | 사전 정의된 플레이북에 따라 인시던트에 체계적으로 대응 |

### SIEM과 SOAR의 관계

```
[SIEM] ─── 탐지·분석 ───→ 경보 발생
                              │
                              ↓
[SOAR] ─── 자동화 대응 ──→ 플레이북 실행
                              │
              ┌───────────────┼───────────────┐
              ↓               ↓               ↓
         IP 자동 차단    티켓 자동 생성    악성코드 샌드박스
         (방화벽 연동)   (Jira, ServiceNow)  분석 요청
```

### 자동화 대응 플레이북 예시: 피싱 메일 대응

```
1. SIEM에서 "피싱 의심 메일" 경보 수신
2. [자동] 메일 헤더에서 발신 IP, URL, 첨부파일 해시 추출
3. [자동] TI 피드에서 발신 IP/URL/해시 조회
4. [자동] 악성 판정 시:
   ├─ 해당 메일을 수신한 전체 사용자 목록 조회
   ├─ 메일 서버에서 해당 메일 격리(Quarantine)
   ├─ 첨부파일 해시를 EDR에서 검색 → 실행 여부 확인
   ├─ URL을 프록시에서 차단
   └─ 보안관제 티켓 자동 생성 (심각도: High)
5. [수동] 관제 요원이 결과 검토 후 최종 승인/조치
```

## 6. 최신 트렌드: XDR (Extended Detection and Response)

### XDR이란?

SIEM, SOAR, EDR의 기능을 **하나의 통합 플랫폼**으로 결합한 차세대 보안 솔루션.

기존에는 탐지(SIEM) → 대응 자동화(SOAR) → 엔드포인트 대응(EDR)이 각각 분리되어 있었으나, XDR은 이를 단일 플랫폼에서 통합 제공한다.

### SIEM vs SOAR vs XDR 비교

| 항목 | SIEM | SOAR | XDR |
|------|------|------|-----|
| **주요 목적** | 로그 수집·분석·탐지 | 대응 자동화·오케스트레이션 | 통합 탐지·대응 |
| **데이터 범위** | 모든 소스 로그 | SIEM 경보 + 외부 도구 | 엔드포인트 + 네트워크 + 클라우드 + 이메일 |
| **분석 방식** | 룰 + 상관분석 | 플레이북 기반 자동화 | AI/ML 기반 자동 상관분석 |
| **대응** | 경보 생성 (수동 대응) | 플레이북 자동 실행 | 탐지~대응 자동 연계 |
| **도입 복잡도** | 높음 (룰 튜닝 필요) | 중간 (플레이북 설계 필요) | 상대적으로 낮음 (벤더 통합) |
| **대표 제품** | Splunk, QRadar | Palo Alto XSOAR, Splunk SOAR | Palo Alto Cortex XDR, Microsoft Defender XDR, Trend Micro Vision One |

### 보안관제 솔루션 진화 요약

```
1세대: 단위 보안장비 (개별 관리)
  ↓
2세대: ESM (이벤트 통합 수집)
  ↓
3세대: SIEM (빅데이터 기반 로그 분석)
  ↓
3.5세대: SIEM + SOAR (탐지 + 자동 대응)
  ↓
4세대: XDR (통합 탐지·대응 플랫폼)
```

## 8. SIEM 도입 시 고려사항

### (1) EPS (Events Per Second) 산정

SIEM의 규모를 결정하는 가장 중요한 지표.

- **EPS**: SIEM이 초당 처리해야 하는 이벤트(로그) 수
- **산정 방법**: 각 연동 장비의 평균 EPS를 측정하여 합산

```
예시 산정:
  방화벽 3대     × 평균 500 EPS  = 1,500 EPS
  IPS 2대       × 평균 300 EPS  = 600 EPS
  WAF 2대       × 평균 200 EPS  = 400 EPS
  서버 50대     × 평균 10 EPS   = 500 EPS
  네트워크장비 20대 × 평균 5 EPS = 100 EPS
  ─────────────────────────────────
  총 예상 EPS                    = 3,100 EPS
  피크 시간 대비 여유분 (×2~3)    = 6,200 ~ 9,300 EPS
  
  → 최소 10,000 EPS급 SIEM 도입 필요
```

### (2) 로그 저장 용량 계산

```
일일 로그량 = EPS × 86,400초 × 평균 로그 크기(bytes)

예시:
  5,000 EPS × 86,400초 × 500 bytes = 약 216 GB/일
  
  90일 보관 시: 216 GB × 90 = 약 19.4 TB
  1년 보관 시: 216 GB × 365 = 약 78.8 TB
  
  압축률 적용(50~70%): 78.8 TB × 0.4 = 약 31.5 TB (실 저장 용량)
```

> **참고**: 정보통신망법 등에 따라 접속기록 최소 1년(금융은 5년) 보관 의무가 있으므로 법적 요건을 반드시 반영해야 한다.

### (3) 라이선스 모델

| 모델 | 설명 | 대표 제품 |
|------|------|-----------|
| **EPS 기반** | 초당 처리 이벤트 수에 따라 과금 | 이글루 SPiDER TM, IBM QRadar |
| **데이터 볼륨 기반** | 일일 인덱싱 데이터량(GB/일)에 따라 과금 | Splunk |
| **종량제 (Pay-as-you-go)** | 실제 사용량 기반 과금 | Microsoft Sentinel |
| **노드/장비 수 기반** | 연동 장비 수에 따라 과금 | 일부 국내 제품 |
| **오픈소스 + 기술지원** | 기본 기능 무료, 기술지원·고급 기능 유료 구독 | Elastic SIEM |

### (4) 연동 가능 장비 및 확장성

도입 전 반드시 확인해야 할 사항:

- 현재 운영 중인 보안장비·서버·네트워크 장비와의 **로그 연동 호환성**
- 향후 도입 예정 장비에 대한 **커스텀 파서 개발 가능 여부**
- 클라우드 환경(AWS, Azure, GCP) **로그 수집 지원 여부**
- STIX/TAXII 등 **TI 표준 프로토콜 지원 여부**
- API를 통한 **SOAR/티켓 시스템 연동 가능 여부**
- 수평 확장(Scale-out) 가능 여부 및 **클러스터링 지원**
