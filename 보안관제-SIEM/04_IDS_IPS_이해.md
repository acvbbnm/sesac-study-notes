# 04. IDS / IPS 이해

---

## 1. IDS (Intrusion Detection System, 침입탐지시스템)

컴퓨터 또는 네트워크에서 발생하는 이벤트들을 모니터링하고, 침입 발생 여부를 **탐지(Detection)**하고 **대응(Response)**하는 자동화된 시스템.

- 원본 트래픽을 손실·변조 없이 복사 → 트래픽 유통에 관여하지 않음 (**Out of Path** 방식)

### 동작 원리

```
① 데이터 수집
   └─ 시스템 사용 내역, 네트워크 패킷 등 수집

② 데이터 가공 및 축약
   └─ 수집된 감사 데이터를 침입 판정 가능한 의미 있는 정보로 변환

③ 침입 분석 및 탐지
   └─ 비정상 행위(행위기반) 또는 오용 탐지(지식기반)로 침입 여부 판정

④ 보고 및 대응
   └─ 침입으로 판단 시 보안관리자에게 보고 → 관리자가 조치 수행
```

### IDS 유형 분류

IDS는 감시 대상에 따라 크게 **NIDS**와 **HIDS**로 분류된다.

#### NIDS (Network-based IDS)

네트워크 세그먼트에 배치되어 해당 구간을 통과하는 **모든 패킷을 캡처·분석**하는 방식.

- **배치 위치**: 방화벽 뒤 스위치의 미러(SPAN) 포트, DMZ 구간, 인터넷 경계 구간
- **동작 방식**: 네트워크 인터페이스를 Promiscuous 모드로 설정하여 모든 패킷을 수신·분석

```
인터넷 ── 라우터 ── 방화벽 ── 스위치 ──(SPAN/Mirror)──→ NIDS
                                  │
                               서버군
```

| 장점 | 단점 |
|------|------|
| 네트워크 전체를 소수의 센서로 감시 가능 | 암호화된 트래픽(HTTPS, VPN) 내용 분석 불가 |
| 호스트에 에이전트 설치 불필요 | 고속 네트워크(10Gbps 이상)에서 패킷 손실 가능 |
| OS 독립적으로 운영 가능 | 스위치 환경에서 별도 미러링 설정 필요 |
| 공격자가 탐지 장비의 존재를 알기 어려움 | 호스트 내부의 로컬 공격(권한 상승 등) 탐지 불가 |

#### HIDS (Host-based IDS)

개별 호스트(서버, 워크스테이션)에 에이전트를 설치하여 해당 시스템의 **로그, 파일 시스템 변경, 프로세스 활동** 등을 감시하는 방식.

- **배치 위치**: 보호 대상 서버(웹 서버, DB 서버 등)에 직접 설치
- **감시 대상**: 시스템 로그, 파일 무결성(해시 비교), 레지스트리 변경, 프로세스 목록, 커널 모듈

| 장점 | 단점 |
|------|------|
| 암호화된 트래픽도 복호화 후 분석 가능 | 각 호스트마다 설치·관리 필요 (운영 비용 증가) |
| 파일 변조, 권한 상승 등 로컬 공격 탐지 가능 | 호스트 자원(CPU, 메모리) 소모 |
| 사용자 행위와 명령어 수준의 상세 감사 가능 | 네트워크 레벨 공격(DDoS, 포트스캔) 탐지 어려움 |
| 해당 호스트에 특화된 정밀 탐지 가능 | 공격자가 루트 권한 획득 시 에이전트 무력화 가능 |

**대표 제품**: OSSEC(오픈소스 HIDS), Tripwire(파일 무결성), Wazuh

#### NIDS vs HIDS 요약 비교

| 구분 | NIDS | HIDS |
|------|------|------|
| 감시 범위 | 네트워크 세그먼트 전체 | 개별 호스트 |
| 설치 위치 | 스위치 미러 포트 / TAP 장비 | 보호 대상 서버 |
| 암호화 트래픽 | 분석 불가 | 분석 가능 |
| 내부자 위협 | 네트워크 이상만 탐지 | 로컬 행위까지 탐지 |
| 운영 부하 | 네트워크에만 영향 | 호스트 자원 소모 |
| 권장 운영 | 경계 구간 감시 | 핵심 서버 정밀 감시 |

> **실무 팁**: NIDS와 HIDS를 **함께 운영**하는 것이 가장 효과적이다. NIDS로 네트워크 경계를 감시하고, 핵심 서버에는 HIDS를 설치하여 심층 방어(Defense in Depth)를 구현한다.

### 탐지 방식 비교

| 방식 | 원리 | 장점 | 단점 |
|------|------|------|------|
| **지식기반 / 오용탐지** (Signature-based) | 알려진 공격 패턴(Signature)과 매칭 | 오탐률 낮음. 트로이목마·백도어 탐지 가능 | 신규·알려지지 않은 공격 탐지 불가. 탐지율 낮음 |
| **행위기반 / 비정상탐지** (Anomaly-based) | 급격한 변화·통계적 이상 탐지 | 알려지지 않은 신규 공격 탐지 가능 | False Positive(오탐률) 높음 |

### 탐지 방식 심화

#### Signature-based (지식기반 / 오용탐지) 동작 원리

사전에 정의된 **공격 시그니처(패턴)**를 데이터베이스에 저장하고, 수집된 트래픽·로그와 **패턴 매칭**을 수행하여 일치하면 공격으로 판정하는 방식.

**핵심 기술**:

1. **문자열 패턴 매칭**: 패킷 페이로드에서 특정 문자열 검색
   - 예: HTTP 요청에서 `../etc/passwd` 문자열 탐지 → 디렉토리 트래버설 공격
   - 예: 패킷 내 `<script>alert(` 문자열 탐지 → XSS 공격

2. **정규식(Regular Expression) 매칭**: 유연한 패턴 정의
   - 예: `/\.\.\/(\.\.\/)*etc\/passwd/` → 다양한 변형의 경로 조작 탐지
   - 예: `/union\s+(all\s+)?select/i` → SQL Injection 변형 탐지

3. **헤더 필드 검사**: 프로토콜 헤더의 비정상 값 확인
   - 예: TCP 플래그 조합 `SYN+FIN` 동시 설정 → 비정상 패킷(스캔 공격)

**한계점**: 시그니처에 등록되지 않은 **Zero-day 공격**이나 시그니처를 우회하도록 변형된 공격은 탐지 불가 → 지속적인 시그니처 업데이트가 필수

#### Anomaly-based (행위기반 / 비정상탐지) 동작 원리

정상 상태의 **베이스라인(Baseline)**을 먼저 수립하고, 현재 활동이 베이스라인에서 벗어나면 **비정상(Anomaly)**으로 판정하는 방식.

**베이스라인 수립 방법**:

1. **통계적 분석**: 일정 기간 동안 정상 트래픽의 통계치(평균, 표준편차)를 수집
   - 예: 평소 웹 서버 트래픽이 100Mbps인데 갑자기 2Gbps로 증가 → DDoS 의심
   - 예: 특정 사용자가 평소 09~18시에 접속하는데 새벽 3시에 대량 파일 다운로드 → 내부자 위협 의심

2. **프로파일 기반 분석**: 사용자·시스템·네트워크별 정상 행위 프로파일 생성
   - 로그인 시간대, 접근하는 자원, 데이터 전송량 등을 프로파일화

3. **머신러닝 기반 탐지**: 학습 알고리즘을 사용하여 정상/비정상 패턴 자동 분류
   - 비지도학습: 클러스터링을 통해 정상 그룹에서 벗어나는 이상치(Outlier) 탐지
   - 지도학습: 레이블링된 공격/정상 데이터로 분류 모델 학습
   - 딥러닝: RNN, LSTM 등을 이용한 시계열 트래픽 이상 탐지

**장점**: Zero-day 공격, 내부자 위협 등 알려지지 않은 공격 탐지 가능  
**단점**: 학습 기간 필요, 오탐률(False Positive)이 높음, 베이스라인 자체가 오염될 수 있음

#### Stateful Protocol Analysis (상태 기반 프로토콜 분석)

프로토콜의 **정상적인 상태 전이(State Transition)**를 미리 정의하고, 실제 트래픽이 이 모델에서 벗어나는지 검사하는 방식.

- 예: HTTP 프로토콜에서 요청(Request) 없이 응답(Response)만 오는 경우 → 비정상
- 예: TCP 3-Way Handshake 없이 데이터 전송이 발생하는 경우 → 비정상
- 예: FTP에서 인증(USER/PASS) 없이 파일 전송(RETR) 명령이 오는 경우 → 비정상

**Signature-based와의 차이점**: 단순 패턴 매칭이 아닌 **프로토콜 문맥(Context)**을 이해하므로 더 정밀한 탐지 가능

---

### 장점 / 단점

**장점**
- 내부 사용자의 오·남용 탐지 가능
- 해킹 사고 발생 시 어느 정도 근원지 추적 가능

**단점**
- 대규모 네트워크에 사용 곤란
- 관리 및 운영이 어려움
- 새로운 침입 기법에 대한 즉각 대응 곤란
- 보안사고에 대한 근본적 해결책 아님

## 2. IPS (Intrusion Prevention System, 침입방지시스템)

다양한 보안기술을 이용하여 침입이 일어나기 전에 실시간으로 침입을 막고, 유해 트래픽을 차단하기 위한 **능동형 보안 솔루션**.

- IPS: **예방적·사전 조치** / IDS: **탐지적·사후 조치**
- 트래픽 유통에 직접 관여 → **In-line** 방식

### 공격 패턴 인지 방식

| 방식 | 설명 | 특징 |
|------|------|------|
| **Signature Based (지식기반)** | 각 공격에 정확한 Signature 정의 → 패턴 매칭 시 차단 | 오탐 가능성 적음. 알려지지 않은 공격에 Signature 없으면 차단 불가 |
| **Heuristics Based (행위기반)** | Anomaly Detection 방식. 알려지지 않은 공격 수집·분석 | 능동적 대처 가능. 오탐 가능성 있음 |

### IPS 오탐 시 영향과 운영 방법

IPS는 **In-line 방식**으로 트래픽 경로에 직접 위치하므로, 오탐(False Positive) 발생 시 **정상 서비스 트래픽까지 차단**하는 심각한 문제가 발생할 수 있다.

#### 오탐 발생 시 영향

```
정상 사용자 요청 ──→ IPS (오탐으로 차단) ──✕──→ 웹 서버
                        │
                    정상 트래픽이 DROP 됨
                    → 서비스 장애 발생
                    → 고객 불만, 매출 손실
```

- 웹 서비스 접속 불가 (HTTP 요청이 공격으로 오인)
- 정상 업무용 파일 전송 차단 (대용량 파일이 공격 패턴으로 오인)
- VPN 접속 차단 (암호화 트래픽의 일부 패턴이 공격으로 오인)
- 특정 애플리케이션 통신 불가 (비표준 프로토콜이 비정상으로 판단)

#### 안전한 운영을 위한 전환 절차

IPS 도입 시 반드시 다음의 **단계적 전환 절차**를 따라야 한다:

```
[1단계] 탐지 모드 (Detection/Monitor Mode)
   └─ IPS를 In-line에 배치하되, 차단 없이 탐지만 수행
   └─ 기간: 최소 2~4주 (트래픽 패턴 충분히 수집)
   └─ 목적: 오탐 패턴 파악 및 정책 튜닝
       ↓
[2단계] 선별적 차단 모드
   └─ 확실한 공격(Critical/High 위험도)만 차단, 나머지는 탐지
   └─ 화이트리스트 정책 적용 (정상 트래픽 예외 처리)
   └─ 기간: 2~4주 추가 관찰
       ↓
[3단계] 전면 차단 모드 (Prevention Mode)
   └─ 전체 정책에 대해 차단 활성화
   └─ 지속적인 모니터링 및 오탐 피드백 반영
```

**운영 시 핵심 수칙**:
- 신규 시그니처 적용 시 반드시 **탐지 모드로 먼저 테스트** 후 차단 전환
- **Bypass(Fail-Open) 기능** 설정: IPS 장비 장애 시 트래픽이 차단되지 않고 통과되도록 구성
- 주요 서비스 IP/포트에 대한 **화이트리스트** 관리
- 오탐 발생 시 즉시 해당 시그니처를 **탐지 모드로 전환**하고, 원인 분석 후 재적용

## 3. IDS vs IPS 비교

| 구분 | IDS | IPS |
|------|-----|-----|
| 목적 | 침입 여부의 **감지** | 침입 이전의 **방지** |
| 구성 방식 | Out of Path (Sniffing) | In-line |
| 탐지 기반 | 로그·Signature 기반 패턴 매칭, 비정상 행위 탐지 | 정책·규칙 DB 기반 |
| 대응 | 실시간 탐지 + 사후 분석 대응 | 실시간 즉각 대응, 세션 기반 탐지 |
| 단점 | 차단 불가 | 오탐 현상 발생 시 정상 트래픽 차단 위험, 고가 장비 |

### 구성도 비교

```
[IDS 구성]                          [IPS 구성]
라우터                              라우터
  │                                   │
방화벽                              방화벽
  │                                   │
스위치 ──(Mirror)──→ IDS            IPS (In-line)
  │                                   │
서버군                              스위치
                                       │
                                    서버군
```

## 4. IDS/IPS 주요 기능

### 실시간 모니터

- TCP/IP 상의 애플리케이션 프로토콜별 트래픽 24시간 모니터링
- 서비스별·컴퓨터별·관리자별 상세 내역 검색
- 서버·관리자·사용량·사용시간·네트워크/시스템 부하량 등 관리 정보 제공

### 탐지/방어/경보

- 비인가·비정상 사용자 침투 시 실시간 차단·경보 조치
- 공격 시간·공격자 정보·조치사항·위험도 등 상세 정보 표시

### 실시간 차단 목록

- **동적 차단 목록**: 실시간으로 차단하는 내역 (차단시간·방법·공격주소·대상주소)
- **방화벽 로그**: 방화벽 정책 관련 내역

## 5. IDS/IPS 로그 구성

```
[Victim=125.209.210.92]     ← 공격 대상 IP
[Protocol=tcp/80]           ← 대상 프로토콜 및 포트
[Risk=High]                 ← SNIPER IPS 정의 위험도
[Handling=Alarm]            ← 공격에 대한 IPS의 대응 방법
[Information=]              ← 부가 정보
[SrcPort=57231]             ← 공격자 Port
[HackType=00004]            ← SNIPER IPS 정의 공격 카테고리
```

## 6. IDS/IPS 정책 운영 시 주의사항

- IDS/IPS는 **탐지 정책(Signature)이 등록된 경우에만** 탐지하고, 나머지 패킷은 무시 (Positive 방식)
- 탐지된 것은 이미 공격이 시스템에 도달했음을 의미 → 지속적인 탐지 정책 업데이트 필요
- 오탐율이 매우 높으므로 최적화를 위해 충분한 **Customizing** 시간 필요
- **RawData 정책**을 어떻게 활용하느냐가 관제 품질의 핵심

## 7. Snort 룰 구조

Snort는 가장 널리 사용되는 **오픈소스 NIDS**로, 시그니처 기반 탐지를 수행한다. Snort 룰의 기본 구조를 이해하는 것은 IDS/IPS 정책 관리의 핵심이다.

### 룰 기본 구조

Snort 룰은 크게 **룰 헤더(Rule Header)**와 **룰 옵션(Rule Options)**으로 구성된다.

```
[액션] [프로토콜] [출발지IP] [출발지Port] -> [목적지IP] [목적지Port] (옵션들)
```

```
alert tcp any any -> $HOME_NET 80 (msg:"SQL Injection 시도"; content:"union select"; nocase; sid:1000001; rev:1;)
├─── 룰 헤더 ────────────────────┤ ├──────────── 룰 옵션 ──────────────────────────────────────────┤
```

### 룰 헤더 각 필드 설명

| 필드 | 설명 | 예시 |
|------|------|------|
| **액션(Action)** | 룰 매칭 시 수행할 동작 | `alert`, `log`, `pass`, `drop`, `reject` |
| **프로토콜(Protocol)** | 검사 대상 프로토콜 | `tcp`, `udp`, `icmp`, `ip` |
| **출발지 IP** | 패킷의 출발지 IP 주소 | `any`, `192.168.1.0/24`, `$EXTERNAL_NET` |
| **출발지 Port** | 패킷의 출발지 포트 | `any`, `80`, `1024:` (1024 이상) |
| **방향 연산자** | 트래픽 방향 | `->` (단방향), `<>` (양방향) |
| **목적지 IP** | 패킷의 목적지 IP 주소 | `$HOME_NET`, `10.0.0.0/8` |
| **목적지 Port** | 패킷의 목적지 포트 | `80`, `[80,443]`, `!22` (22 제외) |

**주요 액션**:
- `alert`: 경고 생성 + 로그 기록
- `log`: 로그만 기록
- `pass`: 해당 패킷 무시 (화이트리스트)
- `drop`: 패킷 차단 + 로그 기록 (IPS 모드)
- `reject`: 패킷 차단 + RST/ICMP 응답 전송

### 주요 룰 옵션

| 옵션 | 설명 | 예시 |
|------|------|------|
| `msg` | 경고 메시지 (관제 화면에 표시) | `msg:"XSS 공격 탐지";` |
| `content` | 페이로드에서 검색할 문자열 | `content:"\|2f 65 74 63 2f\|passwd";` |
| `nocase` | 대소문자 구분 없이 매칭 | `nocase;` |
| `offset` | content 검색 시작 위치 (바이트) | `offset:0;` |
| `depth` | content 검색 범위 (바이트) | `depth:50;` |
| `pcre` | 정규식 패턴 매칭 | `pcre:"/union\s+select/i";` |
| `flow` | 세션 상태 및 방향 지정 | `flow:to_server,established;` |
| `sid` | 룰 고유 식별 번호 | `sid:1000001;` |
| `rev` | 룰 수정 버전 | `rev:3;` |
| `classtype` | 공격 분류 | `classtype:web-application-attack;` |
| `priority` | 우선순위 (1=높음, 4=낮음) | `priority:1;` |
| `reference` | 참조 정보 (CVE 등) | `reference:cve,2021-44228;` |
| `threshold` | 임계값 설정 (반복 탐지 제어) | `threshold:type both, track by_src, count 5, seconds 60;` |

### 실전 룰 예시

#### 예시 1: SQL Injection 탐지

```
alert tcp $EXTERNAL_NET any -> $HOME_NET 80 (
    msg:"SQL Injection - UNION SELECT 탐지";
    flow:to_server,established;
    content:"union"; nocase;
    content:"select"; nocase; distance:0; within:20;
    pcre:"/union\s+(all\s+)?select/i";
    classtype:web-application-attack;
    sid:1000001; rev:1;
)
```

#### 예시 2: 디렉토리 트래버설 공격 탐지

```
alert tcp $EXTERNAL_NET any -> $HOME_NET $HTTP_PORTS (
    msg:"Directory Traversal - /etc/passwd 접근 시도";
    flow:to_server,established;
    content:".."; content:"/etc/passwd";
    classtype:web-application-attack;
    sid:1000002; rev:1;
)
```

#### 예시 3: SSH 브루트포스 탐지

```
alert tcp $EXTERNAL_NET any -> $HOME_NET 22 (
    msg:"SSH 브루트포스 공격 의심 - 60초 내 5회 이상 접속 시도";
    flow:to_server,established;
    threshold:type both, track by_src, count 5, seconds 60;
    classtype:attempted-admin;
    sid:1000003; rev:1;
)
```

#### 예시 4: Log4Shell (CVE-2021-44228) 탐지

```
alert tcp any any -> $HOME_NET any (
    msg:"Log4Shell JNDI Injection 탐지";
    flow:to_server,established;
    content:"${jndi:"; nocase;
    reference:cve,2021-44228;
    classtype:attempted-admin;
    priority:1;
    sid:1000004; rev:2;
)
```

## 8. 오탐(False Positive)과 미탐(False Negative)

보안관제에서 IDS/IPS의 탐지 품질을 결정짓는 가장 핵심적인 개념이다.

### 정의

| 구분 | 정의 | 설명 |
|------|------|------|
| **True Positive (정탐)** | 실제 공격을 공격으로 탐지 | 정상적인 탐지. 이상적 상황 |
| **False Positive (오탐)** | 정상 트래픽을 공격으로 잘못 탐지 | 관제 피로도 증가, IPS에서는 서비스 장애 유발 |
| **False Negative (미탐)** | 실제 공격을 탐지하지 못함 | 가장 위험. 침해사고로 이어질 수 있음 |
| **True Negative (정상)** | 정상 트래픽을 정상으로 판단 | 정상적인 판단. 이상적 상황 |

```
                    실제 상태
                 공격       정상
탐지    공격   TP(정탐)   FP(오탐)
결과    정상   FN(미탐)   TN(정상)
```

### 오탐(False Positive) 발생 원인

- **시그니처가 너무 광범위**: 지나치게 포괄적인 패턴으로 정상 트래픽까지 매칭
  - 예: `content:"select"` 만으로 탐지 → 일반 검색어 "select your plan"도 탐지
- **환경 미반영**: 내부 취약점 스캐너, 모의해킹 도구, 개발 서버의 테스트 트래픽
- **프로토콜 오인식**: 비표준 포트 사용이나 커스텀 프로토콜을 오인
- **임계값 부적절**: 너무 낮은 threshold 설정

### 미탐(False Negative) 발생 원인

- **시그니처 미등록**: 새로운 공격 유형에 대한 패턴이 DB에 없음 (Zero-day)
- **우회 기법 사용**: 패킷 분할, 인코딩 변환 등으로 시그니처 회피
- **암호화 트래픽**: HTTPS 등 암호화된 통신 내 공격 페이로드 분석 불가
- **성능 한계**: 고속 트래픽에서 패킷 유실로 인한 탐지 누락

### 튜닝 방법

| 튜닝 방법 | 설명 |
|-----------|------|
| **시그니처 정밀화** | `content` 조건을 구체화하고, `offset`, `depth`, `within` 등으로 검색 범위 한정 |
| **화이트리스트 적용** | 내부 스캐너, 관리 도구 등의 IP/포트를 예외 처리 (`pass` 룰 활용) |
| **임계값 조정** | `threshold` 옵션으로 일정 횟수 이상 반복 시에만 탐지 |
| **컨텍스트 추가** | `flow:established` 등으로 세션 상태 조건 추가 |
| **환경 변수 활용** | `$HOME_NET`, `$EXTERNAL_NET` 등을 실제 네트워크에 맞게 설정 |
| **정기적 리뷰** | 주기적으로 탐지 로그를 분석하여 반복 오탐 패턴 제거 |

### 보안관제에서의 중요성

- **오탐이 많으면**: 관제 요원의 **경보 피로(Alert Fatigue)** 발생 → 실제 공격을 놓칠 위험 증가
- **미탐이 많으면**: 침해사고가 발생해도 인지하지 못함 → 대응 시점을 놓치게 됨
- **오탐률과 미탐률은 트레이드오프 관계**: 탐지 민감도를 높이면 오탐 증가, 낮추면 미탐 증가
- 관제 품질의 핵심은 이 **균형점(Sweet Spot)**을 찾는 것이며, 이를 위해 지속적인 **정책 튜닝**이 필수

## 9. IDS/IPS 우회 기법

방어자가 IDS/IPS의 한계를 이해하고 대응하기 위해 반드시 알아야 할 주요 우회 기법들이다.

### 주요 우회 기법

#### 1. 패킷 분할 (Fragmentation)

IP 패킷을 아주 작은 조각(Fragment)으로 나누어 전송함으로써, IDS가 개별 조각에서 시그니처를 매칭하지 못하게 하는 기법.

```
원본 패킷: "GET /etc/passwd HTTP/1.1"

분할 후:
  Fragment 1: "GET /e"
  Fragment 2: "tc/pa"
  Fragment 3: "sswd "
  Fragment 4: "HTTP/"
  Fragment 5: "1.1"

→ IDS가 각 조각만 보면 "/etc/passwd" 패턴 매칭 실패
→ 목적지 서버에서 재조립 후 정상 처리
```

**대응**: IDS/IPS에서 **패킷 재조립(Reassembly)** 기능 활성화

#### 2. 인코딩 우회

공격 페이로드를 다양한 인코딩 방식으로 변환하여 시그니처를 회피하는 기법.

| 인코딩 방식 | 원본 | 인코딩 후 |
|-------------|------|-----------|
| URL 인코딩 | `/etc/passwd` | `%2fetc%2fpasswd` |
| 더블 URL 인코딩 | `/etc/passwd` | `%252fetc%252fpasswd` |
| 유니코드 | `../` | `..%c0%af` |
| Hex 인코딩 | `<script>` | `%3cscript%3e` |
| Base64 | 공격 코드 | `YXR0YWNrIGNvZGU=` |

**대응**: IDS/IPS에서 **다중 디코딩(Normalization)** 기능 활성화, `http_inspect` 프리프로세서 사용

#### 3. 세션 스플라이싱 (Session Splicing)

TCP 세그먼트를 매우 작게 분할하고, 각 세그먼트 사이에 시간 간격을 두어 전송하는 기법. IDS의 세션 타임아웃보다 느리게 보내면 세션 추적을 회피할 수 있다.

```
세그먼트 1: "uni"     (전송 후 15초 대기)
세그먼트 2: "on "     (전송 후 15초 대기)
세그먼트 3: "sel"     (전송 후 15초 대기)
세그먼트 4: "ect"

→ IDS 세션 타임아웃이 10초이면 세션을 추적하지 못함
→ 서버에서는 TCP 재조립으로 정상 처리
```

**대응**: IDS의 **세션 타임아웃 값을 충분히 길게 설정**, `stream5` 프리프로세서 튜닝

#### 4. 느린 스캔 (Slow Scan)

포트 스캔이나 취약점 스캔을 매우 느린 속도로 수행하여 IDS의 **시간 기반 임계값(threshold)** 탐지를 회피하는 기법.

- 일반 스캔: 1초에 수백 개 포트 스캔 → IDS 탐지
- 느린 스캔: 1시간에 1개 포트 스캔 → 임계값 미달로 탐지 회피

**대응**: 장기간 로그 상관분석(Correlation), SIEM 연동을 통한 누적 분석

#### 5. TTL 조작 (TTL Manipulation)

IDS와 목적지 서버 사이의 네트워크 홉(Hop) 차이를 이용하여, IDS에는 도달하지만 서버에는 도달하지 않는 가짜 패킷을 삽입하는 기법.

```
공격자 → [패킷A: "GET /nor" TTL=높음] → IDS(통과) → 서버(도달)
공격자 → [패킷B: "mal.html" TTL=낮음] → IDS(통과) → 라우터에서 폐기(TTL 만료)
공격자 → [패킷C: "etc/passwd" TTL=높음] → IDS(통과) → 서버(도달)

IDS가 보는 것: "GET /normal.htmletc/passwd" → 정상으로 판단
서버가 받는 것: "GET /noretc/passwd" → 공격 성공
```

**대응**: IDS에서 **TTL 기반 패킷 무결성 검증** 활성화

### 우회 기법을 방어자가 알아야 하는 이유

- IDS/IPS는 **만능이 아니며** 우회될 수 있다는 사실을 인지해야 함
- 우회 기법을 이해해야 **탐지 정책을 정밀하게 튜닝** 가능
- **프리프로세서 설정**(패킷 재조립, 프로토콜 정규화)의 중요성 인식
- **다층 방어(Defense in Depth)** 전략의 필요성: IDS/IPS만으로는 충분하지 않으며, WAF, SIEM, EDR 등과 연동 필요

## 10. 오픈소스 IDS/IPS: Snort vs Suricata 비교

| 비교 항목 | Snort | Suricata |
|-----------|-------|----------|
| **개발 주체** | Sourcefire (현 Cisco) | OISF (Open Information Security Foundation) |
| **최초 출시** | 1998년 | 2010년 |
| **처리 방식** | 단일 스레드 (Snort 2.x) / 다중 스레드 (Snort 3) | **멀티 스레드** 기본 지원 |
| **성능** | 단일 코어 성능 우수 | 멀티코어 환경에서 고성능 (10Gbps+ 처리) |
| **룰 호환성** | Snort 룰 (VRT/Community 룰) | **Snort 룰 호환** + ET(Emerging Threats) 룰 |
| **프로토콜 분석** | 프리프로세서 기반 | **Application Layer 프로토콜 자동 감지** |
| **파일 추출** | 제한적 | HTTP/SMTP 등에서 **파일 추출·해시 비교** 지원 |
| **출력 형식** | Unified2, Syslog 등 | EVE JSON (Elasticsearch 연동 용이) |
| **Lua 스크립트** | Snort 3에서 지원 | 기본 지원 (커스텀 탐지 로직) |
| **IPS 모드** | 지원 (iptables 연동) | 지원 (NFQ, AF_PACKET, DPDK) |
| **라이선스** | GPL v2 | GPL v2 |

### 선택 가이드

- **고속 네트워크(10Gbps 이상)** 환경 → **Suricata** 권장 (멀티스레드)
- **기존 Snort 룰 자산이 많은 경우** → 두 엔진 모두 호환 가능
- **ELK 스택(Elasticsearch + Kibana) 연동** → Suricata의 EVE JSON 출력이 유리
- **파일 기반 위협 탐지 필요** → Suricata의 파일 추출 기능 활용
- **학습·교육 목적** → Snort (레퍼런스가 풍부)

## 11. 국내 주요 IPS 제품

| 제품명 | 제조사 | 특징 |
|--------|--------|------|
| **SNIPER IPS** | 윈스(WINS) | 국내 시장 점유율 1위. 한국 네트워크 환경에 특화된 시그니처 제공. 관제 연동 용이. 다양한 공공기관·기업 납품 실적 |
| **TMS (Threat Management System)** | 안랩(AhnLab) | DDoS 탐지·차단 특화. 안랩의 위협 인텔리전스와 연동. V3 등 안랩 보안 제품군과 통합 관리 |
| **SECUI MFI** | 시큐아이(SECUI) | 방화벽·IPS 통합(UTM). 고성능 하드웨어 일체형. LG U+ 그룹사 기반 기술력 |
| **AXGATE** | 엑스게이트 | 차세대 방화벽(NGFW) + IPS 통합. 가상화·클라우드 환경 지원 |
| **BLUEMAX NGF** | 파이오링크 | 애플리케이션 인지 기반 IPS. L7 레벨 정밀 탐지. ADC(Application Delivery Controller)와 통합 |

### 국내 IPS 제품의 공통 특징
