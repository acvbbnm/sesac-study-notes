# 05. 웹방화벽 (WAF) 이해

---

## 1. 개요

웹 기반 서비스가 발전하면서 항상 개방되어 있는 웹(포트 80/443)을 통한 공격이 일반화·집중화됨. 단순 홈페이지 변조부터 웹서버를 통한 악성코드 유포까지 사고 발생.

**WAF (Web Application Firewall)**는 웹서버 앞 단에 위치하여 외부에서 들어오는 HTTP/HTTPS 프로토콜 트래픽을 감시하고, 웹 어플리케이션에 대한 악의적인 공격을 웹서버 도달 전에 차단하는 전용 보안 시스템.

> 방화벽은 80/443 포트 자체를 열어두어야 하므로 해당 포트를 통한 웹 공격은 차단 불가 → WAF로 보완

---

## 2. WAF 등장 배경

### 2.1 웹 서비스의 폭발적 증가

- 2000년대 이후 전자상거래, 온라인 뱅킹, 클라우드 서비스 등 웹 기반 서비스가 기하급수적으로 증가
- 기업의 핵심 비즈니스가 웹 애플리케이션을 통해 운영되면서 공격 표면(Attack Surface)이 크게 확대
- 모바일 앱도 내부적으로 웹 API(REST, GraphQL)를 사용하므로 웹 공격의 영향 범위가 더욱 넓어짐

### 2.2 기존 보안장비의 한계

| 보안장비 | 한계점 |
|----------|--------|
| **방화벽** | L3/L4 계층에서 IP·포트 기반 필터링만 수행. HTTP 80/443 포트는 서비스를 위해 반드시 열어두어야 하므로, 해당 포트를 통한 웹 공격은 탐지·차단 불가 |
| **IPS/IDS** | 시그니처 기반 패턴 매칭으로 일부 웹 공격 탐지 가능하나, HTTP 프로토콜의 구조(헤더, 쿠키, 파라미터, POST 바디 등)를 깊이 파싱하지 못함. 인코딩·난독화된 공격에 취약 |
| **네트워크 보안장비** | SSL/TLS 암호화 트래픽(HTTPS) 내부를 복호화하여 검사하기 어려움 |

### 2.3 웹 애플리케이션 취약점의 특수성

- 웹 애플리케이션은 사용자 입력을 직접 처리하므로 입력값 검증 실패 시 SQL Injection, XSS 등 심각한 취약점 발생
- 개발자마다 보안 수준이 달라 일관된 보안 품질 확보가 어려움
- 소스코드 수정 없이 앞단에서 공격을 차단할 수 있는 WAF의 필요성 대두
- 개인정보보호법, 정보통신망법 등 컴플라이언스 요건에서도 웹방화벽 도입을 권고·의무화

## 3. OWASP Top 10 (2021년 기준)

OWASP(Open Web Application Security Project)는 웹 애플리케이션 보안 위협을 정기적으로 분석하여 가장 위험한 10가지 취약점을 발표한다. WAF는 이러한 OWASP Top 10 위협을 방어하는 핵심 수단이다.

| 순위 | 항목 | 설명 |
|------|------|------|
| **A01** | **Broken Access Control** (취약한 접근 제어) | 인가되지 않은 사용자가 다른 사용자의 데이터에 접근하거나 관리자 기능을 사용할 수 있는 취약점. IDOR(Insecure Direct Object Reference), 수평/수직 권한 상승 등 포함 |
| **A02** | **Cryptographic Failures** (암호화 실패) | 민감 데이터(비밀번호, 신용카드, 개인정보)가 평문 전송·저장되거나, 취약한 암호 알고리즘(MD5, SHA1) 사용. 이전 명칭: Sensitive Data Exposure |
| **A03** | **Injection** (인젝션) | 사용자 입력이 검증 없이 쿼리·명령에 삽입되어 SQL Injection, NoSQL Injection, OS Command Injection, LDAP Injection 등 발생. XSS도 이 범주에 포함(HTML Injection) |
| **A04** | **Insecure Design** (불안전한 설계) | 설계 단계부터 보안을 고려하지 않아 발생하는 근본적 결함. Threat Modeling 미수행, 비즈니스 로직 취약점 등 |
| **A05** | **Security Misconfiguration** (보안 설정 오류) | 불필요한 기능 활성화, 기본 계정·비밀번호 미변경, 상세한 에러 메시지 노출, 디렉터리 리스팅 허용, 불필요한 HTTP 메서드 허용 등 |
| **A06** | **Vulnerable and Outdated Components** (취약하고 오래된 구성 요소) | 알려진 취약점이 있는 라이브러리·프레임워크·OS를 패치 없이 사용. Apache Struts, Log4j 등의 사례 |
| **A07** | **Identification and Authentication Failures** (식별 및 인증 실패) | 세션 관리 취약점, 무차별 대입(Brute Force) 허용, 약한 비밀번호 정책, 세션 고정(Session Fixation), 다중 인증(MFA) 미적용 |
| **A08** | **Software and Data Integrity Failures** (소프트웨어 및 데이터 무결성 실패) | CI/CD 파이프라인의 무결성 미검증, 안전하지 않은 역직렬화(Insecure Deserialization), 신뢰할 수 없는 소스의 플러그인·라이브러리 사용 |
| **A09** | **Security Logging and Monitoring Failures** (보안 로깅 및 모니터링 실패) | 로그인 시도, 접근 제어 실패, 입력 검증 실패 등의 이벤트가 로깅되지 않거나 모니터링되지 않아 침해 사고 탐지 지연 |
| **A10** | **Server-Side Request Forgery (SSRF)** (서버 측 요청 위조) | 서버가 사용자 제공 URL로 요청을 보내도록 하여 내부 네트워크 스캔, 클라우드 메타데이터 접근, 내부 서비스 공격 등 수행 |

> **WAF와 OWASP Top 10의 관계**: WAF는 A01(접근 제어 우회 시도 탐지), A03(Injection 패턴 차단), A05(정보 노출 차단), A07(무차별 대입 차단) 등에 직접적으로 대응하며, 나머지 항목에 대해서도 보조적 방어 역할을 수행한다.

## 5. WAF 탐지 방식

### 5.1 Negative Security Model (차단 목록 기반 / Blacklist)

- **원리**: 알려진 공격 패턴(시그니처)을 데이터베이스에 등록하고, 해당 패턴과 일치하는 요청을 차단
- **탐지 대상 예시**: `' OR 1=1--`, `<script>alert(`, `../../../etc/passwd`, `UNION SELECT` 등
- **장점**
  - 구축이 비교적 간단하고 빠르게 적용 가능
  - 알려진 공격에 대해 즉시 방어 가능
  - 정상 트래픽에 대한 오탐(False Positive)이 상대적으로 적음
- **단점**
  - 알려지지 않은 공격(Zero-Day)에 취약
  - 시그니처 DB를 지속적으로 업데이트해야 함
  - 인코딩, 난독화를 통한 우회 가능성 존재

### 5.2 Positive Security Model (허용 목록 기반 / Whitelist)

- **원리**: 정상적인 요청의 형태(허용된 URL, 파라미터 타입, 값 범위, HTTP 메서드 등)를 정의하고, 이에 부합하지 않는 모든 요청을 차단
- **장점**
  - Zero-Day 공격 포함 알려지지 않은 공격까지 차단 가능
  - 시그니처 업데이트 의존도가 낮음
  - 보다 근본적인 방어 가능
- **단점**
  - 초기 구축에 많은 시간과 노력 필요 (정상 트래픽 학습 기간 필요)
  - 웹 애플리케이션 변경 시마다 정책 재설정 필요
  - 정상 요청을 차단하는 오탐(False Positive) 발생 가능성이 높음

### 5.3 실무에서의 적용

- 대부분의 상용 WAF는 **Negative + Positive 혼합 모델**을 사용
- 초기에는 Negative Model로 알려진 공격을 차단하면서, 학습 기간(Learning Mode)을 통해 Positive Model 정책을 자동 생성
- 최근에는 **머신러닝 기반 행위 분석**을 결합하여 비정상 요청을 탐지하는 방식도 확산

## 6. 주요 기능

### 6.1 탐지 로그

- 정의한 탐지 룰에 따라 탐지된 이벤트 목록 제공
- 제공 정보: 탐지 룰, 위험 행동 대상의 주소·국가, 대상 URL, 발생 시각
- **Raw Data 상세보기**: 탐지 이벤트에서 우클릭 → 상세보기 → Raw data 확인 후 Decoding
- 정탐/오탐 유무 판단 → 대응

### 6.2 감사 로그

- 운영 관련 감사 정보를 목록 형태로 제공
- 데이터 종류: 로그인 관련 / 설정 변경 / 시스템 / 데이터 / 네트워크 인터페이스

### 6.3 정책 설정

- 탐지 보안 정책 및 웹서버 정보 설정
- 정책 변경 시 **저장 버튼 클릭** 필수 (취소 클릭 시 저장 안 됨)
- 신규 웹서버 추가: 설정 마법사 → 네트워크 설정 → 웹서버 IP/Port/Mode 설정
- **SSL 기능**: 웹서버 설정에서 SSL 항목 선택 시 인증서(cert) + 키(key) 파일 등록 필요
- **Proxy IP 설정**: Proxy 모드 시 필요. Inline 모드 시 불필요

## 7. WAF 동작 모드 (배치 구성)

### 7.1 기본 동작 모드

| 모드 | 설명 |
|------|------|
| **Inline 모드** | 웹방화벽이 직접 트래픽을 처리. 차단 가능 |
| **Proxy 모드** | 웹방화벽이 프록시 역할. Proxy IP 별도 설정 필요 |

### 7.2 배치 구성 상세

#### Reverse Proxy 모드

```
[클라이언트] → [WAF (Reverse Proxy)] → [웹서버]
              ↑ 클라이언트는 WAF의 IP로 접속
              ↑ WAF가 요청을 검사 후 웹서버로 전달
```

- **구성**: WAF가 웹서버 앞에서 클라이언트의 요청을 대신 수신하고, 검사 후 정상 요청만 웹서버로 전달
- **장점**
  - 웹서버의 실제 IP 주소를 외부에 노출하지 않아 보안 강화
  - SSL 종단(SSL Offloading) 처리 가능 → 웹서버 부하 감소
  - 로드 밸런싱, 캐싱 등 부가 기능 제공 가능
  - 가장 많이 사용되는 배치 방식
- **단점**
  - 네트워크 구성 변경 필요 (DNS 또는 IP 변경)
  - WAF 자체가 단일 장애점(SPOF)이 될 수 있음 → HA(이중화) 구성 필요
  - 약간의 지연(Latency) 발생

#### Transparent Proxy 모드

```
[클라이언트] → [WAF (Transparent)] → [웹서버]
              ↑ 기존 네트워크 구성 변경 없음
              ↑ L2 레벨에서 투명하게 동작
```

- **구성**: WAF가 네트워크 경로 상에 투명하게 위치하여 트래픽을 가로채 검사. 클라이언트와 서버 모두 WAF의 존재를 인식하지 못함
- **장점**
  - 기존 네트워크 구성(IP, DNS)을 변경할 필요 없음
  - 도입이 간편하고 빠름
- **단점**
  - SSL 복호화가 어려울 수 있음
  - Reverse Proxy 대비 부가 기능(캐싱, 로드밸런싱) 제한적

#### Bridge(인라인) 모드

```
[클라이언트] → [WAF (Bridge/Inline)] → [웹서버]
              ↑ L2 브릿지로 동작
              ↑ 모든 트래픽이 WAF를 물리적으로 통과
```

- **구성**: WAF가 L2 브릿지(스위치)처럼 동작하여 네트워크 경로에 물리적으로 삽입
- **장점**
  - 네트워크 구성 변경 최소화
  - IP 주소 할당 불필요
  - 모든 트래픽을 물리적으로 검사 가능
- **단점**
  - WAF 장애 시 네트워크 전체 단절 위험 (Fail-Open/Fail-Close 설정 필요)
  - 대용량 트래픽 처리 시 병목 가능

#### 모드별 비교 요약

| 항목 | Reverse Proxy | Transparent Proxy | Bridge(인라인) |
|------|--------------|-------------------|---------------|
| 네트워크 변경 | 필요 (DNS/IP) | 불필요 | 최소 |
| SSL 처리 | 용이 (SSL Offloading) | 제한적 | 제한적 |
| 웹서버 IP 은닉 | 가능 | 불가 | 불가 |
| 부가 기능 | 풍부 | 제한적 | 제한적 |
| 도입 난이도 | 중간 | 낮음 | 낮음 |
| 장애 영향 | HA로 대응 | 우회 가능 | 네트워크 단절 위험 |

## 9. WAF 우회 기법과 대응

> **학습 목적**: 공격자의 우회 기법을 이해해야 WAF 정책을 정확하게 설정하고, 탐지 룰의 사각지대를 줄일 수 있다. 방어자 관점에서 반드시 알아야 하는 내용이다.

### 9.1 인코딩 우회

| 기법 | 예시 | 설명 |
|------|------|------|
| **URL Encoding** | `%27%20OR%201%3D1--` | 특수문자를 %XX 형식으로 인코딩하여 시그니처 우회 |
| **Double Encoding** | `%2527` → `%27` → `'` | URL 인코딩을 2중으로 적용. WAF가 1회만 디코딩할 경우 우회 성공 |
| **Unicode Encoding** | `%u0027` (= `'`) | 유니코드 표현을 이용한 우회. IIS 환경에서 특히 유효 |
| **HTML Entity** | `&#39;` 또는 `&#x27;` | HTML 엔티티 인코딩으로 XSS 필터 우회 |
| **Base64 Encoding** | `PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==` | 페이로드를 Base64로 인코딩하여 전달 |

### 9.2 구문 변형 우회

| 기법 | 예시 | 설명 |
|------|------|------|
| **대소문자 혼합** | `SeLeCt`, `UnIoN` | WAF가 대소문자 구분 매칭 시 우회 가능 |
| **주석 삽입** | `UN/**/ION SEL/**/ECT` | SQL 주석(`/**/`)을 키워드 사이에 삽입하여 패턴 매칭 회피 |
| **공백 대체** | `UNION%09SELECT`, `UNION%0aSELECT` | 공백 대신 탭(%09), 줄바꿈(%0a) 등 사용 |
| **동의어 치환** | `CONCAT()` 대신 `CONCAT_WS()` | 동일 기능의 다른 함수·구문 사용 |
| **문자열 분할** | `CHAR(83)+CHAR(69)+CHAR(76)+CHAR(69)+CHAR(67)+CHAR(84)` | 문자열을 문자 코드로 분할하여 조합 |

### 9.3 HTTP 프로토콜 악용

| 기법 | 설명 |
|------|------|
| **HTTP Parameter Pollution (HPP)** | 동일 파라미터를 여러 번 전달하여 WAF와 웹서버가 다른 값을 처리하도록 유도 |
| **Content-Type 변조** | `multipart/form-data` 등 다른 Content-Type으로 전환하여 WAF 파서 우회 |
| **Chunked Transfer Encoding** | 요청 본문을 청크로 분할하여 전송, WAF의 재조합 실패 유도 |
| **HTTP Method 변경** | GET → POST 또는 PUT 등으로 변경하여 특정 메서드만 검사하는 WAF 우회 |

### 9.4 대응 방안

- 다중 디코딩(Recursive Decoding) 적용: 입력값을 여러 차례 디코딩한 후 검사
- 대소문자 무시(Case-Insensitive) 패턴 매칭 적용
- 정규화(Normalization) 처리 후 검사 수행
- 모든 HTTP 메서드에 대해 검사 수행
- Content-Type에 관계없이 요청 본문 검사
- Positive Security Model을 병행하여 허용된 형식 외의 요청 차단

## 10. WAF 로그 분석 실무

### 10.1 SQL Injection 탐지

**탐지 키워드 및 패턴**:
```
' OR 1=1--
" OR ""="
UNION SELECT
UNION ALL SELECT
ORDER BY [숫자]--
'; DROP TABLE
1' AND '1'='1
SLEEP(5)
BENCHMARK(10000000, SHA1('test'))
```

**로그 분석 포인트**:
- 요청 URL 또는 POST 파라미터에 SQL 예약어(`SELECT`, `UNION`, `INSERT`, `UPDATE`, `DELETE`, `DROP`) 포함 여부
- 싱글 쿼트(`'`), 더블 대시(`--`), 세미콜론(`;`) 등 SQL 특수문자의 비정상적 사용
- 동일 출발지 IP에서 파라미터 값을 점진적으로 변경하며 반복 요청 (자동화 도구 사용 징후)
- 응답 코드가 200이면서 응답 크기가 비정상적으로 크거나 변동이 큰 경우 → 데이터 추출 가능성

### 10.2 XSS (Cross-Site Scripting) 탐지

**탐지 키워드 및 패턴**:
```
<script>alert(
<img src=x onerror=
<svg onload=
javascript:alert(
<iframe src="javascript:
document.cookie
document.location
eval(
String.fromCharCode(
```

**로그 분석 포인트**:
- 파라미터에 HTML 태그(`<script>`, `<img>`, `<svg>`, `<iframe>`)가 포함된 요청
- 이벤트 핸들러 속성(`onerror`, `onload`, `onclick`, `onmouseover`) 사용
- `javascript:` 프로토콜 핸들러 사용
- 인코딩된 형태의 XSS 페이로드 (HTML Entity, URL Encoding, Unicode)

### 10.3 Directory Traversal 탐지

**탐지 키워드 및 패턴**:
```
../../etc/passwd
..%2f..%2f
....//....//
..%252f..%252f
/etc/shadow
/windows/system32/
cmd.exe
/proc/self/environ
```

**로그 분석 포인트**:
- URL 경로에 `../` 또는 인코딩 변형(`..%2f`, `..%5c`, `%2e%2e/`)이 반복적으로 포함
- 시스템 파일 경로(`/etc/passwd`, `/etc/shadow`, `win.ini`, `boot.ini`) 접근 시도
- 파일 다운로드 기능의 파라미터에서 경로 조작 시도

### 10.4 정탐/오탐 판별 기준

| 구분 | 정탐 (True Positive) | 오탐 (False Positive) |
|------|---------------------|----------------------|
| **정의** | 실제 공격을 공격으로 정확히 탐지 | 정상 요청을 공격으로 잘못 탐지 |
| **판별 기준** | 요청의 의도가 명확히 악의적 (자동화 도구 사용, 반복 시도, 알려진 공격 패턴) | 업무 상 정상적으로 사용될 수 있는 문자열이 탐지된 경우 |
| **예시 - 정탐** | 파라미터에 `' UNION SELECT username, password FROM users--` 포함 | - |
| **예시 - 오탐** | - | 게시판 글 내용에 "SELECT 버튼을 클릭하세요"가 포함되어 SQL Injection으로 탐지 |
| **대응** | 출발지 IP 차단, 보안 담당자 보고, 웹서버 피해 여부 확인 | 해당 URL/파라미터에 대한 예외 정책(화이트리스트) 등록 |

**오탐 판별 체크리스트**:
1. 해당 요청이 실제 서비스의 정상 기능에서 발생한 것인가?
2. 요청 파라미터의 값이 사용자가 일반적으로 입력할 수 있는 내용인가?
3. 동일 패턴의 요청이 다수의 정상 사용자에게서도 발생하는가?
4. 해당 공격이 성공했을 경우 서버 응답에 변화가 있었는가?
5. 출발지 IP의 다른 요청 패턴은 정상적인가?

## 11. WAF vs 방화벽 비교

| 항목 | 방화벽 | WAF |
|------|--------|-----|
| 분석 계층 | L3/L4 (IP, Port) | L7 (HTTP 헤더, 본문, URL, 파라미터) |
| 차단 기준 | IP·포트 기반 ACL | 웹 공격 패턴 (SQL Injection, XSS 등) |
| HTTP 80/443 | 열어두어야 함 | 해당 포트 내 악성 요청 탐지·차단 |

## 12. WAF와 다른 보안장비의 역할 분담

### 12.1 다계층 방어 (Defense in Depth) 구조

```
[인터넷]
    │
    ▼
┌──────────────────────────────────────────────┐
│  방화벽 (Firewall)                            │
│  - L3/L4 계층 방어                            │
│  - IP/Port 기반 접근 제어 (ACL)               │
│  - 불필요한 포트 차단                          │
│  - 네트워크 세그멘테이션                       │
│  - 차단 대상: 비인가 IP, 불필요 포트 접근      │
└──────────────────────────────────────────────┘
    │  (허용된 IP·포트의 트래픽만 통과)
    ▼
┌──────────────────────────────────────────────┐
│  IPS/IDS (침입방지/탐지시스템)                 │
│  - L3~L7 시그니처 기반 탐지                   │
│  - 네트워크 레벨 공격 차단                     │
│  - 포트 스캔, DDoS, 웜·바이러스 탐지           │
│  - 알려진 취약점 익스플로잇 차단               │
│  - 차단 대상: 네트워크 공격, 악성코드 전파      │
└──────────────────────────────────────────────┘
    │  (네트워크 레벨 공격이 제거된 트래픽)
    ▼
┌──────────────────────────────────────────────┐
│  WAF (웹방화벽)                               │
│  - L7 (HTTP/HTTPS) 전문 분석                  │
│  - 웹 애플리케이션 공격 차단                   │
│  - SQL Injection, XSS, CSRF 등               │
│  - 쿠키·세션 보호, 파라미터 검증               │
│  - SSL 복호화 후 검사                         │
│  - 차단 대상: 웹 애플리케이션 계층 공격         │
└──────────────────────────────────────────────┘
    │  (검증된 정상 웹 요청만 통과)
    ▼
┌──────────────────────────────────────────────┐
│  웹서버 / WAS                                 │
└──────────────────────────────────────────────┘
```

### 12.2 각 장비별 역할 비교

| 구분 | 방화벽 | IPS/IDS | WAF |
|------|--------|---------|-----|
| **동작 계층** | L3/L4 | L3~L7 | L7 (HTTP/HTTPS) |
| **주요 기능** | IP·포트 접근 제어 | 시그니처 기반 침입 탐지·차단 | 웹 공격 패턴 분석·차단 |
| **차단 대상** | 비인가 네트워크 접근 | 네트워크 공격, 웜, 취약점 공격 | SQL Injection, XSS, 파일 업로드 공격 등 |
| **HTTP 이해도** | 없음 (포트만 인식) | 제한적 (패턴 매칭) | 심층 분석 (헤더, 본문, 쿠키, 세션) |
| **SSL 트래픽** | 검사 불가 | 검사 어려움 | 복호화 후 검사 가능 |
| **오탐 관리** | 단순 (IP/Port 기반) | 시그니처 튜닝 필요 | 웹 애플리케이션별 세밀한 예외 정책 필요 |

### 12.3 왜 다계층 방어가 필요한가

- **단일 장비로는 모든 공격을 차단할 수 없음**: 각 장비는 특정 계층·유형의 공격에 특화
- **방화벽만 있는 경우**: 80/443 포트를 통한 웹 공격은 그대로 통과
- **IPS만 있는 경우**: HTTP 프로토콜 심층 분석 부족, 인코딩·난독화된 웹 공격 탐지 어려움
- **WAF만 있는 경우**: 비인가 포트 접근, 네트워크 레벨 DDoS 등은 방어 불가
- **결론**: 방화벽(네트워크 접근 제어) → IPS(알려진 공격 차단) → WAF(웹 공격 전문 차단)의 **계층별 방어**가 필수

## 13. 정리

| 핵심 항목 | 내용 |
|-----------|------|
| WAF 정의 | 웹서버 앞단에서 HTTP/HTTPS 트래픽을 분석하여 웹 공격을 차단하는 보안 시스템 |
| 등장 배경 | 방화벽/IPS의 한계 (80/443 포트 개방 필수), 웹 취약점의 특수성 |
| 탐지 방식 | Negative Model(차단 목록) + Positive Model(허용 목록) 혼합 사용 |
| 배치 구성 | Reverse Proxy(가장 보편적), Transparent Proxy, Bridge 모드 |
| 대응 위협 | OWASP Top 10 기반: Injection, XSS, 접근 제어 우회, SSRF 등 |
| 실무 핵심 | 로그 분석(정탐/오탐 판별), 정책 튜닝, 우회 기법 이해 |
| 다계층 방어 | 방화벽(L3/L4) → IPS(L3~L7) → WAF(L7) 순서로 계층적 방어 구성 |
