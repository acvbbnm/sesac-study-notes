# 03. 방화벽의 이해

---

## 1. 방화벽 정의

**Firewall**은 외부로부터 내부망을 보호하기 위한 네트워크 구성요소로, 외부의 불법침입으로부터 내부 정보자산을 보호하고 유해정보 유입을 차단하기 위한 **정책 + 하드웨어 + 소프트웨어**의 총칭.

- **효과**: 네트워크 출입로를 단일화하여 보안관리 범위를 좁히고 접근제어를 효과적으로 수행
- **원리**: 관리자가 사전 설정한 보안 규칙(ACL)에 따라 패킷을 허용 또는 차단
- **위치**: 내부 네트워크와 외부 네트워크(인터넷) 중간

```
인터넷 → [방화벽(접근제어 목록)] → 내부 네트워크
              ↑ 접근 허용 / 접근 차단
```

## 2. 방화벽의 역사와 발전

방화벽 기술은 네트워크 위협의 진화에 맞춰 세대별로 발전해 왔다.

### 2.1 1세대: 패킷 필터링 방화벽 (Packet Filtering Firewall)

- **등장 시기**: 1980년대 후반
- **동작 계층**: OSI Layer 3~4 (네트워크/전송 계층)
- **원리**: 각 패킷의 헤더 정보(출발지 IP, 목적지 IP, 포트, 프로토콜)만 확인하여 허용/차단 판단
- **특징**:
  - 개별 패킷을 독립적으로 검사 (이전 패킷과의 연관관계 무시)
  - 처리 속도가 매우 빠름
  - ACL(Access Control List) 기반으로 단순 규칙 적용
- **한계**:
  - 패킷 간의 연관성(세션)을 추적하지 못함
  - IP Spoofing, 패킷 분할 공격에 취약
  - 애플리케이션 데이터(페이로드) 검사 불가
- **대표 장비**: 초기 라우터의 ACL 기능 (Cisco 라우터 ACL)

### 2.2 2세대: 상태기반 방화벽 (Stateful Inspection Firewall)

- **등장 시기**: 1990년대 초반 (Check Point Software의 FireWall-1이 대표적)
- **동작 계층**: OSI Layer 3~4 + 세션 상태 추적
- **원리**: **세션 테이블(State Table)**을 유지하여 패킷이 기존 연결의 일부인지 판단
- **특징**:
  - TCP 3-way handshake를 추적하여 정상 연결 여부 확인
  - 연결 상태(NEW, ESTABLISHED, RELATED, INVALID)에 따라 필터링
  - 응답 패킷은 별도 정책 없이 세션 테이블 기반으로 자동 허용
- **장점**: 패킷 필터링보다 보안성이 높고, 별도 응답 정책 불필요
- **한계**: 여전히 페이로드(애플리케이션 데이터) 검사 불가

### 2.3 3세대: 애플리케이션 게이트웨이 (Application Gateway / Proxy Firewall)

- **등장 시기**: 1990년대 중반
- **동작 계층**: OSI Layer 7 (애플리케이션 계층)
- **원리**: 클라이언트와 서버 사이에서 프록시 역할을 수행, 애플리케이션 프로토콜(HTTP, FTP, SMTP 등)을 이해하고 검사
- **특징**:
  - 내부 네트워크 주소를 완전히 은닉
  - 각 애플리케이션별 전용 프록시 데몬 필요
  - 콘텐츠 레벨의 필터링 가능 (URL 필터링, 악성코드 검사)
- **한계**:
  - 처리 속도 저하 (모든 트래픽을 프록시가 중계)
  - 새로운 프로토콜 지원 시 별도 프록시 개발 필요
  - 대용량 트래픽 처리에 부적합

### 2.4 차세대 방화벽 (NGFW: Next Generation Firewall)

- **등장 시기**: 2000년대 후반 (Gartner가 2009년 NGFW 개념 정의)
- **동작 계층**: OSI Layer 3~7 전 구간
- **핵심 기능**:
  - 기존 Stateful 방화벽 기능 포함
  - DPI(Deep Packet Inspection): 패킷 페이로드까지 심층 검사
  - 애플리케이션 인식 및 제어 (포트가 아닌 애플리케이션 자체를 식별)
  - 사용자/그룹 기반 정책 적용 (AD/LDAP 연동)
  - IPS(침입방지) 기능 통합
  - SSL/TLS 복호화 검사

```
[세대별 발전 요약]

1세대 패킷 필터링  →  개별 패킷 헤더만 검사 (L3~L4)
        ↓
2세대 Stateful     →  세션 상태 추적 + 패킷 헤더 검사
        ↓
3세대 App Gateway  →  애플리케이션 프로토콜 이해 + 프록시
        ↓
NGFW               →  DPI + 앱 인식 + 사용자 기반 + IPS 통합
```

## 3. Stateless vs Stateful 방화벽

### 3.1 Stateless 방화벽 (패킷 필터링)

- 각 패킷을 **개별적으로 독립 판단** (이전/이후 패킷과의 관계 무시)
- ACL 규칙에 따라 허용/차단만 수행
- **요청 패킷과 응답 패킷을 각각 별도 정책으로 설정**해야 함

```
[Stateless 방화벽 정책 예시]
정책1: 내부 → 외부 TCP 80 허용     (요청)
정책2: 외부 → 내부 TCP 80 허용     (응답) ← 별도 정책 필요!
```

- 문제점: 응답 정책을 열어두면, 공격자가 해당 포트로 내부에 직접 접근 가능

### 3.2 Stateful 방화벽 (상태기반 검사)

- **세션 테이블(Session Table / State Table)**을 유지하여 연결 상태를 추적
- 최초 요청(SYN)이 정책에 의해 허용되면 세션 테이블에 기록
- 이후 해당 세션에 속하는 패킷(응답 포함)은 세션 테이블을 조회하여 자동 허용
- **응답 패킷에 대한 별도 정책이 불필요**

```
[세션 테이블 구조 예시]
+----------+----------+--------+--------+----------+--------+---------+
| Src IP   | Dst IP   | Src Pt | Dst Pt | Protocol | State  | Timeout |
+----------+----------+--------+--------+----------+--------+---------+
| 10.1.1.5 | 8.8.8.8  | 52301  | 443    | TCP      | ESTAB  | 3600s   |
| 10.1.1.8 | 1.1.1.1  | 48210  | 80     | TCP      | SYN    | 30s     |
| 10.1.2.3 | 9.9.9.9  | 61002  | 53     | UDP      | NEW    | 60s     |
+----------+----------+--------+--------+----------+--------+---------+
```

### 3.3 핵심 차이 비교

| 항목 | Stateless | Stateful |
|------|-----------|----------|
| 세션 추적 | 불가 | 가능 (세션 테이블) |
| 응답 정책 | 별도 설정 필요 | 자동 허용 |
| 보안 수준 | 낮음 | 높음 |
| 처리 속도 | 빠름 (단순 비교) | 약간 느림 (테이블 조회) |
| TCP 핸드셰이크 검증 | 불가 | 가능 |
| 비정상 패킷 탐지 | 어려움 | 가능 (세션 상태 기반) |
| 정책 관리 | 복잡 (양방향 설정) | 간편 (단방향 설정) |

### 3.4 Stateful 방화벽이 중요한 이유

1. **보안 강화**: 정상적인 TCP 3-way handshake를 거치지 않은 비정상 패킷(ACK Flood, RST 공격 등)을 세션 테이블에 없으므로 자동 차단
2. **정책 간소화**: 요청 정책만 설정하면 응답은 자동 처리되므로 관리 부담 감소, 설정 오류 위험 감소
3. **가시성 확보**: 현재 활성 세션 목록을 통해 네트워크 연결 현황을 실시간 파악 가능
4. **UDP/ICMP 처리**: 비연결형 프로토콜도 가상 세션을 생성하여 타임아웃 기반으로 상태 관리 가능

## 4. 차세대 방화벽 (NGFW) 상세

### 4.1 기존 방화벽과의 차이

| 항목 | 전통적 방화벽 | NGFW |
|------|-------------|------|
| 검사 기준 | IP, Port, Protocol | IP, Port, Protocol + 앱 + 사용자 + 콘텐츠 |
| 패킷 검사 | 헤더만 검사 | 헤더 + 페이로드(DPI) |
| 애플리케이션 식별 | 포트 기반 추정 | 앱 시그니처 기반 정확한 식별 |
| 사용자 식별 | IP 기반 | AD/LDAP 연동 사용자/그룹 식별 |
| IPS | 별도 장비 | 통합 내장 |
| SSL 검사 | 불가 | SSL 복호화 후 검사 가능 |
| 위협 인텔리전스 | 없음 | 클라우드 기반 실시간 위협 DB 연동 |

### 4.2 DPI (Deep Packet Inspection)

DPI는 패킷의 헤더뿐만 아니라 **페이로드(실제 데이터)까지 검사**하는 기술이다.

```
[일반 패킷 검사 vs DPI 비교]

일반 검사:  [IP헤더][TCP헤더] ← 여기까지만 검사 | [페이로드] ← 무시
DPI:        [IP헤더][TCP헤더][페이로드] ← 전체 검사 (악성코드, 앱 식별)
```

- **동작 원리**:
  - 패킷의 데이터 영역을 시그니처 DB와 대조
  - 알려진 악성코드, 취약점 공격 패턴, 특정 애플리케이션 프로토콜 식별
  - 정규표현식 기반 패턴 매칭 수행
- **활용**:
  - 포트를 우회하는 애플리케이션 탐지 (예: 포트 443으로 동작하는 P2P)
  - 악성코드가 포함된 파일 전송 차단
  - 데이터 유출 방지(DLP) 기능 구현

### 4.3 애플리케이션 인식 (Application Awareness)

전통 방화벽은 포트 번호로 서비스를 구분하지만, 현대 애플리케이션은 동일 포트를 공유한다.

```
[포트 443(HTTPS)을 사용하는 애플리케이션들]
- 일반 웹 브라우징
- YouTube 스트리밍
- Google Drive 파일 업로드
- Slack 메신저
- Zoom 화상회의
- 악성코드 C2 통신

→ 전통 방화벽: 포트 443이므로 모두 허용 또는 모두 차단
→ NGFW: 각 애플리케이션을 개별 식별하여 선택적 제어 가능
```

- **App-ID (Palo Alto)**, **Application Control (Fortinet)** 등의 기능명으로 제공
- 수천 개의 애플리케이션 시그니처를 내장하고 지속 업데이트

### 4.4 사용자 기반 정책 (User-ID)

- AD(Active Directory), LDAP, RADIUS 등과 연동하여 IP가 아닌 **사용자 계정** 기반으로 정책 적용
- 동일 IP라도 로그인한 사용자에 따라 다른 정책 적용 가능
- DHCP 환경에서 IP가 변경되어도 사용자 기반 정책은 유지됨

```
[사용자 기반 정책 예시]
- "영업부" 그룹 → Salesforce 허용, YouTube 차단
- "개발팀" 그룹 → GitHub 허용, SNS 차단
- "임원" 그룹   → 전체 허용
- "게스트"      → 인터넷만 허용, 내부 자원 접근 차단
```

## 5. UTM (Unified Threat Management)

### 5.1 개념

**UTM(통합위협관리)**은 방화벽, IPS, VPN, 안티바이러스, 안티스팸, URL 필터링, 콘텐츠 필터링 등 **다수의 보안 기능을 하나의 장비에 통합**한 보안 솔루션이다.

```
[UTM 통합 기능]
+--------------------------------------------------+
|                    UTM 장비                       |
|                                                  |
|  방화벽 | IPS | VPN | 안티바이러스 | 웹필터링    |
|  안티스팸 | DLP | 애플리케이션 제어              |
+--------------------------------------------------+
```

### 5.2 UTM vs NGFW 비교

| 항목 | UTM | NGFW |
|------|-----|------|
| 주요 타깃 | 중소기업 (SMB) | 중대형 기업 / 데이터센터 |
| 설계 철학 | 다수 보안 기능의 단순 통합 | 방화벽 중심으로 고급 기능 심층 통합 |
| 성능 | 기능 활성화 시 성능 저하 큼 | 기능 활성화에도 고성능 유지 |
| 관리 편의성 | 단일 콘솔로 모든 기능 관리 | 단일 콘솔 + 정교한 정책 수립 가능 |
| 트래픽 처리 | 소규모 트래픽에 적합 | 대용량 트래픽 처리 가능 |
| 가격 | 상대적으로 저렴 | 상대적으로 고가 |
| 안티바이러스/스팸 | 기본 포함 | 선택적 구독 |

> **요약**: UTM은 "보안 기능의 물리적 통합"에 초점, NGFW는 "방화벽 기능의 질적 진화"에 초점. 최근에는 두 개념의 경계가 흐려지는 추세이다.

## 6. 방화벽 보안정책 4종

| 정책 | 방향 | 설명 |
|------|------|------|
| **Paranoid** | All Block | 모든 트래픽 차단 |
| **Prudent** | Any Open + Drop | 특정 트래픽 허용, 나머지 Drop |
| **Cautious** | Any Block + Allow | 특정 트래픽 차단, 나머지 Allow |
| **Promiscuous** | All Open | 모든 트래픽 허용 |

> 실무에서는 기본 정책을 **Any Drop** (Deny All)으로 설정하고, 필요한 트래픽만 허용하는 **Whitelist** 방식이 일반적.

## 7. ACL(Access Control List) 작성 실무

### 7.1 5-Tuple 기반 정책 구성

방화벽 정책은 기본적으로 **5-Tuple** 정보를 기반으로 작성한다.

| 요소 | 설명 | 예시 |
|------|------|------|
| **출발지 IP (Source IP)** | 트래픽을 보내는 호스트/네트워크 | 10.10.1.0/24 |
| **목적지 IP (Destination IP)** | 트래픽을 받는 호스트/네트워크 | 192.168.100.10 |
| **출발지 Port (Source Port)** | 보내는 측의 포트 번호 | Any (임시 포트) |
| **목적지 Port (Destination Port)** | 서비스 포트 번호 | 443 (HTTPS) |
| **프로토콜 (Protocol)** | 사용 프로토콜 | TCP, UDP, ICMP |

추가로 **Zone(영역)**, **Action(허용/차단)**, **로깅 여부**, **스케줄** 등을 함께 설정한다.

### 7.2 정책 작성 시 고려사항

- **최소 권한 원칙 (Least Privilege)**: 꼭 필요한 트래픽만 허용
- **출발지/목적지를 최대한 구체적으로 지정** (Any 사용 최소화)
- **서비스 포트도 구체적으로 지정** (Any Port 지양)
- **정책에 반드시 설명(Description) 기입**: 누가 왜 요청했는지 기록
- **만료일(Expiration) 설정**: 임시 정책은 만료일 명시

### 7.3 실제 정책 예시

```
+-----+-------------+-----------------+--------+---------+------+--------+--------+----------------------------+
| No  | Src Zone    | Src IP          | Dst IP          | Dst Pt| Proto  | Action | Log    | 설명                       |
+-----+-------------+-----------------+-----------------+-------+--------+--------+--------+----------------------------+
| 1   | Untrust     | Any             | 192.168.1.10    | 443   | TCP    | Allow  | Yes    | 외부→웹서버 HTTPS 허용     |
| 2   | Untrust     | Any             | 192.168.1.11    | 25    | TCP    | Allow  | Yes    | 외부→메일서버 SMTP 허용    |
| 3   | Trust       | 10.10.1.0/24    | Any             | 80    | TCP    | Allow  | Yes    | 내부→외부 HTTP 허용        |
| 4   | Trust       | 10.10.1.0/24    | Any             | 443   | TCP    | Allow  | Yes    | 내부→외부 HTTPS 허용       |
| 5   | Trust       | 10.10.1.0/24    | 8.8.8.8         | 53    | UDP    | Allow  | Yes    | 내부→DNS 조회 허용         |
| 6   | DMZ         | 192.168.1.10    | 10.10.2.100     | 3306  | TCP    | Allow  | Yes    | 웹서버→DB서버 MySQL 허용   |
| 100 | Any         | Any             | Any             | Any   | Any    | Deny   | Yes    | 기본 차단 (Default Deny)   |
+-----+-------------+-----------------+-----------------+-------+--------+--------+--------+----------------------------+
```

## 8. 방화벽 정책 최적화

### 8.1 정책 히트 카운트(Hit Count) 분석

- 각 정책에 매칭된 트래픽 횟수를 **히트 카운트**로 기록
- 히트 카운트가 0인 정책 → 사용되지 않는 정책으로, 삭제 검토 대상
- 히트 카운트가 높은 정책 → 상위에 배치하여 검사 성능 향상

```
[히트 카운트 분석 예시]
정책 #1:  Hit Count = 1,250,000  → 최상위 유지
정책 #2:  Hit Count = 850,000    → 상위 유지
정책 #15: Hit Count = 0          → 6개월간 미사용, 삭제 검토
정책 #22: Hit Count = 3          → 임시 정책 여부 확인
```

### 8.2 쉐도우 룰 (Shadow Rule)

**쉐도우 룰**은 상위 정책에 의해 가려져서 절대 매칭되지 않는 하위 정책이다.

```
[쉐도우 룰 예시]
정책 #5:  Src=Any, Dst=10.10.1.0/24, Port=Any, Action=Deny   ← 이 정책이
정책 #12: Src=Any, Dst=10.10.1.50,   Port=80,  Action=Allow  ← 이 정책을 가림

→ 정책 #12는 영원히 매칭되지 않음 (정책 #5가 먼저 매칭되므로)
→ 해결: 정책 #12를 정책 #5보다 상위로 이동
```

### 8.3 중복 룰 (Redundant Rule)

동일한 조건의 정책이 여러 개 존재하는 경우. 관리 혼선을 초래하고 정책 수를 불필요하게 증가시킨다.

### 8.4 Any-Any 룰의 위험성

```
[위험한 정책 예시]
Src=Any, Dst=Any, Port=Any, Protocol=Any, Action=Allow
```

- **모든 트래픽을 무조건 허용**하므로 방화벽의 존재 의미가 사라짐
- 초기 구축 시 테스트 목적으로 생성 후 제거하지 않는 경우가 많음
- 보안감사에서 가장 먼저 지적되는 항목
- Any-Any 룰 하위의 모든 Deny 정책이 무효화됨

### 8.5 정책 최적화 절차

1. 전체 정책 히트 카운트 수집
2. 미사용 정책(Hit=0) 식별 및 담당자 확인
3. 쉐도우/중복 룰 탐지 및 정리
4. Any-Any 허용 정책 제거
5. 정책 순서 최적화 (히트 카운트 높은 정책 상위 배치)
6. 임시 정책의 만료일 확인 및 정리
7. 변경 내역 문서화 및 승인

## 9. 방화벽 NAT

**NAT (Network Address Translation)**: 사설 IP를 공인 IP로 변환하는 주소 변환 서비스.

**필요성**
- 공인 IP 주소 절약 (IPv4 고갈 문제)
- 보안 강화: 내부 사설 IP를 외부에서 직접 접근 불가

```
내부PC (192.168.1.x) → [방화벽/NAT] → 외부서버
                        101.89.1.12 (공인IP)
```

### 9.1 NAT 종류 (Juniper 기준 4종)

| 종류 | 방향 | 동작방식 | 사용 시나리오 |
|------|------|---------|-------------|
| **PAT (N:1)** | 내→외 | 다수 사설IP → 공인IP 하나로 변환 | 일반적인 인터넷 접속 |
| **DIP (N:N)** | 내→외 | 특정 사설IP 대역 → 특정 공인IP 또는 대역 | IP 인증이 필요한 외부 서비스 접속 |
| **VIP (1:N)** | 외→내 | 공인IP 하나를 포트 번호에 따라 내부 서버로 분산 | 공인IP 1개, 내부 서버 2대 이상 |
| **MIP (1:1)** | 외→내 | 공인IP 하나 ↔ 내부 서버 1:1 매핑 | 다수의 공인IP 보유 시 각 서버에 1:1 할당 |

### 9.2 PAT / SNAT / DNAT 상세

#### SNAT (Source NAT) - 출발지 주소 변환

내부에서 외부로 나갈 때 **출발지 IP를 변환**한다.

```
[SNAT 패킷 변환 과정]

1) 내부 PC가 패킷 전송
   Src: 10.10.1.50:52100 → Dst: 203.0.113.80:443

2) 방화벽에서 SNAT 적용 (출발지 IP 변환)
   Src: 101.89.1.12:52100 → Dst: 203.0.113.80:443
       ↑ 공인IP로 변환

3) 외부 서버가 응답
   Src: 203.0.113.80:443 → Dst: 101.89.1.12:52100

4) 방화벽에서 역변환 (NAT 테이블 참조)
   Src: 203.0.113.80:443 → Dst: 10.10.1.50:52100
                                 ↑ 원래 사설IP로 복원
```

#### PAT (Port Address Translation) - 포트 기반 주소 변환

하나의 공인 IP를 **포트 번호로 구분**하여 다수의 내부 호스트가 공유한다.

```
[PAT 동작 원리]

내부 PC-A (10.10.1.50:52100) → 방화벽 → 101.89.1.12:40001 → 외부서버
내부 PC-B (10.10.1.51:48200) → 방화벽 → 101.89.1.12:40002 → 외부서버
내부 PC-C (10.10.1.52:55300) → 방화벽 → 101.89.1.12:40003 → 외부서버
                                        ↑ 동일 공인IP, 포트로 구분

[PAT 테이블]
+----------------+--------+----------------+--------+
| 내부 IP        | 내부 Pt| 변환 IP        | 변환 Pt|
+----------------+--------+----------------+--------+
| 10.10.1.50     | 52100  | 101.89.1.12    | 40001  |
| 10.10.1.51     | 48200  | 101.89.1.12    | 40002  |
| 10.10.1.52     | 55300  | 101.89.1.12    | 40003  |
+----------------+--------+----------------+--------+
```

#### DNAT (Destination NAT) - 목적지 주소 변환

외부에서 내부로 접근할 때 **목적지 IP를 변환**한다. 서버 공개(포트 포워딩)에 사용.

```
[DNAT 패킷 변환 과정 - 포트 매핑]

1) 외부 클라이언트가 공인IP로 접속
   Src: 203.0.113.50:61200 → Dst: 101.89.1.12:443

2) 방화벽에서 DNAT 적용 (목적지 IP를 내부 서버로 변환)
   Src: 203.0.113.50:61200 → Dst: 192.168.1.10:443
                                   ↑ 내부 웹서버로 전달

3) 내부 서버가 응답
   Src: 192.168.1.10:443 → Dst: 203.0.113.50:61200

4) 방화벽에서 역변환
   Src: 101.89.1.12:443 → Dst: 203.0.113.50:61200
        ↑ 공인IP로 복원하여 응답
```

```
[포트 매핑을 이용한 다중 서버 공개]

공인IP 101.89.1.12:80   → 내부 웹서버    192.168.1.10:80
공인IP 101.89.1.12:443  → 내부 웹서버    192.168.1.10:443
공인IP 101.89.1.12:25   → 내부 메일서버  192.168.1.11:25
공인IP 101.89.1.12:8080 → 내부 개발서버  192.168.1.12:80
```

## 10. 방화벽 운영 모드

| 모드 | OSI 계층 | 특징 |
|------|---------|------|
| **Transparent Mode (L2)** | Layer 2 | Route·Switch 사이에서 Bridge로 구성. 장비에 Manage IP만 할당. IP 재설계 불필요 |
| **NAT Mode (L3)** | Layer 3 | 내부 사설IP 사용. Outbound 트래픽은 공인IP로 Source IP 변환. Routing Table 필요 |
| **Route Mode (L3)** | Layer 3 | 방화벽 하단 네트워크도 공인IP 사용. NAT 불필요. Routing Table 필요 |

## 11. 방화벽 정책 설정 순서 (우선순위)

방화벽은 기본적으로 **상위에서 하위로** 정책이 적용됨.

```
1. Block IP (P2P, 메신저 등 차단)
2. 방화벽 접근 룰 (ADMIN 권한)
3. Client 인증 및 VPN 접근 룰
4. 대외용 서비스 룰
5. 외부 접근 룰 (서버 접근 권한)
6. 내부에서 외부로 나가는 룰
7. Any Drop (기본 차단)
```

**주의사항**
- 방화벽에 대한 ICMP는 기본적으로 차단
- 방화벽 접근은 관리자 Client만 허용

## 14. 방화벽 관리방안

방화벽은 네트워크 관문에서 오가는 패킷을 제어하므로 이상 발생 시 전체 피해 가능 → 효율적 관리 필수.

**정기 점검사항**
- 정기적인 룰 점검 (불필요한 룰 정리)
- 정기적인 로그 및 룰 백업
- 정기적인 로그 분석
- 방화벽 장애 시 대처방안 사전 준비 (Fail-Over 테스트)

## 15. 방화벽의 한계

방화벽을 우회하는 다양한 해킹 방법이 존재.

**한계점**
- VPN 등 일반적이지 않은 패킷 처리 한계
- 방화벽에서 허용한 경로(telnet, ftp 등)를 통한 취약점 공격 대응 어려움
- 물리적 보안, WWW, Mail을 이용한 해킹 대응 한계
- 허용된 포트(80, 443)를 통한 애플리케이션 레벨 공격은 방화벽으로 차단 불가

→ **IPS, WAF, IDS**와의 다층 방어(Defense in Depth) 필요
