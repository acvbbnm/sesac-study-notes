# 02. 네트워크의 이해

## 1. OSI 7계층

| 계층 | 이름 | 설명 | 보안장비 |
|------|------|------|---------|
| 7 | Application (응용) | 응용 프로세스가 네트워크에 연결할 수 있도록 인터페이스 제공 | IPS, WAF |
| 6 | Presentation (표현) | 데이터 표현 차이 해결, 형식 변환 | - |
| 5 | Session (세션) | 응용 계층 간 연결 설정·유지·종료 | - |
| 4 | Transport (전송) | 컴퓨터 간 연결 설정·유지·종료 | IDS, 방화벽(TCP/UDP 차단) |
| 3 | Network (네트워크) | 라우팅 프로토콜로 최적 경로 선택 및 자료 전송 | 방화벽(IP 차단) |
| 2 | Data Link (데이터링크) | 물리 전송 링크를 통해 자료를 안전하게 전송 | - |
| 1 | Physical (물리) | 물리 링크의 전기적·기계적 규약 정의 | - |

### 1-1. 각 계층 상세 설명

#### L7 - Application (응용 계층)
- **역할**: 사용자가 네트워크에 접근할 수 있는 인터페이스 제공 (웹 브라우저, 이메일 클라이언트 등)
- **주요 프로토콜**: HTTP, HTTPS, FTP, SMTP, POP3, IMAP, DNS, SNMP, Telnet, SSH
- **PDU**: 메시지(Message) 또는 데이터(Data)
- **보안관제 관점**: WAF가 이 계층에서 웹 공격(SQL Injection, XSS 등)을 탐지/차단

#### L6 - Presentation (표현 계층)
- **역할**: 데이터의 인코딩/디코딩, 암호화/복호화, 압축/해제
- **관련 기술**: SSL/TLS 암호화, JPEG/MPEG 인코딩, ASCII/EBCDIC 변환
- **PDU**: 데이터(Data)
- **보안관제 관점**: HTTPS 트래픽의 SSL/TLS 복호화가 이 계층에서 이루어짐. 암호화 트래픽을 복호화하지 않으면 보안장비가 내용을 분석할 수 없음

#### L5 - Session (세션 계층)
- **역할**: 통신 세션의 설정, 유지, 종료 관리. 동기화(Synchronization) 제공
- **관련 프로토콜**: NetBIOS, RPC(Remote Procedure Call), SQL
- **PDU**: 데이터(Data)
- **보안관제 관점**: 세션 하이재킹(Session Hijacking) 공격이 이 계층을 대상으로 함

#### L4 - Transport (전송 계층)
- **역할**: 종단 간(End-to-End) 신뢰성 있는 데이터 전송, 흐름 제어, 오류 제어
- **주요 프로토콜**:
  - **TCP** (Transmission Control Protocol): 연결 지향, 신뢰성 보장 (3-way handshake)
  - **UDP** (User Datagram Protocol): 비연결 지향, 빠른 전송 (실시간 스트리밍, DNS 등)
- **PDU**: **세그먼트(Segment)** (TCP) / **데이터그램(Datagram)** (UDP)
- **식별자**: **포트 번호** (Port Number)
- **보안관제 관점**: 방화벽이 TCP/UDP 포트 기반으로 트래픽 허용/차단. IDS가 이 계층의 이상 징후 탐지

#### L3 - Network (네트워크 계층)
- **역할**: 논리적 주소(IP) 지정, 라우팅을 통한 최적 경로 결정
- **주요 프로토콜**: IP, ICMP, ARP, RARP, OSPF, BGP, RIP
- **PDU**: **패킷(Packet)**
- **주요 장비**: 라우터(Router), L3 스위치
- **식별자**: **IP 주소**
- **보안관제 관점**: 방화벽이 출발지/목적지 IP 기반으로 접근 제어. IP 스푸핑 공격 탐지

#### L2 - Data Link (데이터링크 계층)
- **역할**: 물리적 주소(MAC) 지정, 프레임 단위 전송, 오류 검출(CRC)
- **주요 프로토콜**: Ethernet, PPP, HDLC, ARP(L2/L3 경계)
- **PDU**: **프레임(Frame)**
- **주요 장비**: 스위치(Switch), 브리지(Bridge)
- **식별자**: **MAC 주소** (48비트, 예: AA:BB:CC:DD:EE:FF)
- **보안관제 관점**: MAC 스푸핑, ARP 스푸핑 공격이 이 계층에서 발생

#### L1 - Physical (물리 계층)
- **역할**: 비트(0과 1) 단위의 전기적 신호 전송
- **관련 장비**: 허브, 리피터, 케이블(UTP, 광케이블), 커넥터
- **PDU**: **비트(Bit)**
- **보안관제 관점**: 물리적 도청(탭핑), 케이블 절단 등의 물리적 보안 위협

### 1-2. 캡슐화(Encapsulation)와 역캡슐화(De-encapsulation)

데이터가 송신 측에서 수신 측으로 전달될 때 각 계층을 거치며 헤더가 추가/제거되는 과정이다.

**송신 시 (캡슐화 - 위에서 아래로)**
```
[응용 계층]   데이터 생성
     ↓
[전송 계층]   TCP/UDP 헤더 추가  →  세그먼트(Segment)
     ↓
[네트워크 계층]  IP 헤더 추가      →  패킷(Packet)
     ↓
[데이터링크 계층] MAC 헤더 + 트레일러 추가  →  프레임(Frame)
     ↓
[물리 계층]   전기 신호로 변환    →  비트(Bit)
```

**수신 시 (역캡슐화 - 아래에서 위로)**
```
[물리 계층]   전기 신호 수신      →  비트(Bit)
     ↓
[데이터링크 계층] MAC 헤더 제거      →  패킷(Packet) 추출
     ↓
[네트워크 계층]  IP 헤더 제거       →  세그먼트(Segment) 추출
     ↓
[전송 계층]   TCP/UDP 헤더 제거  →  데이터(Data) 추출
     ↓
[응용 계층]   데이터 처리
```

> **보안관제에서의 의미**: 패킷 분석 도구(Wireshark 등)로 캡처한 패킷을 분석할 때, 각 계층의 헤더 정보를 읽어 출발지/목적지 IP, 포트, 프로토콜, 페이로드 내용 등을 확인한다. 이 과정을 이해해야 정확한 로그 분석이 가능하다.

### 1-3. OSI 7계층 vs TCP/IP 4계층 비교

OSI 모델은 **이론적 참조 모델**이고, TCP/IP 모델은 **실제 인터넷에서 사용되는 프로토콜 스택**이다.

| TCP/IP 4계층 | OSI 7계층 대응 | 주요 프로토콜 | PDU |
|-------------|---------------|-------------|-----|
| **응용 계층** (Application) | L7 응용 + L6 표현 + L5 세션 | HTTP, FTP, DNS, SMTP, SSH, SNMP | 메시지 |
| **전송 계층** (Transport) | L4 전송 | TCP, UDP | 세그먼트/데이터그램 |
| **인터넷 계층** (Internet) | L3 네트워크 | IP, ICMP, ARP, IGMP | 패킷 |
| **네트워크 접근 계층** (Network Access) | L2 데이터링크 + L1 물리 | Ethernet, Wi-Fi, PPP | 프레임/비트 |

**왜 두 가지 모델이 존재하는가?**

- **OSI 모델**: ISO(국제표준화기구)에서 1984년에 발표한 이론적 표준 모델. 네트워크 통신의 각 단계를 7개 계층으로 명확하게 분리하여 교육과 설계의 참조 프레임워크로 활용된다. 하지만 실제 프로토콜 구현과 정확히 일치하지 않는 경우가 많다.
- **TCP/IP 모델**: 실제 인터넷 프로토콜을 기반으로 만들어진 실용적 모델. 미국 국방부(DoD)의 ARPANET에서 시작되어 현재 인터넷의 표준이 되었다. OSI보다 단순한 4계층 구조이며, 실제 프로토콜 구현과 직접 대응된다.
- **보안관제 실무**에서는 두 모델을 혼용하여 사용한다. 방화벽 규칙 설명 시 "L3/L4 기반 필터링"이라고 하면 OSI 기준이고, 실제 패킷 분석 시에는 TCP/IP 스택 기준으로 헤더를 해석한다.

## 2. TCP 연결 관리

### 2-1. TCP 3-Way Handshake (연결 수립)

TCP는 데이터 전송 전 반드시 연결을 수립해야 하는 **연결 지향(Connection-Oriented)** 프로토콜이다.

```
클라이언트                          서버
    |                                |
    |  ① SYN (seq=100)              |
    | ─────────────────────────────→ |   클라이언트 → SYN_SENT 상태
    |                                |   서버 → SYN_RECEIVED 상태
    |  ② SYN+ACK (seq=200, ack=101) |
    | ←───────────────────────────── |
    |                                |
    |  ③ ACK (seq=101, ack=201)     |
    | ─────────────────────────────→ |   양쪽 → ESTABLISHED 상태
    |                                |
    |      ★ 데이터 전송 시작 ★       |
```

1. **SYN**: 클라이언트가 서버에 연결 요청 (시퀀스 번호 전달)
2. **SYN+ACK**: 서버가 요청 수락 + 자신의 시퀀스 번호 전달
3. **ACK**: 클라이언트가 수락 확인 → 연결 완료 (ESTABLISHED)

### 2-2. TCP 4-Way Teardown (연결 해제)

```
클라이언트                          서버
    |                                |
    |  ① FIN (연결 종료 요청)        |
    | ─────────────────────────────→ |   클라이언트 → FIN_WAIT_1
    |                                |
    |  ② ACK (종료 요청 수신 확인)    |
    | ←───────────────────────────── |   클라이언트 → FIN_WAIT_2
    |                                |   서버 → CLOSE_WAIT
    |  ③ FIN (서버도 종료 요청)       |
    | ←───────────────────────────── |   서버 → LAST_ACK
    |                                |
    |  ④ ACK (종료 수신 확인)         |
    | ─────────────────────────────→ |   클라이언트 → TIME_WAIT
    |                                |   서버 → CLOSED
    |   (TIME_WAIT 타이머 만료 후)    |
    |        클라이언트 → CLOSED      |
```

> **TIME_WAIT 상태**: 클라이언트는 마지막 ACK 전송 후 일정 시간(보통 2MSL, 약 60초) 대기한다. 이는 마지막 ACK가 유실되어 서버가 FIN을 재전송할 경우를 대비하기 위함이다.

### 2-3. SYN Flood 공격과의 관련성

SYN Flood는 TCP 3-Way Handshake의 구조적 취약점을 악용한 **DoS(서비스 거부) 공격**이다.

```
공격자 ────→ SYN ────→ [서버]  (① 대량의 SYN 패킷 전송)
          ← SYN+ACK ←         (② 서버가 SYN+ACK 응답)
           (ACK 안 보냄)        (③ 공격자는 ACK를 보내지 않음)
                                    ↓
                         서버의 백로그 큐(Backlog Queue)에
                         반열림(Half-Open) 연결이 쌓임
                                    ↓
                         큐 포화 → 정상 사용자 연결 불가
```

**공격 원리**:
- 공격자가 출발지 IP를 위조(IP Spoofing)하여 대량의 SYN 패킷 전송
- 서버는 각 SYN에 대해 SYN+ACK를 보내고 ACK를 기다리며 자원(메모리) 할당
- ACK가 오지 않으므로 반열림(Half-Open) 상태 연결이 계속 누적
- 서버의 연결 대기 큐(Backlog Queue)가 가득 차면 정상 사용자도 접속 불가

**대응 방법**:
- **SYN Cookie**: 서버가 SYN 수신 시 자원을 할당하지 않고, SYN+ACK의 시퀀스 번호에 연결 정보를 암호화하여 인코딩. ACK가 도착하면 시퀀스 번호를 검증하여 연결 수립
- **방화벽/IPS 임계치 설정**: 동일 출발지 IP에서 초당 SYN 요청 수 제한
- **TCP 타임아웃 단축**: 반열림 상태 유지 시간 감소
- **DDoS 방어 장비**: Out of Path 구성으로 대규모 SYN Flood 차단

## 3. IP 주소 체계

### 3-1. IPv4 주소 구조

IPv4 주소는 **32비트**로 구성되며, 8비트씩 4개의 옥텟(Octet)으로 나누어 10진수로 표기한다.

```
예시: 192.168.1.100

2진수: 11000000.10101000.00000001.01100100
       ──────── ──────── ──────── ────────
       1옥텟    2옥텟    3옥텟    4옥텟

      ├── 네트워크 부분 ──┤├── 호스트 부분 ──┤
      (어떤 네트워크인가)    (네트워크 안에서 어떤 호스트인가)
```

### 3-2. IPv4 클래스

| 클래스 | 첫 옥텟 범위 | 네트워크 비트 | 호스트 비트 | 기본 서브넷 마스크 | 용도 |
|--------|-------------|-------------|-----------|------------------|------|
| A | 1 ~ 126 | 8비트 | 24비트 | 255.0.0.0 (/8) | 대규모 네트워크 |
| B | 128 ~ 191 | 16비트 | 16비트 | 255.255.0.0 (/16) | 중규모 네트워크 |
| C | 192 ~ 223 | 24비트 | 8비트 | 255.255.255.0 (/24) | 소규모 네트워크 |
| D | 224 ~ 239 | - | - | - | 멀티캐스트 |
| E | 240 ~ 255 | - | - | - | 예약 (실험용) |

> **참고**: 127.0.0.0/8은 루프백(Loopback) 주소 대역으로 예약되어 있다 (127.0.0.1 = localhost).

### 3-3. 사설 IP 대역 (RFC 1918)

인터넷에서 라우팅되지 않는 내부 네트워크 전용 주소 대역이다. NAT(Network Address Translation)를 통해 공인 IP로 변환되어야 외부 통신이 가능하다.

| 클래스 | 사설 IP 대역 | CIDR 표기 | 사용 가능 호스트 수 |
|--------|------------|-----------|-------------------|
| A | 10.0.0.0 ~ 10.255.255.255 | 10.0.0.0/8 | 약 1,677만 개 |
| B | 172.16.0.0 ~ 172.31.255.255 | 172.16.0.0/12 | 약 104만 개 |
| C | 192.168.0.0 ~ 192.168.255.255 | 192.168.0.0/16 | 약 6만 5천 개 |

**보안관제에서의 의미**:
- 보안 로그에서 출발지/목적지가 사설 IP인 경우 → 내부 트래픽으로 판단
- 외부에서 들어오는 패킷의 출발지가 사설 IP인 경우 → **IP 스푸핑 의심** (사설 IP는 인터넷에서 라우팅 불가)
- 방화벽에서 사설 IP 대역이 출발지인 외부 트래픽은 반드시 차단해야 함 (Bogon Filtering)

### 3-4. 서브네팅(Subnetting) 기초

서브네팅은 하나의 네트워크를 더 작은 서브네트워크로 분할하는 기법이다.

**CIDR (Classless Inter-Domain Routing) 표기법**:

IP 주소 뒤에 슬래시(/)와 네트워크 비트 수를 붙여 표기한다.

```
예시: 192.168.1.0/24

/24 = 서브넷 마스크 255.255.255.0
    = 네트워크 비트 24개, 호스트 비트 8개
    = 사용 가능 호스트: 2^8 - 2 = 254개
      (네트워크 주소 192.168.1.0과 브로드캐스트 주소 192.168.1.255 제외)
```

**서브네팅 예시**:

192.168.1.0/24를 4개의 서브넷으로 분할:

| 서브넷 | 네트워크 주소 | 사용 가능 범위 | 브로드캐스트 | 서브넷 마스크 |
|--------|-------------|--------------|------------|-------------|
| 1 | 192.168.1.0/26 | 192.168.1.1 ~ .62 | 192.168.1.63 | 255.255.255.192 |
| 2 | 192.168.1.64/26 | 192.168.1.65 ~ .126 | 192.168.1.127 | 255.255.255.192 |
| 3 | 192.168.1.128/26 | 192.168.1.129 ~ .190 | 192.168.1.191 | 255.255.255.192 |
| 4 | 192.168.1.192/26 | 192.168.1.193 ~ .254 | 192.168.1.255 | 255.255.255.192 |

> **보안관제에서의 의미**: 서브넷을 이해해야 방화벽 정책의 대역 기반 규칙을 정확히 해석할 수 있다. 예를 들어 "192.168.1.0/26 허용"이라는 룰은 192.168.1.0 ~ 192.168.1.63 범위의 IP만 허용한다는 의미이다.

## 4. 주요 프로토콜과 포트 번호

### 4-1. Well-Known Ports (0 ~ 1023)

보안관제에서 가장 자주 접하는 포트 번호 목록이다.

| 포트 | 프로토콜 | 설명 | 보안관제 참고 |
|------|---------|------|-------------|
| 20 | FTP-Data | FTP 데이터 전송 | 평문 전송 → 스니핑 위험 |
| 21 | FTP-Control | FTP 제어/명령 | 평문 인증 → 계정 탈취 위험 |
| 22 | SSH | 보안 원격 접속 | 브루트포스 공격 대상, 비정상 접속 시도 모니터링 필수 |
| 23 | Telnet | 원격 접속 (평문) | **사용 금지 권고** - 모든 통신이 평문으로 노출 |
| 25 | SMTP | 이메일 발송 | 스팸 발송, 피싱 메일 탐지 |
| 53 | DNS | 도메인 이름 해석 | DNS 터널링, DNS 증폭 공격, 악성 도메인 질의 탐지 |
| 80 | HTTP | 웹 서비스 (평문) | 웹 공격(SQLi, XSS, 디렉터리 트래버설 등) 탐지 |
| 110 | POP3 | 이메일 수신 | 평문 인증 위험 |
| 143 | IMAP | 이메일 수신 (동기화) | 평문 인증 위험 |
| 443 | HTTPS | 웹 서비스 (암호화) | SSL/TLS 복호화 없이는 페이로드 분석 불가 |
| 445 | SMB | 파일 공유 (Windows) | 랜섬웨어 전파 경로 (WannaCry 등), 내부 횡적 이동 |
| 3306 | MySQL | 데이터베이스 | 외부 노출 시 DB 직접 공격 가능 |
| 3389 | RDP | 원격 데스크톱 | 브루트포스 공격, 랜섬웨어 침입 경로로 자주 악용 |
| 8080 | HTTP-Alt | 대체 웹 서비스 | 프록시 서버, 개발 서버 등에서 사용 |

### 4-2. 포트 분류

| 범위 | 분류 | 설명 |
|------|------|------|
| 0 ~ 1023 | Well-Known Ports | 표준 서비스에 할당된 포트 (IANA 관리) |
| 1024 ~ 49151 | Registered Ports | 특정 애플리케이션에 등록된 포트 |
| 49152 ~ 65535 | Dynamic/Private Ports | 클라이언트가 임시로 사용하는 포트 (Ephemeral Port) |

**보안관제에서 포트를 보는 시각**:
- **비정상 포트 사용 탐지**: HTTP 트래픽이 80이 아닌 다른 포트로 나간다면 → 우회 시도 또는 악성코드 C2 통신 의심
- **내부 → 외부 고위험 포트 연결 감시**: 내부 PC에서 외부 445, 3389 포트 접속 시도 → 비정상 행위
- **사용하지 않는 포트 오픈 탐지**: 서버에서 불필요한 포트가 열려 있으면 공격 표면(Attack Surface) 증가

## 5. 패킷 흐름 이해

### 5-1. 실제 패킷 처리 과정 (웹 접속 시나리오)

사용자가 `http://www.example.com`을 접속할 때 패킷이 어떻게 처리되는지 계층별로 살펴본다.

**송신 측 (클라이언트 PC)**
```
[L7 응용]     브라우저가 HTTP GET 요청 생성
                "GET / HTTP/1.1\r\nHost: www.example.com"
     ↓
[L4 전송]     TCP 헤더 추가
                출발지 포트: 52000 (임시 포트)
                목적지 포트: 80 (HTTP)
                시퀀스 번호, 플래그(ACK, PSH) 등
     ↓
[L3 네트워크]  IP 헤더 추가
                출발지 IP: 192.168.1.100
                목적지 IP: 93.184.216.34 (DNS로 해석한 IP)
                TTL, 프로토콜 번호(6=TCP) 등
     ↓
[L2 데이터링크] Ethernet 프레임 헤더 + 트레일러 추가
                출발지 MAC: AA:BB:CC:11:22:33
                목적지 MAC: 게이트웨이(라우터)의 MAC
                CRC 체크섬
     ↓
[L1 물리]     전기 신호로 변환하여 케이블로 전송
```

**중간 경로 (라우터/방화벽/IPS)**
```
[라우터]      L2 헤더 확인 → L3 IP 헤더로 라우팅 결정
              → 다음 홉의 MAC 주소로 L2 헤더 재생성

[방화벽]      L3(IP) + L4(포트) 정보 확인
              → 정책에 따라 허용/차단 판단

[IPS]         L3~L7 페이로드까지 심층 패킷 검사(DPI)
              → 공격 시그니처 매칭 → 탐지/차단
```

**수신 측 (웹 서버)**
```
[L1 물리]     전기 신호 수신 → 비트 스트림으로 변환
     ↓
[L2 데이터링크] 프레임 수신 → 목적지 MAC 확인 → CRC 검증
               → 정상이면 IP 패킷 추출 (L2 헤더 제거)
     ↓
[L3 네트워크]  목적지 IP 확인 → 자신의 IP와 일치 확인
               → TCP 세그먼트 추출 (IP 헤더 제거)
     ↓
[L4 전송]     목적지 포트(80) 확인 → 해당 포트의 프로세스(웹서버)로 전달
               → 시퀀스 번호 확인, ACK 응답 준비
     ↓
[L7 응용]     웹 서버(Apache/Nginx)가 HTTP 요청 해석
               → 요청된 페이지 데이터로 응답 생성
```

## 6. VLAN과 서브넷

### 6-1. VLAN (Virtual LAN)

VLAN은 물리적 네트워크 구성과 무관하게, **스위치에서 논리적으로 네트워크를 분리**하는 기술이다.

```
물리적으로 같은 스위치에 연결되어 있지만:

┌─────────────────────────────────────────┐
│              L2 스위치                    │
│                                          │
│  [VLAN 10: 인사팀]    [VLAN 20: 개발팀]   │
│   포트 1, 2, 3         포트 4, 5, 6       │
│   192.168.10.0/24     192.168.20.0/24    │
│                                          │
│  → VLAN 10과 VLAN 20 간 직접 통신 불가    │
│  → 통신하려면 L3 장비(라우터)를 거쳐야 함   │
└─────────────────────────────────────────┘
```

**VLAN의 보안적 의미**:
- **브로드캐스트 도메인 분리**: ARP 스푸핑 등의 L2 공격 범위를 VLAN 단위로 제한
- **접근 통제 강화**: VLAN 간 통신은 반드시 라우터/방화벽을 통과하므로 정책 적용 가능
- **내부 횡적 이동 차단**: 공격자가 한 VLAN을 장악해도 다른 VLAN으로의 이동이 제한됨
- **업무 영역별 분리**: 부서, 기능, 보안 등급에 따라 네트워크를 논리적으로 분리

### 6-2. 서브넷과 VLAN의 관계

일반적으로 **하나의 VLAN = 하나의 서브넷**으로 구성한다.

```
VLAN 10 (인사팀)     →  192.168.10.0/24  →  게이트웨이: 192.168.10.1
VLAN 20 (개발팀)     →  192.168.20.0/24  →  게이트웨이: 192.168.20.1
VLAN 30 (서버팜)     →  192.168.30.0/24  →  게이트웨이: 192.168.30.1
VLAN 100 (DMZ)      →  10.10.100.0/24   →  게이트웨이: 10.10.100.1
```

> **보안관제 실무**: 로그 분석 시 출발지/목적지 IP를 보고 어느 VLAN(어느 부서/영역)에서 발생한 트래픽인지 빠르게 파악할 수 있어야 한다. 이를 위해 IP 대역-VLAN-부서 매핑 테이블을 사전에 확보하는 것이 중요하다.

## 7. 보안관제 네트워크 시나리오

```
공격자#1 ─┐
           ├→ [라우터] → [방화벽] → [IPS] → [IDS] → [스위치] → 내부망
공격자#2 ─┘
                                              ↑
                                          관제 요원 분석
                                    (공격 유효성 확인 후 방화벽 IP 차단)
```

1. 공격자가 내부 시스템 권한 획득 목적으로 공격 시도
2. 관제 요원이 보안장비(방화벽·IPS·IDS·WAF) 이벤트 분석
3. 공격 유효성 확인 → 방화벽에서 공격자 IP 차단
4. 탐지 이벤트에 대한 공격 설명 및 대응 조치를 보고서로 작성 → 담당자 통보

## 8. 네트워크 구성 방식

### In-line 모드 (일반적)

```
[라우터] → [방화벽] → [IPS] → [스위치] → [서버]
```

- 모든 트래픽이 보안장비를 반드시 통과
- 탐지 + **차단** 가능
- 요구 사항:
  - 빠른 패킷 처리 속도
  - 변종 패턴 검출 정확성
  - 장비 오류 시 **Bypass** 기능
  - 2대 이상 구성 시 **Fail-Over** 기능

### Sniffing 모드

```
[라우터] → [방화벽] → [스위치] → [서버]
                          ↓ (미러링)
                         [IDS]
```

- 미러링 장비를 통해 트래픽을 복사하여 분석
- **탐지만 가능**, 차단 기능 없음
- IDS 장비에서 주로 사용

### Out of Path 모드

```
[인터넷] → [라우터] → [미러링 장비] → [라우터] → [방화벽] → 내부망
                              ↓
                      [DDoS 탐지장비(센서)]
                              ↓
                      [DDoS 차단장비]
```

- 물리 회선 바깥에 탐지·차단 장비 설치
- 미러링으로 트래픽 분석 → 공격 차단
- Inline 방식보다 구성 복잡, 고비용
- ISP 및 대형 서비스 망에서 주로 사용 (DDoS 대응)

### HA (High Availability) 구성

**Active-Active 방식**
```
인터넷 ─┐        ┌─ 방화벽A ─┐
         ├─ L4 ─┤            ├─ 내부망
         │        └─ 방화벽B ─┘
         │   (한쪽 장애 시 Fail-Over)
```
- 트래픽 Load Balancing
- 한쪽 장애 시 Fail-Over로 서비스 가용성 보장

**Active-Standby 방식**
```
평상시: [방화벽A(Active)] ──→ 내부망
장애 시: [방화벽B(Standby)] ──→ 내부망
```
- 평소 Active 방화벽으로 통신
- Active 장애 시 Standby 자동 전환

## 9. Zone 개념

| Zone | 정의 |
|------|------|
| **내부망** | 물리적 망분리·접근통제시스템으로 외부 직접 접근이 차단되는 구간 |
| **DMZ** | 인터넷과 내부망 사이 중간 지점. 외부 서비스 제공 시 내부 보호 목적 |
| **인터넷 구간** | 개인정보처리시스템과 인터넷이 직접 연결된 구간 |

```
인터넷 → [방화벽] → DMZ 구간 (웹서버, 메일서버 등 대외 서비스)
                  └→ 내부망 (DB 서버, 내부 업무 시스템)
```

### Zone 간 통신 흐름

- 외부(Untrust) <-> 내부(Trust): 방화벽에서 엄격히 통제
- 외부(Untrust) <-> DMZ: 허용된 서비스 포트만 오픈
- 내부(Trust) <-> DMZ: 내부에서 DMZ 접근은 상대적으로 허용

### 9-1. DMZ 상세

#### DMZ가 필요한 이유

외부 사용자에게 웹, 메일 등의 서비스를 제공해야 하지만, 해당 서버가 해킹될 경우 내부망까지 침투되는 것을 막아야 한다. DMZ는 이 두 가지 요구를 동시에 충족하는 **완충 지대(Buffer Zone)** 역할을 한다.

```
                    ┌──────────────────────────────────────┐
                    │         방화벽 (이중 방화벽 구조)       │
                    │                                      │
인터넷 ───→ [외부 방화벽] ───→ DMZ ───→ [내부 방화벽] ───→ 내부망
                    │            │                          │
                    │        웹서버                     DB서버 │
                    │       메일서버                   ERP시스템│
                    │       DNS서버                   파일서버  │
                    │      VPN 게이트웨이              AD서버   │
                    └──────────────────────────────────────┘
```

#### 실제 기업 환경에서의 DMZ 구성 사례

**일반적인 기업 DMZ 구성**:

```
인터넷
   │
[외부 방화벽] ──── 정책: 외부→DMZ 허용 포트만 오픈 (80, 443 등)
   │
┌──┴──────────────────── DMZ ────────────────────────┐
│                                                     │
│  [웹서버]  [메일서버]  [DNS서버]  [리버스프록시]       │
│  (80/443)  (25/110)   (53)      (80/443)            │
│                                                     │
└─────────────────────────┬──────────────────────────┘
                          │
               [내부 방화벽] ──── 정책: DMZ→내부 최소한의 포트만 허용
                          │         (예: 웹서버→DB 3306만 허용)
                          │
               ┌──────────┴─────────── 내부망 ───────┐
               │                                      │
               │  [DB서버]  [AD서버]  [업무시스템]       │
               │  (3306)   (389)    (내부포트)          │
               │                                      │
               └──────────────────────────────────────┘
```

**DMZ 방화벽 정책 원칙**:

| 방향 | 정책 | 예시 |
|------|------|------|
| 인터넷 → DMZ | 필요한 서비스 포트만 허용 | 외부 → 웹서버 80, 443만 허용 |
| DMZ → 인터넷 | 원칙적으로 차단 (필요시 최소 허용) | 메일서버 → 외부 25 포트만 허용 |
| DMZ → 내부망 | **최소한의 포트만 허용** (핵심) | 웹서버 → DB서버 3306만 허용 |
| 내부망 → DMZ | 관리 목적으로 허용 | 관리자 PC → 웹서버 SSH(22) 허용 |
| 인터넷 → 내부망 | **완전 차단** | 예외 없음 (VPN 통해서만 접근) |
| 내부망 → 인터넷 | 프록시를 통해 제한적 허용 | 업무 PC → 프록시서버 → 인터넷 |

> **핵심 원칙**: DMZ의 서버가 해킹되더라도, 내부 방화벽이 DMZ→내부망 통신을 최소한으로 제한하고 있으므로 공격자가 내부망까지 침투하기 어렵다. 이것이 DMZ의 핵심 보안 가치이다.

**보안관제에서의 DMZ 모니터링 포인트**:
- DMZ 서버에서 내부망으로의 **비정상 포트 접속 시도** → 서버 침해 의심
- DMZ 서버에서 외부 인터넷으로의 **아웃바운드 연결** → 악성코드 C2 통신 의심
- DMZ 서버 간의 **횡적 이동(Lateral Movement)** → 공격 확산 의심
- 허용되지 않은 포트로의 인바운드 트래픽 → 공격 시도 또는 정책 위반

## 10. Health Check (가용성 모니터링)

**사용 도구**: NMS (Network Management System), Cacti

**프로토콜**: ICMP (Ping), SNMP

**동작 원리**
```
NMS/Cacti ──[Request]──→ [라우터] → [방화벽(Port Open 필요)] → 서버
          ←─[Response]──

(서버 다운 시 Response 없음 → 장애 감지)
```

> 방화벽에서 Health Check 패킷(ICMP, SNMP)이 통과할 수 있도록 필요한 포트를 사전에 오픈해야 함.
