# 08. SIEM 운영

---

## 1. SIEM 구성요소

### Manager
- 경보·감사 데이터 발생 시 다양한 알람 처리 (Sound, Email, SMS, 스크립트, SNMP)
- 감사 데이터 및 설정 데이터 저장을 위한 DB 백업·삭제 스케줄링 처리
- 모든 자체 감사 데이터 생성 및 DB 저장
- 상관분석 엔진 구동: 수집된 이벤트를 실시간으로 룰과 대조하여 경보 생성
- 에이전트 상태 모니터링 및 헬스체크 관리

### Console
- 사용자 및 에이전트 그룹 관리
- 구성관리, 수집조건, 연관성 분석, DB 백업·삭제 관리 등 모든 설정 화면 제공
- 실시간 대시보드 및 보고서 출력 인터페이스
- 경보 확인, 티켓 생성, 대응 이력 관리 화면

### Agent
- 관리 대상 장비에서 수집한 로그를 정해진 규칙에 따라 **정규화**
- 수집조건 규칙과 비교 → Manager 전송 여부 결정
- 동일 패턴 이벤트는 **축약 처리** → 네트워크·DB 부하 최소화
- 장비와의 통신 장애 시 로컬 버퍼링 후 재전송 (데이터 유실 방지)

### 구성도

```
침입차단 이벤트 ─┐
침입탐지 이벤트 ─┤ [Agent] ──SSL 통신──→ [Manager] ──→ [Console]
Virus 이벤트  ─┤               (데이터 수집·판단)    (감시자/리포팅/분석)
기타 이벤트   ─┘                    │
                               [데이터베이스]
                                         ↘ 알림 경보 (Email/SMS)
```

## 2. 로그 수집 아키텍처

### Agent 방식 vs Agentless 방식

| 항목 | Agent 방식 | Agentless 방식 |
|------|-----------|---------------|
| **설치** | 수집 대상 장비에 Agent 소프트웨어 설치 | 별도 설치 없음 |
| **수집 방법** | Agent가 로그를 읽어 Manager에 전송 | Syslog, SNMP Trap, API 등 프로토콜로 수집 |
| **장점** | 실시간 수집, 로그 필터링/축약 가능, 통신 암호화 | 설치 부담 없음, 네트워크 장비·보안장비에 적합 |
| **단점** | 장비에 Agent 설치 필요, 리소스 소모 | 로그 유실 가능성(UDP 기반 Syslog), 전처리 어려움 |
| **적용 대상** | 서버(Windows/Linux), 애플리케이션 로그 | 방화벽, IPS, 스위치, 라우터 등 네트워크 장비 |

### Syslog Forwarder의 역할

```
[보안장비/네트워크장비]
       │ Syslog (UDP 514 / TCP 514 / TCP 6514-TLS)
       ▼
[Syslog Forwarder / Relay]
       │  ← 로그 버퍼링, 프로토콜 변환, 전송 보장
       │  ← 여러 소스의 로그를 집중하여 Manager 부하 분산
       ▼
[SIEM Manager]
```

- **역할 1 - 로그 집중(Aggregation)**: 다수의 장비 로그를 한 곳에 모아 SIEM으로 전달
- **역할 2 - 프로토콜 변환**: UDP Syslog → TCP 또는 TLS로 변환하여 전송 안정성 확보
- **역할 3 - 버퍼링**: 네트워크 장애 시 로그를 로컬에 임시 저장 후 복구 시 재전송
- **역할 4 - 필터링**: 불필요한 로그(Debug 레벨 등)를 사전에 제거하여 SIEM 부하 감소

### 로그 수집 시 네트워크 부하 관리

| 기법 | 설명 |
|------|------|
| **로그 축약(Aggregation)** | 동일 패턴 이벤트를 N건으로 묶어 1건으로 전송 (예: 같은 IP에서 동일 차단 100건 → 1건 + count=100) |
| **필터링** | 수집 단계에서 불필요 로그 제거 (Informational 레벨 등) |
| **전송 주기 조절** | 실시간 전송 대신 일정 주기(예: 10초)로 배치 전송 |
| **압축 전송** | Agent-Manager 간 데이터 압축하여 대역폭 절감 |
| **QoS 설정** | 로그 전송 트래픽에 별도 VLAN 또는 QoS 정책 적용 |
| **트래픽 모니터링** | Agent별 EPS(Events Per Second) 모니터링으로 이상 급증 조기 감지 |

## 3. 로그와 파싱

### 로그 (Log)
컴퓨터나 서버에서 사용자의 행위 정보를 **시간에 따라 기록**한 데이터.

### 파싱 (Parsing)
원본 로그를 **필드 별로 구분**하는 작업.

```
원본 로그 (Raw):
duration=3 machine_name=FW1 src_ip=10.20.30.149 src_port=53209 dst_ip=192.168.100.100 ...

파싱 후:
┌────────────┬──────────────────┐
│ duration   │ 3                │
│ machine    │ FW1              │
│ src_ip     │ 10.20.30.149     │
│ src_port   │ 53209            │
│ dst_ip     │ 192.168.100.100  │
│ dst_port   │ 80               │
│ protocol   │ TCP              │
└────────────┴──────────────────┘
```

### 파싱 심화 - 정규표현식 기반 파싱

로그 포맷이 장비마다 다르므로 정규표현식(Regex)을 사용하여 필요한 필드를 추출한다.

**예시 1: 방화벽 로그 파싱**

```
원본 로그:
Jul 29 10:23:45 FW1 action=deny src=10.20.30.149 dst=192.168.100.100 proto=TCP dport=443

정규표현식:
(\w+ \d+ [\d:]+) (\S+) action=(\w+) src=([\d.]+) dst=([\d.]+) proto=(\w+) dport=(\d+)

추출 결과:
  Group 1: Jul 29 10:23:45    → timestamp
  Group 2: FW1                → device_name
  Group 3: deny               → action
  Group 4: 10.20.30.149       → src_ip
  Group 5: 192.168.100.100    → dst_ip
  Group 6: TCP                → protocol
  Group 7: 443                → dst_port
```

**예시 2: Apache 웹서버 접근 로그 파싱**

```
원본 로그:
10.0.0.5 - admin [29/Jul/2026:14:30:12 +0900] "GET /admin/config HTTP/1.1" 200 5432

정규표현식:
([\d.]+) - (\S+) \[([^\]]+)\] "(\w+) (\S+) HTTP/[\d.]+" (\d+) (\d+)

추출 결과:
  src_ip: 10.0.0.5
  user: admin
  timestamp: 29/Jul/2026:14:30:12 +0900
  method: GET
  uri: /admin/config
  status_code: 200
  bytes: 5432
```

### 표준 로그 포맷

#### CEF (Common Event Format)

ArcSight에서 제정한 표준 로그 포맷. 파이프(|)로 헤더 필드를 구분하고, 확장 필드는 key=value 형태.

```
CEF:0|Security|IPS|4.0|100|Intrusion Detected|8|src=10.0.0.1 dst=192.168.1.1 spt=12345 dpt=80 act=blocked

헤더 구조:
CEF:버전|장비벤더|장비제품|장비버전|시그니처ID|이벤트명|심각도|확장필드

확장 필드:
  src = 출발지 IP
  dst = 목적지 IP
  spt = 출발지 Port
  dpt = 목적지 Port
  act = 수행 동작
```

#### LEEF (Log Event Extended Format)

IBM QRadar에서 사용하는 표준 로그 포맷. 탭으로 필드를 구분.

```
LEEF:2.0|Vendor|Product|Version|EventID|cat=Alert	src=10.0.0.1	dst=192.168.1.1	sev=8	action=blocked

헤더 구조:
LEEF:버전|벤더|제품|버전|이벤트ID|확장필드(탭 구분)
```

#### CEF vs LEEF 비교

| 항목 | CEF | LEEF |
|------|-----|------|
| 제정 | ArcSight (Micro Focus) | IBM QRadar |
| 구분자 | 파이프(\|) + key=value | 탭 + key=value |
| 심각도 | 0~10 (헤더에 포함) | sev 키로 확장 필드에 기록 |
| 호환성 | 대부분의 SIEM 지원 | 주로 QRadar 생태계 |

## 4. 정규화 (Normalization)

### 정규화란?

이기종 장비에서 수집된 서로 다른 형식의 로그를 **통일된 필드 구조**로 변환하는 과정이다. 각 벤더마다 같은 정보를 다른 필드명으로 기록하기 때문에, SIEM에서 통합 분석하려면 반드시 정규화가 필요하다.

### 정규화가 필요한 이유

```
문제 상황: "출발지 IP"를 검색하고 싶은데...

  Palo Alto 방화벽 로그:  src=10.0.0.1
  Fortinet 방화벽 로그:   srcip=10.0.0.1
  Snort IPS 로그:         {src_addr: 10.0.0.1}
  Apache 웹로그:          10.0.0.1 - - [29/Jul/...

→ 필드명이 모두 다르므로 통합 검색·분석 불가
→ 정규화를 통해 모두 "src_ip" 필드로 통일
```

### 필드 매핑 예시

| SIEM 표준 필드 | Palo Alto FW | Fortinet FW | Snort IPS | Check Point FW | Windows Event |
|--------------|-------------|------------|----------|---------------|--------------|
| src_ip | src | srcip | src_addr | s_addr | IpAddress |
| dst_ip | dst | dstip | dst_addr | d_addr | TargetIp |
| src_port | sport | srcport | src_port | s_port | IpPort |
| dst_port | dport | dstport | dst_port | service | TargetPort |
| action | action | action | action | action | Keywords |
| protocol | proto | proto | protocol | proto | Protocol |
| user | srcuser | user | - | user | TargetUserName |
| severity | severity | level | priority | severity | Level |
| timestamp | receive_time | date+time | timestamp | time | TimeCreated |

### 정규화 처리 흐름

```
① 원본 로그 수신 (Raw Log)
   ↓
② 로그 소스 식별 (어떤 장비/벤더인지 판별)
   ↓
③ 파서 선택 (장비별 전용 파서 적용)
   ↓
④ 필드 추출 (정규표현식 또는 구분자 기반)
   ↓
⑤ 필드 매핑 (장비 고유 필드명 → SIEM 표준 필드명 변환)
   ↓
⑥ 데이터 타입 변환 (문자열→숫자, 타임스탬프 포맷 통일 등)
   ↓
⑦ 보강(Enrichment) - 선택사항
   (GeoIP 국가 정보 추가, 자산 정보 매핑, 사용자 정보 연계 등)
   ↓
⑧ 정규화된 이벤트 저장 및 분석 엔진 전달
```

## 5. 이벤트 검색

### 검색 경로
```
SIEM → 보안관제 탭 → 통합 로그 검색
```

### 검색 조건 설정
- **로그유형 탭 선택**: Firewall, IPS, UTM, WebFW 등
- **로그 소스 탭 선택**: 실제 이벤트가 수집되는 Agent 장비 선택
- **Query 조건 설정**: 시간 / 출발지 IP / 목적지 IP / 출발지 Port / 목적지 Port / Method

## 6. 이상 그래프 확인

연동된 각 보안장비에 대해 일일 그래프 또는 30분별 그래프를 생성하여 이벤트 수치를 시각적으로 확인.

### 이상 그래프 탐지 시 확인 절차
```
① 검색할 Agent 선택
② 30분 / 일일 / 30분 경보 등 원하는 그래프 선택
③ 로그 소스 유형 선택 (FW, IPS, WebFW 등)
④ 적용

→ 이벤트 급증 구간 클릭
→ 해당 시간대의 상세 로그 확인
   (시간 / 로그소스IP / 로그소스명 / Source IP / Destination IP / Port 등)
```

### 그래프 프로파일 저장 및 불러오기
- 장비별 그래프를 **프로파일**로 저장 → 매번 새로 생성할 필요 없이 빠르게 관제
- 프로파일 열기: 우측 상단 탭 → 프로파일 목록에서 선택
- 프로파일 삭제: 리스트에서 삭제할 프로파일 선택 → X 버튼 클릭

## 7. 번들룰 (Bundle Rule)

가용성 체크를 위한 경보. 장비 장애로 인한 이벤트 미수집, 펌웨어 업데이트로 인한 필드 변경 시 미수집 등 탐지.

| 종류 | 설명 |
|------|------|
| **핑 체크** | 주기적으로 대상 장비에 Ping 전송 → 실패 시 경보 발생 |
| **프로세스 체크** | 대상 프로세스 동작 여부 주기 확인 |
| **미수집 체크** | 일정 시간 동안 로그가 수집되지 않을 경우 경보 |

## 8. 단일경보 생성

특정 조건(Object)이 충족될 때 경보를 발생시키는 가장 기본 단위의 경보.

### 생성 과정

```
① 장비에서 발생하는 이벤트가 SIEM에 어떤 식으로 수집되는지 확인
   → 통합 로그 검색에서 조건에 맞는 Query 입력 후 검색

② 탐지할 Column 선택
   (주의: Stealth Commanding 같은 문자열이 RAW에는 있지만 다른 Column에는 없을 수 있음
    → 장비별 수집 방식을 먼저 파악해야 함)

③ Object 생성
   → 필드명·연산자(AND/OR/Like)·값 입력 → '+' 버튼 클릭 → 오브젝트 그룹 지정 → 이름 설정 → 생성/수정

④ 경보 설정
   → 룰 이름 / 발생 주기(분) / 발생 건수 설정
   → 로그 소스 선택
   → Object 추가 → 등록

⑤ 제외 조건 설정 (오탐 감소)
   → 고객사 요청 IP, Google IP 등 특정 출발지 IP 제외 등록
```

**Object 이름 규칙 예시**
- `[WAF_Wapple]경보명`
- `[고객사_WAF]경보명`
- Object 그룹은 벤더사별 또는 고객사별로 구분하여 관리 용이하게 구성

**경보 설정 예시**
```
룰 이름: [WAF] Buffer Overflow 탐지
발생 주기: 1분
발생 건수: 1건
→ 1분에 해당 이벤트가 1건 발생하면 경보
```

## 9. 상관분석 (Correlation) 경보

단일 경보의 조합으로 생성. Step 별로 경보 단계가 진행되므로 고도화된 경보 생성에 적합.

### 특징
- 단일 경보를 기반으로 단계별 탐지 설정 가능
- 이기종 장비 간 연계 탐지 가능
- 1단계 탐지 로그 중에서 2단계를 통해 원하는 로그만 필터링

### 상관분석 응용 예시

**공격자 침투 시나리오 탐지**
```
Step 1: 방화벽 포트 스캔 탐지 (정보수집 단계)
Step 2: IPS/WAF 시그니처 기반 탐지 (침투·시스템 장악 단계)
```

**내부 사용자 비정상 행위 탐지**
```
Step 1: 내부 사용자 IP + 내부 서버 접근 탐지
Step 2: 업무 시간 외 특정 서버 접근 탐지 (비정상 행위)
```

### 상관분석 룰 작성 심화 - 실무 시나리오 10선

#### 시나리오 1: Brute Force 로그인 시도 탐지

```
Step 1: 동일 출발지 IP에서 로그인 실패 이벤트 5분 내 10회 이상 발생
        - 조건: action=login_failed, count >= 10, timewindow=5min
        - 그룹핑: src_ip 기준
Step 2: 해당 IP에서 로그인 성공 이벤트 발생
        - 조건: action=login_success
        - 연계 필드: src_ip (Step 1의 src_ip와 동일)
→ 의미: 무차별 대입 후 계정 탈취 성공 가능성
→ 심각도: Critical
```

#### 시나리오 2: 포트스캔 후 침투 시도

```
Step 1: 방화벽에서 동일 src_ip의 서로 다른 dst_port 접근 30분 내 20개 이상
        - 조건: distinct(dst_port) >= 20, timewindow=30min
Step 2: IPS/WAF에서 해당 src_ip의 공격 시그니처 탐지
        - 조건: event_type=attack
        - 연계 필드: src_ip
→ 의미: 정찰 활동 후 취약점 공격 시도
→ 심각도: High
```

#### 시나리오 3: 비인가 국가 접근 탐지

```
Step 1: 외부 IP에서 내부 서버 접근 시도
        - 조건: src_country NOT IN (KR, US, JP) AND dst_ip IN 내부서버대역
Step 2: 해당 접근이 허용(Allow)된 경우
        - 조건: action=allow
        - 연계 필드: src_ip, dst_ip
→ 의미: 비인가 국가에서의 내부 시스템 접근 성공
→ 심각도: High
```

#### 시나리오 4: 업무외 시간 접근 탐지

```
Step 1: 내부 사용자 IP에서 서버 접근
        - 조건: src_ip IN 내부대역, dst_ip IN 서버대역
        - 시간 조건: 22:00 ~ 06:00 또는 주말/공휴일
Step 2: 접근 후 파일 다운로드 또는 DB 쿼리 실행
        - 조건: action IN (download, query, export)
→ 의미: 업무 시간 외 비정상 데이터 접근
→ 심각도: Medium ~ High
```

#### 시나리오 5: 대량 데이터 유출 징후

```
Step 1: 특정 내부 IP에서 외부로의 아웃바운드 트래픽 급증
        - 조건: direction=outbound, bytes_sent > 100MB, timewindow=1hour
Step 2: 해당 IP에서 이메일 대량 발송 또는 클라우드 스토리지 업로드 탐지
        - 조건: dst_port IN (25, 587, 443) AND dst_domain LIKE (*drive*, *dropbox*, *wetransfer*)
→ 의미: 내부 정보 유출 시도 가능성
→ 심각도: Critical
```

#### 시나리오 6: 악성코드 감염 후 C&C 통신 탐지

```
Step 1: 안티바이러스에서 악성코드 탐지 이벤트 발생
        - 조건: event_type=malware_detected
Step 2: 해당 호스트에서 외부 C&C 의심 IP/도메인으로 통신 시도
        - 조건: dst_ip IN C&C블랙리스트 OR dst_domain IN 위협정보DB
        - 연계 필드: src_ip (감염 호스트)
→ 의미: 악성코드 감염 후 명령제어 서버 통신 시도
→ 심각도: Critical
```

#### 시나리오 7: 권한 상승 후 비정상 행위

```
Step 1: 일반 사용자 계정으로 관리자 권한 획득 이벤트
        - 조건: event_id=4672 (Windows 특수 권한 할당) 또는 sudo 사용 로그
Step 2: 권한 상승 후 시스템 설정 변경 또는 계정 생성
        - 조건: event_id IN (4720, 4732, 7045) - 계정 생성, 그룹 추가, 서비스 설치
        - 연계 필드: user, src_ip
→ 의미: 권한 상승을 통한 시스템 장악 시도
→ 심각도: Critical
```

#### 시나리오 8: SQL Injection 공격 탐지

```
Step 1: WAF에서 SQL Injection 시그니처 탐지
        - 조건: attack_type=SQL_Injection
Step 2: 동일 src_ip에서 DB 서버로 직접 통신 시도
        - 조건: dst_port IN (1433, 3306, 1521, 5432)
        - 연계 필드: src_ip
→ 의미: 웹 공격 후 DB 직접 접근 시도
→ 심각도: High
```

#### 시나리오 9: VPN 이상 접근 탐지

```
Step 1: VPN 로그인 성공
        - 조건: event_type=vpn_login, action=success
Step 2: 동일 사용자 계정이 서로 다른 국가에서 단시간 내 접속
        - 조건: 동일 user, 서로 다른 src_country, timewindow=1hour
→ 의미: 계정 탈취 후 VPN 악용 (Impossible Travel)
→ 심각도: High
```

#### 시나리오 10: 웹셸 업로드 후 실행 탐지

```
Step 1: WAF에서 파일 업로드 공격 탐지 (확장자 우회, 웹셸 패턴)
        - 조건: attack_type IN (file_upload, webshell)
Step 2: 웹서버에서 비정상 프로세스 실행 (cmd.exe, /bin/sh, powershell 등)
        - 조건: parent_process=httpd/nginx/iis AND child_process IN (cmd, sh, powershell)
→ 의미: 웹셸 업로드 성공 후 시스템 명령 실행
→ 심각도: Critical
```

## 10. 단일경보 vs 상관분석 비교

| 항목 | 단일경보 | 상관분석 |
|------|---------|---------|
| 조건 | 단일 이벤트 조건 충족 | 단일경보 여러 개의 조합 |
| 단계 | 1단계 | 다단계 (Step 1 → Step 2 → ...) |
| 활용 | 개별 장비의 특정 이벤트 탐지 | 복잡한 공격 시나리오, 이기종 연계 탐지 |
| 오탐 관리 | 제외 IP, 제외 조건 설정 | 단계별 필터링으로 정밀도 향상 |

## 11. 경보 우선순위(Severity) 체계

### 등급 기준

| 등급 | 점수 | 기준 | 예시 |
|------|------|------|------|
| **Critical** | 9~10 | 즉각 대응 필요. 시스템 침해 확인 또는 핵심 자산 직접 위협 | 랜섬웨어 감염 확인, C&C 통신 성공, 관리자 계정 탈취, 웹셸 실행 |
| **High** | 7~8 | 신속 대응 필요. 침해 가능성 높은 공격 시도 | Brute Force 성공, SQL Injection 탐지, 비인가 국가 접근 허용, 권한 상승 |
| **Medium** | 4~6 | 확인 필요. 잠재적 위협 또는 정책 위반 | 업무외 시간 접근, 반복적 정책 위반, 취약점 스캔 탐지 |
| **Low** | 2~3 | 모니터링 대상. 단독으로는 위협 아님 | 포트스캔 시도(차단됨), 비정상 DNS 쿼리, 정보 수집 행위 |
| **Info** | 0~1 | 참고 정보. 이상 징후 기록용 | 정상 정책 변경, 사용자 로그인/로그아웃, 시스템 재시작 |

### 등급별 대응 SLA (응답 시간)

| 등급 | 초기 확인 | 분석 완료 | 보고 | 비고 |
|------|----------|----------|------|------|
| **Critical** | 5분 이내 | 30분 이내 | 1시간 이내 | 즉시 전화 보고 + 침해사고 대응 절차 착수 |
| **High** | 15분 이내 | 1시간 이내 | 2시간 이내 | 담당자 즉시 통보, 필요시 에스컬레이션 |
| **Medium** | 30분 이내 | 4시간 이내 | 당일 보고 | 관제 일일보고서에 포함 |
| **Low** | 1시간 이내 | 8시간 이내 | 주간 보고 | 추이 모니터링, 반복 시 등급 상향 검토 |
| **Info** | 해당 없음 | 해당 없음 | 월간 보고 | 통계 분석 시 참고 자료로 활용 |

### 경보 에스컬레이션 기준

```
1차: 관제 요원 (모든 경보 초기 확인)
  ↓ Critical/High 경보 발생 시
2차: 관제 팀장 (상황 판단 및 대응 지시)
  ↓ 침해사고 확인 시
3차: CERT/침해사고대응팀 (전문 분석 및 대응)
  ↓ 대규모 침해 또는 개인정보 유출 시
4차: CISO/경영진 보고 + 유관기관 신고 (KISA 등)
```

## 13. 오탐 관리 실무

### 화이트리스트 관리

#### 화이트리스트 등록 대상

| 유형 | 예시 | 등록 사유 |
|------|------|----------|
| 내부 관리 IP | 10.0.0.50 (관리자 PC) | 정기 취약점 점검 시 공격 탐지 오탐 |
| 검색엔진 봇 IP | Googlebot, Bingbot IP 대역 | 웹 크롤링이 스캔 공격으로 오탐 |
| CDN IP 대역 | Cloudflare, Akamai 대역 | 다수 요청이 DDoS로 오탐 |
| 모니터링 시스템 | Nagios, Zabbix 서버 IP | 헬스체크 트래픽이 스캔으로 오탐 |
| 협력사 IP | 외부 유지보수 업체 IP | 원격 접속 시 비인가 접근으로 오탐 |

#### 화이트리스트 등록 절차

```
① 오탐 식별: 경보 분석 후 오탐으로 판단
② 등록 요청: 화이트리스트 등록 요청서 작성 (사유, IP, 적용 기간)
③ 검토·승인: 관제 팀장 또는 보안 담당자 승인
④ 등록: SIEM 제외 조건에 해당 IP/조건 추가
⑤ 주기 검토: 분기별로 화이트리스트 유효성 재검토
⑥ 만료 관리: 임시 등록 건은 만료일 도래 시 자동 해제 또는 재승인
```

### 경보 튜닝 주기

| 튜닝 주기 | 활동 내용 |
|----------|----------|
| **일간** | 당일 발생한 오탐 경보 확인, 즉시 제외 가능한 건 처리 |
| **주간** | 주간 오탐 현황 집계, 반복 오탐 패턴 분석, 임계치 조정 검토 |
| **월간** | 전체 경보 룰 오탐률 분석, 튜닝 대상 룰 선정, 룰 수정/비활성화 |
| **분기** | 화이트리스트 전수 검토, 비활성 룰 정리, 신규 위협 대응 룰 추가 |

### 오탐률 KPI

```
오탐률(%) = (오탐 건수 / 전체 경보 건수) × 100

목표 오탐률: 30% 이하 (업계 권장)
우수 수준:  20% 이하
관리 기준:  50% 초과 시 해당 룰 즉시 튜닝 필요
```

| KPI 항목 | 측정 방법 | 목표값 |
|---------|----------|-------|
| 전체 오탐률 | 월간 오탐 건수 / 월간 전체 경보 건수 | 30% 이하 |
| 룰별 오탐률 | 개별 룰의 오탐 건수 / 해당 룰 전체 경보 건수 | 40% 이하 |
| 경보 처리율 | 처리 완료 경보 / 전체 발생 경보 | 95% 이상 |
| 평균 처리 시간 | 경보 발생 ~ 처리 완료까지 소요 시간 | 등급별 SLA 준수 |

### 신규 경보 등록 후 모니터링 기간

```
① 테스트 모드 운영 (1~2주)
   - 신규 경보를 "알림 없음" 모드로 등록
   - 실제 경보 발생 건수와 오탐 여부를 모니터링
   - 일일 경보 건수, 오탐률, 주요 탐지 IP 등 기록

② 임계치 조정 (1주)
   - 테스트 결과 기반으로 발생 건수, 시간 윈도우 등 조정
   - 오탐률 50% 이상이면 조건 재설계

③ 정식 운영 전환
   - 오탐률 30% 이하 달성 시 정식 경보로 전환
   - 알림(Email/SMS) 활성화

④ 안정화 모니터링 (2주)
   - 정식 전환 후 2주간 집중 모니터링
   - 추가 튜닝 필요 시 즉시 반영
```

| 경보 발생 현황 | 등급별 경보 건수, 전일 대비 증감률 |

| Top 공격 출발지 | 상위 5개 공격 출발지 IP 및 국가 |
| Top 공격 유형 | 상위 5개 공격 유형 및 건수 |
| 장비 가용성 | 수집 장비별 정상/장애 현황, 미수집 발생 여부 |
| 특이사항 | 신규 위협, 이슈사항, 조치 필요 사항 |

### 주간 보고서

| 포함 항목 | 세부 내용 |
|----------|----------|
| 보고 기간 | 해당 주 월~일 |
| 주간 경보 추이 | 일별 경보 발생 추이 그래프, 전주 대비 증감 분석 |
| 공격 유형 분석 | 주간 공격 유형 분포, 신규 공격 패턴 여부 |
| 오탐 현황 | 주간 오탐률, 튜닝 대상 룰 목록 |
| 장비 운영 현황 | 장비별 EPS 추이, 장애 발생 이력 |
| 위협 인텔리전스 | 주간 주요 보안 위협 동향, 관련 경보 발생 여부 |
| 개선 사항 | 룰 튜닝 내역, 신규 룰 등록 내역, 화이트리스트 변경 이력 |

### 월간 보고서

| 포함 항목 | 세부 내용 |
|----------|----------|
| 보고 기간 | 해당 월 1일 ~ 말일 |
| 월간 경보 통계 | 등급별·유형별·장비별 경보 건수 통계 |
| 경보 추이 분석 | 월별 경보 추이 (최근 6개월), 전월 대비 증감 분석 |
| 상관분석 탐지 현황 | 상관분석 룰별 탐지 건수, 주요 탐지 사례 상세 |
| 오탐 관리 현황 | 월간 오탐률 추이, KPI 달성 여부, 튜닝 이력 |
| 침해사고 대응 현황 | 침해사고 발생 건수, 대응 결과, 재발 방지 대책 |
| SIEM 운영 현황 | 로그 수집량 추이, 스토리지 사용량, 시스템 성능 현황 |
| 개선 권고사항 | 룰 고도화 방안, 신규 로그 소스 연동 계획, 프로세스 개선 제안 |

### 보고서 자동화

| 자동화 항목 | 방법 |
|------------|------|
| 데이터 수집 | SIEM API 또는 DB 쿼리를 통한 통계 데이터 자동 추출 |
| 보고서 생성 | 템플릿 기반 자동 보고서 생성 (HTML/PDF) |
| 배포 | 이메일 자동 발송 (일일: 익일 09시, 주간: 매주 월요일, 월간: 익월 5일) |
| 대시보드 연동 | 보고서 핵심 지표를 대시보드 위젯으로 연동하여 실시간 확인 |

```
자동화 구성 예시:

① SIEM 스케줄러에서 매일 01:00에 전일 데이터 쿼리 실행
② 쿼리 결과를 보고서 템플릿에 자동 삽입
③ PDF/HTML 형식으로 보고서 파일 생성
④ 사전 등록된 수신자 목록에 이메일 자동 발송
⑤ 보고서 파일을 문서 관리 시스템에 자동 아카이빙
```
