# 시나리오1 데이터 사전과 조사 과제

## 실습 목표

스타트업의 클라우드 보안 담당자로서 3주간의 활동을 조사한다. 주어진 로그에서 조사할 대상을 고르고, 원시 이벤트로 가설을 확인하고, 남아 있는 불확실성을 보고한다.

실습을 마치면 다음을 할 수 있어야 한다.

- 질문에 필요한 로그 소스와 현재 자료의 한계를 설명한다.
- 사용자·시간창의 평시 활동과 다른 특징을 찾아 조사 우선순위를 정한다.
- 규칙과 Isolation Forest 결과를 비교하고 놓칠 수 있는 후보를 찾는다.
- 시도와 성공, 호출 주체와 변경 대상, 관찰 사실과 추정을 구분한다.

## 자료와 분석 단위

이 자료는 AWS 계정 `123456789012`의 활동을 모사한 **교육용 합성 데이터**다. 기간은 KST 2026-03-23~2026-04-12다. 실제 환경에서 수집된 무가공 CloudTrail이라고 해석하지 않는다.

| 파일 | 내용 | 규모 |
|---|---|---:|
| cloudtrail_raw_events.csv | 교육용 원시 이벤트의 평탄화 CSV | 129,805행 |
| logs_aggregated_user_hour.csv | 분석 주체×1시간 집계 | 8,065행 |
| 01_CloudTrail_헌팅.ipynb | 기본 M1~M6·연결 B1~B2·심화 A1~A4 | 12개 활동 |
| 장표127_요약사건.json | 교안 127페이지 요약 사건; CSV와 별개 | 44행 |
| 필터연습_가상입력.json | 성공·주체·KST 야간 조건 연습 전용 | 9개 입력 |

집계 1행은 **사건 1건 또는 API 1건이 아니다.** 같은 사건이 여러 시간창에 걸칠 수 있고 같은 시간창에 여러 출발지의 활동이 섞일 수 있다. `user`와 날짜를 포함한 `hour`를 함께 사용해 연결한다. 실습 결과는 별도 노트북·결과서에 기록한다.

교안 127페이지의 작은 로그셋은 독립된 예제다. 계정 이름이 같더라도 이 CSV의 동일 인물·동일 사건으로 연결하지 않는다. 교안 132페이지의 상위 3개 선택은 축약 표 연습이며, 전체 CSV 과제에서는 상위 5개 시간창을 제출한다.

## 데이터 사전

| 컬럼 | 해석 및 계산 기준 |
|---|---|
| user | 교육용 분석 식별자. IAM 사용자 이름·역할 세션 표기·root 등이 섞여 있으므로 원시 ARN과 유형을 함께 확인 |
| hour | KST 시간창 시작. 예: 03:00은 03:00 이상 04:00 미만 |
| api_call_count | 현재 자료에서는 해당 시간창의 이벤트 행 수. 로그인 이벤트도 포함 |
| error_rate | 오류 코드가 비어 있지 않은 이벤트 수÷전체 이벤트 수, 소수 셋째 자리 반올림 |
| unique_regions | awsRegion의 서로 다른 값 개수. 출발지 국가 수가 아님 |
| sensitive_api_count | 재현용 민감 이벤트 사전의 호출 수. 성공·실패 모두 포함 |
| night_activity | 현재 자료의 기준: 21~23시와 00~06시 시간창이면 1. 즉 21:00부터 다음 날 07:00 직전까지 |
| unique_services | eventSource의 서로 다른 값 개수 |
| source_ip_count | sourceIPAddress의 서로 다른 값 개수. 악성 IP 수가 아님 |
| console_login | ConsoleLogin 이벤트 존재 여부. 로그인 성공·MFA 여부는 아님 |
| hour_of_day | KST 시간창 시작 시각의 시, 0~23 |
| day_of_week | KST 기준 Mon~Sun |
| is_weekend | KST 토·일이면 1 |

원시 컬럼은 `eventTime`(UTC), `awsRegion`, `userIdentityType`, `userIdentityArn`, `eventSource`, `eventName`, `sourceIPAddress`, `errorCode`, 파생 `user`다. 자료에는 이벤트가 있는 시간창만 존재한다. 전체 사용자×전체 시간 조합의 표가 아니며, 빈 시간창을 임의로 정상 행이나 수집 장애로 판정하지 않는다.

시간 변환은 `pd.to_datetime(raw['eventTime'], utc=True).dt.tz_convert('Asia/Seoul')`로 수행한다. UTC를 문자열 상태에서 KST와 비교하지 않는다. 업무시간 기준선은 현재 풀이의 재현을 위해 평일 09시~18시 시간창, 즉 `[09:00,19:00)`을 사용한다.

현재 민감 수의 재현용 목록은 다음과 같다. 생성 코드가 제공되지 않아 관측 데이터에서 대조한 정의다.

```text
AttachRolePolicy, AttachUserPolicy, AuthorizeSecurityGroupIngress,
CreateAccessKey, CreatePolicyVersion, CreateUser, PassRole,
PutUserPolicy, SetDefaultPolicyVersion, UpdateAccessKey
```

`PassRole`은 실제로 API가 아닌 권한이며 이 자료에 잘못 표현된 행이 있다. `ListBucket` 표기도 실제 S3 API·CloudTrail 이벤트명과 구분해야 한다. 현재 수치 재현에는 제공된 집계값을 사용하고, 이 표현들을 실제 AWS의 정확한 관측 사례로 인용하지 않는다. [AWS PassRole 설명](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_passrole.html), [S3 권한과 API 구분](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html)

## 과제 A. 가설과 데이터 점검

1. “비정상적으로 보인다”보다 구체적인 가설 2개를 작성한다. 예: 승인된 업무 범위를 벗어난 IAM 변경 시도가 특정 시간창에 집중되었을 수 있다.
2. 각 가설이 맞다면 어떤 이벤트·필드가 보일지 적는다.
3. 같은 현상을 설명할 수 있는 정상 업무 상황도 하나 적는다.
4. 원시 로그와 집계가 연결되는지 사용자·시간창 한 개를 선택해 확인한다.
5. 현재 자료에 없어서 확인할 수 없는 필드를 적는다.

제출: 가설 / 관찰 예상 / 정상 설명 / 필요한 필드 / 현재 자료의 한계.

## 과제 B. 수동 규칙과 우선순위

먼저 본인 기준으로 후보를 선택하고 조건을 기록한다. 다음 기준 규칙으로 다시 계산하여 차이를 설명한다. 본인 규칙이 다르다는 이유만으로 오답이 되지는 않는다.

| 기준 규칙 | 조건 |
|---|---|
| 호출량 | 사용자 업무시간 호출량 중위수의 4배 이상이면서 최소 80건 이상 |
| 실패율 | error_rate ≥0.15 |
| 리전 | unique_regions ≥3 |
| 민감 호출 | sensitive_api_count ≥2 |
| 조건부 야간 | night_activity=1이고, 민감 호출≥1 또는 실패율≥0.1 또는 호출량≥80 |

충족한 규칙 수를 더해 0~5점으로 만든다. 기준선이 없는 주체는 표시하여 별도 검토한다. 원래 풀이를 정확히 재현할 때는 전체 집계 행의 호출량 중위수로 보완하지만, 그 값이 해당 주체의 실제 평시를 뜻하지는 않는다.

모든 특징을 평시 중위수로 나누지 않는다. 실패율·민감 호출·야간 여부의 중위수는 0일 수 있다. 위 규칙의 신호들은 서로 겹칠 수 있으므로 점수 5를 독립 증거 5개로 해석하지 않는다.

제출: 상위 5개 시간창, 충족 규칙, 정상 가능 사유, 다음 확인 필드. 동점 순서를 정한 방식도 기록한다. 같은 주체의 연속 시간창은 하나의 조사 묶음으로 연결할지 검토한다.

## 과제 C. Isolation Forest와 비교

1. api_call_count, error_rate, unique_regions, sensitive_api_count, night_activity의 5개 특징을 사용한다.
2. 첫 비교에서는 `n_estimators=300`, `random_state=42`, `contamination=0.01`을 사용한다.
3. `decision_function`은 **낮을수록 이상**이다. `predict`의 -1은 모델 경보이며 침해 확정이 아니다.
4. 같은 상위 K에서 수동 규칙·모델 후보를 비교한다. K=5·20·80일 때 조사 범위가 어떻게 달라지는지 기록한다.
5. 변환 비교에서는 contamination을 고정하고 원래 값, 표준화만, 호출량 log1p를 비교한다.
6. 그 후 contamination을 바꿔 경보 수와 제외되는 후보를 확인한다. 점수는 공격 확률이 아니다.

제출: 두 방법 공통 후보 1개, 차이가 나는 후보 1개, 차이를 설명할 특징과 원시 확인 사항. 특징값이 다르다는 관찰과 모델 내부 기여도를 정확히 설명했다는 주장은 구분한다.

## 과제 D. 원시 이벤트 조사

선택 후보를 시간순으로 펼친 뒤 다음을 확인한다.

- UTC/KST를 맞춘 시각과 앞뒤 시간창.
- 호출 주체의 ARN·유형과 출발지별 행위.
- 민감 호출의 오류 코드와 후속 변경 기록.
- 전체 호출 수와 특정 서비스의 호출 수 차이.
- 정상 배포·배치·권한 점검이라는 설명을 뒷받침하거나 약화하는 증거.
- 현재 자료로 확인할 수 없는 대상·정책·세션·MFA·데이터 범위.

오류 코드가 없는 기록은 현재 CSV에서 성공을 시사하는 표기로 사용할 수 있으나, 응답·변경 대상·적용 상태 확인이 필요한 경우를 명시한다. API 이름만으로 유효 권한 상승이나 데이터 유출 완료를 단정하지 않는다.

제출: 원시 CSV의 행 위치 또는 정확한 시각·주체·이벤트 조합을 포함한 근거 3개 이상. “추가 확인 필요”는 합리적인 결과이며 어떤 자료가 필요한지도 적는다.

## 과제 E. 헌팅 결과서와 동료 검토

| 항목 | 작성 내용 |
|---|---|
| 조사 질문 | 무엇을 확인하려 했는가 |
| 범위 | 사용자·시간창·로그 소스 |
| 후보 선정 이유 | 규칙 또는 모델 결과와 특징값 |
| 관찰 사실 | 원시 이벤트와 정확한 근거 위치 |
| 해석 | 관찰이 어떤 가설을 지지하는가 |
| 정상 설명 | 같은 기록이 정상 업무로 발생할 가능성 |
| 미확인 사항 | 대상·성공 결과·영향을 확인할 추가 필드·자료 |
| 우선순위 | 왜 지금 더 조사해야 하는가 |
| 후속 조치 제안 | 증거 보존, 대상 식별, 업무 영향 확인, 필요한 격리·회수 검토 |
| 탐지 개선 | 어떤 신호·맥락을 더 수집하거나 비교할 것인가 |

동료는 보고서에서 근거가 없는 문장 하나와 빠진 대안 설명 하나를 찾아 피드백한다. 작성자는 문장을 수정하거나 추가 근거로 답한다. 실제 키·세션·정책 변경은 이 분석 실습의 수행 범위가 아니다.

정밀도·재현율은 강사가 라벨을 공개할 때 선택적으로 다루는 종료 확장이다. 학생 ZIP에는 라벨이 없으며 이를 기다릴 필요 없이 모든 필수 과제를 마친다. 라벨은 합성 시나리오의 생성 의도이며, 로그만으로 모든 공격 결과를 입증할 수 있다는 의미는 아니다. 속도나 정답 이름 개수보다 근거의 정확성과 판단의 수정 과정을 평가한다.


## 노트북과 연결

과제 A는 B1 및 가설 작성, B는 M3·B2·A1·A4, C는 M4·B2, D는 M5~M6·A2~A3, E는 최종 보고서에 대응합니다. 아래 조건을 직접 구현하는 A1~A4 네 과제의 입출력·힌트·검증 예시는 노트북 안에 모두 있습니다.

| 심화 | 직접 작성하는 분석 규칙 | 확인할 해석 |
|---|---|---|
| A1 | 주체·시각·리전·오류율·민감 호출을 함께 사용한 좁은 예외 | 같은 계정의 다른 활동도 무조건 제외되는가 |
| A2 | IAM List/Get 조회의 시간창별 거부율·거부 종류 | 모든 API를 분모로 쓸 때와 무엇이 다른가 |
| A3 | 같은 주체·IP의 실패→후속 호출을 제한된 시간으로 결합 | 시각 연결만으로 같은 키의 성공을 증명할 수 있는가 |
| A4 | 모델·규칙 조건과 중요 계정 정책을 OR로 결합 | 모델이 빠뜨린 업무상 중요 활동을 어떻게 보완하는가 |

M4의 raw 0.01과 log 0.005 모델은 조사 후보를 좁히는 예시로 두 조건이 다릅니다. 변환만의 효과는 B2에서 세 모델의 contamination을 0.01로 맞추어 비교합니다. B2는 M4/A4의 기존 기준 모델을 덮어쓰지 않습니다. 같은 수치 설정에서도 패키지 버전과 동점 처리에 따라 후보 수·순위가 달라질 수 있으므로 실행 환경과 비교 조건을 기록합니다.
