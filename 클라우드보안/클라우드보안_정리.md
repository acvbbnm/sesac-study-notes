## DAY 1 — AWS 클라우드 인프라와 IAM 보안

### 1. 클라우드 컴퓨팅 기초

**클라우드 서비스 모델 (관리 책임 범위 순서)**

| 모델 | 설명 | 예시 |
|------|------|------|
| IaaS | 인프라(서버/네트워크) 제공 | EC2, S3 |
| CaaS | 컨테이너 관리 환경 제공 | EKS, ECS |
| PaaS | 개발 플랫폼 제공 | Elastic Beanstalk |
| FaaS | 함수 단위 실행 환경 | Lambda |
| SaaS | 완성된 소프트웨어 제공 | Gmail, Slack |

**책임 공유 모델 (Shared Responsibility Model)**
- **AWS 책임**: Security **OF** the Cloud (물리적 인프라, 하드웨어, 네트워크)
- **사용자 책임**: Security **IN** the Cloud (데이터, IAM, 애플리케이션 설정)

### 2. AWS 글로벌 인프라

- **Region**: 38개 (지리적으로 분리된 데이터센터 집합)
- **Availability Zone (AZ)**: 120개 (Region 내 독립 데이터센터)
- **Edge Location**: CDN/Route53 등 엣지 서비스 거점

### 3. IAM (Identity and Access Management)

**IAM 주체 유형**

| 유형 | 자격증명 | 특징 |
|------|----------|------|
| Root 사용자 | 장기(영구) | 모든 권한 보유, 일상 사용 금지 |
| IAM User | 장기(Access Key) | 개인/서비스 계정 |
| IAM Role | 임시(STS) | EC2, Lambda 등에 부여, 자격증명 자동 갱신 |

**IAM Policy 구조**

```json
{
  "Effect": "Allow | Deny",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*",
  "Condition": { "StringEquals": { "aws:RequestedRegion": "ap-northeast-2" } }
}
```

**정책 평가 우선순위**
1. Implicit Deny (기본 거부) — 명시 없으면 거부
2. Explicit Allow (명시적 허용)
3. Explicit Deny (명시적 거부) — 최우선 적용

**ARN (Amazon Resource Name) 구조**
```
arn:partition:service:region:account-id:resource-id
예) arn:aws:iam::123456789012:user/alice
```

### 4. AWS Well-Architected Framework 6원칙

1. **운영 우수성** — 운영 자동화, 지속적 개선
2. **보안** — IAM, 암호화, 탐지, 대응
3. **신뢰성** — 장애 복구, 수평 확장
4. **성능 효율성** — 적절한 리소스 선택
5. **비용 최적화** — 불필요한 지출 제거
6. **지속 가능성** — 에너지 효율 고려

### 5. S3 보안

- **내구성**: 99.999999999% (11 Nine)
- **Bucket Policy**: 버킷 단위 리소스 기반 정책
- **Public Access Block**: 퍼블릭 접근 4가지 차단 설정
- **ACL**: 객체/버킷 수준 접근 제어 (레거시, 가급적 미사용)
- **S3 공개 설정 진단 방법**:
  - 소스코드 점검 (하드코딩된 URL 확인)
  - DNS 쿼리: `dig`, `nslookup`, `host`
  - AWS CLI: `aws s3 ls s3://[bucketname]/ --no-sign-request --region us-west-1`

## DAY 2 — 네트워크 보안과 AWS 취약점 진단

### 1. VPC 네트워크 구성

| 구성요소 | 역할 | 물리 대응 |
|----------|------|-----------|
| EC2 | 가상 서버 | 서버 |
| ENI | 가상 네트워크 인터페이스 | NIC |
| Subnet | IP 범위 구분 | VLAN |
| AZ | 가용 영역 | 존(Zone) |

### 2. AWS 네트워크 보안 서비스

| 서비스 | 적용 레벨 | 특징 |
|--------|-----------|------|
| Security Group | 인스턴스(EC2) | Stateful, Allow 규칙만 존재 |
| NACL | 서브넷 | Stateless, Allow/Deny 모두 존재 |
| WAF | 웹 애플리케이션 | HTTP/HTTPS L7 필터링, SQL Injection/XSS 차단 |
| Shield | AWS 인프라 전체 | DDoS 방어 (Standard: 무료, Advanced: 유료) |

### 3. AWS Security Hub 통합 서비스

- **Inspector**: EC2/컨테이너 취약점 스캔 (CVE 기반)
- **GuardDuty**: 위협 탐지 (머신러닝, CloudTrail/VPC Flow Logs 분석)
- **Macie**: S3 내 민감 데이터(PII) 자동 탐지
- **Config**: 리소스 구성 변경 이력 추적 및 컴플라이언스
- **Firewall Manager**: 다중 계정 WAF/SG 중앙 관리
- **IAM Access Analyzer**: 외부 공개된 리소스 접근 경로 분석

### 4. SSRF (Server-Side Request Forgery)

**공격 흐름**
```
공격자 → 취약한 웹 앱 → EC2 메타데이터(169.254.169.254) → IAM 자격증명 탈취
```

**메타데이터 SSRF 탈취 명령**
```bash
# IAM Role 확인
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/

# 임시 자격증명 탈취
curl http://169.254.169.254/latest/meta-data/iam/security-credentials/[role-name]
```

**대응 방법**
```bash
# IMDSv2 강제 적용 (토큰 기반 메타데이터 접근)
aws ec2 modify-instance-metadata-options \
  --instance-id [id] \
  --http-tokens required \
  --http-endpoint enabled

# 메타데이터 엔드포인트 비활성화
aws ec2 modify-instance-metadata-options \
  --instance-id [id] \
  --http-endpoint disabled
```

**Capital One 사건 (2019)**
- SSRF → EC2 메타데이터 → IAM Role 자격증명 탈취 → S3 버킷 데이터 1억 건 유출

## DAY 3 — 클라우드 로그 분석과 AI 이상 탐지

### 1. 클라우드 로그 유형

| 로그 | 수집 대상 | 활성화 |
|------|-----------|--------|
| CloudTrail | AWS API 호출 (계정 행위 전체) | 기본 활성화 (관리 이벤트) |
| CloudWatch Logs | 애플리케이션, OS, Lambda | 별도 설정 필요 |
| VPC Flow Logs | 네트워크 흐름 (허용/거부 트래픽) | 별도 설정 필요 |
| S3 Access Logs | S3 버킷 접근 기록 | 별도 설정 필요 |

**CloudTrail 이벤트 유형**
- **관리 이벤트**: IAM 변경, EC2 생성 등 — 기본 활성화
- **데이터 이벤트**: S3 객체 읽기/쓰기, Lambda 실행 — 별도 설정
- **인사이트 이벤트**: 비정상 API 호출 패턴 자동 탐지
- **네트워크 활동**: VPC 엔드포인트 활동

**CloudTrail 이벤트 예시**
```json
{
  "eventTime": "2026-03-28T05:12:44Z",
  "eventSource": "iam.amazonaws.com",
  "eventName": "CreateAccessKey",
  "userIdentity": { "type": "Root" },
  "sourceIPAddress": "203.0.113.10",
  "requestParameters": { "userName": "dev-user" }
}
```

### 2. 로그 보안 필수 요소

| 요소 | 구현 방법 |
|------|-----------|
| 보존 기간 | S3 Lifecycle 정책 (장기 보관) |
| 암호화 | SSE-KMS (고객 관리 키) |
| 접근 권한 | S3 Bucket Policy, IAM 최소 권한 |
| 무결성 | CloudTrail Log File Validation |
| 기밀성 | S3 Public Access Block |

**장기 보존 아키텍처**
```
CloudTrail → S3 + Object Lock + KMS + Lifecycle
                              ↓
                    CloudWatch Metric Filter → Alarm → SNS
```

### 3. 탐지 규칙 설계 공식

```
위험 행위 → 로그 필드 매핑 → 필터 조건 → 임계값 → 알림/대응
```

**Logs Insights 기본 쿼리**
```
fields @timestamp, eventName, userIdentity.arn, sourceIPAddress
| filter eventSource = "iam.amazonaws.com"
| stats count(*) as calls by userIdentity.arn, sourceIPAddress
| sort calls desc
| limit 20
```

**헌팅 룰 예시**

| 룰 | 쿼리 | 판단 기준 |
|----|------|-----------|
| Root 로그인 추적 | `filter eventName = "ConsoleLogin" and userIdentity.type = "Root"` | Root 로그인은 평소 0건 |
| 비정상 리전/IP 접근 | `stats count(*) by awsRegion, sourceIPAddress` | 미사용 리전, 낯선 IP |
| 권한 상승 흐름 추적 | `filter eventName like /Attach\|Put\|CreatePolicy\|PassRole/` | AdministratorAccess·PassRole 부여 |

**Metric Filter → Alarm → SNS 파이프라인**
```
CloudWatch Logs → Metric Filter (패턴 매칭) → CloudWatch Alarm → SNS → 이메일/Lambda
```

### 4. AI 기반 이상 탐지

**규칙 기반 vs AI 탐지 비교**

| 구분 | 규칙 기반 | AI 이상 탐지 |
|------|-----------|--------------|
| 판단 기준 | 사전 정의 조건·임계값 | 정상 패턴(Baseline)과의 거리 |
| 장점 | 설명 가능, 즉시 적용 | 알려지지 않은 패턴 탐지 |
| 한계 | 조건 밖 행위 미탐 | 오탐 가능, 결과 해석 필요 |
| 운영 방식 | 중요 이벤트 즉시 경보 | 우선순위 선별과 추가 조사 |

**Isolation Forest 개념**
- **비지도학습** 기반 이상치 탐지 모델 (라벨 없는 로그에 적용 가능)
- 처리 흐름: `로그 집계 → 특징값 생성 → 무작위 분할 → 고립 거리 계산 → 이상 점수`
- 모델 결과는 "**조사 우선순위**"이지, 침해 확정 근거가 아님

**AI 탐지 주요 특징값**

| 특징값 | 정상 범위 | 이상 후보 |
|--------|-----------|-----------|
| api_call_count | 평소 10회 내외 | 300회 |
| error_rate | 대부분 성공 | AccessDenied 비율 높음 |
| unique_services | 소수 서비스 | IAM·S3·EC2·KMS 동시 접근 |
| unique_regions | 서울 리전만 | 다수 리전 호출 |
| night_activity | 업무 시간 내 | 심야 권한 변경 및 키 생성 |
| sensitive_api_count | 거의 없음 | CreateAccessKey, AttachPolicy 증가 |

**AI 탐지 모델 비교**

| 모델 | 적합한 탐지 규칙 |
|------|-----------------|
| Isolation Forest | 여러 지표가 동시에 평소 범위를 벗어난 계정 |
| One-Class SVM | 활동 일정한 서비스/배치 계정의 이탈 감시 |
| LOF (밀도 기반) | 팀·역할별 사용량이 다른 환경의 개별 이탈 |
| K-Means 군집 | 사용자 유형 분류 후 유형별 기준선 생성 |
| Random Forest | 이미 알려진 공격 패턴 재탐지, 사후 분류 |

**적용 원칙**
- **규칙 우선**: 조건·임계값을 사전에 정의할 수 있는 이벤트 (root 로그인, 민감 API)
- **모델 우선**: 절대 기준 없이 평소 대비 변화로 판단하는 지표 (호출량, 리전 수)
- **공통 원칙**: 오탐·미탐은 두 방식 모두 존재하므로 원본 로그로 최종 확인

**사고 대응 보고서 구성**

| 항목 | 내용 |
|------|------|
| 탐지 요약 | 누가, 언제, 어디서, 어떤 API를 호출했는지 |
| 탐지 근거 | 규칙 탐지 조건 또는 AI 이상 점수와 주요 특징값 |
| 영향도 | 권한 변경, 데이터 접근, 자격 증명 노출 가능성 |
| 초기 대응 | 키 비활성화, 세션 종료, 권한 회수, 사용자 확인 |
| 재발 방지 | MFA, 최소 권한, 조건 기반 정책, 로그 경보 개선 |

## DAY 4 — 제로트러스트 & 클라우드 네이티브 보안

### 1. Zero Trust 개념

> **"아무것도 믿지 말고 항상 검증하라"**  
> 인증되지 않은 것은 믿지 말고, 인증된 것도 반복해서 인증하라

**제로트러스트 3원칙**
1. **침해를 가정하라** — 방화벽 내부도 신뢰하지 않음
2. **명시적으로 검증하라** — 위치가 아닌 데이터 포인트 기반 접근 승인
3. **최소 권한을 자동화하라** — CIEM과 IaC를 통해 지속적 축소

**NIST SP 800-207 제로트러스트 7가지 기본 원리**
1. 모든 데이터 소스와 컴퓨팅 서비스는 리소스(보호대상)로 간주
2. 네트워크 위치(내/외부)에 관계없이 모든 통신 보호
3. 기업 리소스에 대한 접근을 세션 단위로 승인(검증)
4. 동적 정책으로 리소스에 대한 접근 결정
5. 모든 자산의 무결성 및 보안 상태를 모니터링하고 측정
6. 모든 리소스의 인증/인가를 강력하게 점검한 후 허용
7. 자산, 네트워크, 인프라 등 현 상태에 대한 정보 수집 후 개선

**제로트러스트 아키텍처 핵심 구성**
- **PDP** (Policy Decision Point): 접근 허용 여부 결정
- **PEP** (Policy Enforcement Point): 접근 제어 실행
- **PIP** (Policy Information Point): 신뢰도 판단용 데이터 제공

**제로트러스트 성숙도 4단계** (CISA ZTMM v2.0 기반)

| 단계 | 특징 |
|------|------|
| 1. 기존 단계 | 수동 정책, 경계 기반 보안 위주 |
| 2. 초기 단계 | 일부 자동화, 기본 모니터링 |
| 3. 향상 단계 | 자동화 확장, 중앙 집중식 제어 |
| 4. 최적화 단계 | 완전 자동화, 동적 정책, 속성 기반 최소 권한 |

### 2. 클라우드 네이티브 보안

**보안 패러다임 전환**

| Traditional Security | Cloud Security |
|---------------------|----------------|
| Focus on "Manage" | Focus on "Change" |
| Network Security | ZeroTrust |
| Focus on "Production" | Focus on "Shift Left" |
| 단일 보안 기술 | Cross functional skill set |
| Threat Detection | Threat anticipation and resolution |

**클라우드 네이티브 보안 핵심 기술**

| 기술 | 설명 |
|------|------|
| CNAPP | Cloud Native Application Protection Platform — CSPM+CIEM+CWPP 통합 |
| CSPM | Cloud Security Posture Management — 클라우드 보안 형상 관리 |
| CWPP | Cloud Workload Protection Platform — 클라우드 워크로드 보안 |
| CIEM | Cloud Infrastructure Entitlement Management — 권한 부여 관리 |
| SECaaS | Security as a Service — 서비스형 보안 |
| DevSecOps | 개발·보안·운영 통합, 파이프라인에 보안 검사 자동화 |
| Container Security | 이미지 스캔, Secrets 보호, 런타임 보호, 구성 오류 점검 |
| SASE | Secure Access Service Edge — ZeroTrust + 네트워크 보안 통합 |

**CNAPP 구성 요소**

| 구성 | 역할 |
|------|------|
| CSPM | 클라우드 자산 현황 시각화, 컴플라이언스 취약점 진단, 구성 오류 탐지 |
| CWPP | 이미지 스캔(CVE/Malware), Secrets 보호, 런타임 모니터링, 컨테이너 네트워크 보호 |
| CNAPP | CSPM+CIEM+CWPP 통합, 실시간 모니터링, Attack Path 분석, 자동화 대응 |

**CI/CD 파이프라인 보안 위협**
- 자동화된 파이프라인 특성상 한 번의 침해가 전 구간으로 확산
- 단계별 보안 검증 6요소:
  1. 이미지 스캔 (Registry 내 CVE/Malware)
  2. Secrets 보호 (API키, 비밀번호 노출 방지)
  3. 이미지 서명 및 검증 (빌드 시 서명, 검증 기준 충족)
  4. 런타임 보호 (검증 기준 미충족 이미지 실행 차단)
  5. 컨테이너 네트워크 보호 (트래픽 모니터링, 접근 제어)
  6. 컨테이너 구성 오류 점검 (CIS Kubernetes Benchmark)

**클라우드 네이티브 보안 아키텍처 (SIEM 연계)**
```
CSPM ─┐
CIEM ─┼─→ SIEM (Cloud Security Manager) → 이메일/SNS 알림
CWPP ─┘
```
- SIEM 한계: 온프레미스 기준 룰과 이벤트 모델로 클라우드 가시성 부족
- 해결: 클라우드 행위 로그, 네이티브 이벤트를 Syslog로 SIEM 연동

### 3. 클라우드 보안 인력 요구 역량

1. **보안 기술 역량** — 취약점 분석, 사고 대응
2. **클라우드 기술 역량** — AWS/Azure/GCP 서비스 이해
3. **개발 역량** — 보안 자동화, IaC, DevSecOps
