1. 악성코드 개요

**악성코드(Malware)** : 악의적 사용자가 컴퓨터 시스템이 위험한 행동을 하도록 조작하기 위해 사용하는 코드의 통칭. 결과는 흔히 **데이터 손상 · 비공개 정보 도난 · 몸값 요구(Ransom) · 무허가 자원 소모 · 서비스 거부**로 이어집니다.

악성코드의 8가지 분류

| **유형** | **핵심 특징** |
|----|----|
| Worm(웜) | 사용자 동작 없이 **자가 복제·전파** (네트워크로 확산) |
| Trojan(트로이 목마) | 정상 파일로 **위장**, 설치되면 원격 접근 권한 부여 |
| Adware(애드웨어) | 원치 않는 **광고 표시**, 속도 저하·대역폭 소비 |
| Spyware(스파이웨어) | 은밀히 **정보 수집**(인증정보·카드번호), 브라우저 하이재킹 |
| Ransomware(랜섬웨어) | 파일을 **암호화** 후 해독 대가로 몸값 요구 |
| Keylogger(키로거) | **키 입력 기록** 후 공격자에게 전송 |
| Rootkit(루트킷) | **커널 레벨** 접근 권한 획득, 제거 매우 어려움 |
| Miner(마이너) | 허가 없이 **암호화폐 채굴**, 자원 소모 |

주요 역사 (History)

| **시기** | **사건**      | **의미**                                   |
|----------|---------------|--------------------------------------------|
| 1983     | Creeper       | 최초로 알려진 **컴퓨터 웜**(ARPANET)       |
| 1986     | Brain         | **최초의 IBM PC 바이러스**(플로피 전파)    |
| 1988     | Morris Worm   | 인터넷 자동 전파 최초 웜, 약 6,000대 감염  |
| 1999     | Melissa · CIH | 이메일 매크로 웜 / BIOS 손상               |
| 2000     | ILOVEYOU      | VBS 스크립트 이메일, 약 5억 달러 피해      |
| 2003     | SQL Slammer   | MS SQL 취약점, 대규모 인터넷 마비          |
| 2019     | GandCrab      | 랜섬웨어(약 2조 3천억원 수익 후 은퇴 선언) |

> **💡 바이러스 vs 웜 vs 트로이**
> **웜은 사용자 동작 없이 스스로 전파**되고, 바이러스는 숙주 파일에 기생해 실행될 때 퍼지며, **트로이 목마는 정상 프로그램으로 위장**해 사용자가 직접 실행하게 유도합니다. 감염 경로는 크게 취약점 공격(Injection)과 사람을 속이는 사회공학(Social Engineering)으로 나뉩니다.

2. 리버싱과 분석 기법

**리버스 엔지니어링(리버싱)** : 실행 파일을 역으로 분석해 동작 원리를 파악하는 것. 악성코드 분석의 핵심 기법입니다.

정적 분석 vs 동적 분석

| **구분** | **정적 분석**                    | **동적 분석**                |
|----------|----------------------------------|------------------------------|
| 방법     | **실행하지 않고** 파일 구조 분석 | **실행시켜** 디버거로 관찰   |
| 대상     | 헤더·코드 영역·데이터 영역       | 메모리·레지스터 등 실행 상태 |
| 도구     | 디스어셈블러(IDA 등)             | 디버거(x64dbg/OllyDbg 등)    |
| 장단     | 안전하지만 정보 제한             | 실제 동작 확인, 감염 위험    |

어셈블리 기초 (Hello Reversing)

| **명령어**    | **동작**                                             |
|---------------|------------------------------------------------------|
| JMP [ADDR]  | 해당 주소로 **EIP 변경**(분기)                       |
| PUSH [REG]  | REG 값을 **스택에 저장**                             |
| POP [REG]   | 스택에서 값을 빼서 **REG에 저장**                    |
| CALL [ADDR] | 현재 EIP를 스택에 PUSH 후 주소로 EIP 변경(함수 호출) |
| RETN          | 스택의 값을 빼서 EIP 변경(호출한 곳으로 복귀)        |

> **💡 EIP = 다음 실행 명령의 주소**
> **EIP(Instruction Pointer)**는 CPU가 다음에 실행할 명령의 주소를 가리킵니다. 리버싱은 이 EIP 흐름과 스택(PUSH/POP)을 추적하는 일이며, **CALL은 복귀 주소를 스택에 저장하고 RETN이 그것을 꺼내 돌아오는** 짝 구조가 함수 호출의 핵심입니다. 예: 두 문자열을 비교해 같으면 MessageBox, 다르면 exit(0).

3. 레지스터 · 메모리 · 스택 프레임

프로그램 실행 시 CPU는 **레지스터**에 값을 담아 연산하고, 함수 호출마다 스택에 **스택 프레임**을 쌓습니다.

호출 규약 (Calling Convention)

| **규약** | **인자 전달·스택 정리** |
|----|----|
| cdecl | 인자를 **오른쪽→왼쪽** 스택 전달, **호출자(caller)가 스택 정리** |
| stdcall | 인자를 오른쪽→왼쪽 전달, **피호출자(callee)가 스택 정리** (Win32 API 기본) |

> **💡 스택 프레임으로 함수 경계를 읽는다**
> 함수가 호출되면 **복귀 주소 → 이전 EBP 저장 → 지역 변수 공간 확보** 순으로 스택 프레임이 만들어집니다. cdecl·stdcall의 차이(누가 스택을 정리하는가)를 알면 디스어셈블 코드에서 함수의 시작·끝과 인자 개수를 읽어낼 수 있습니다. (실습 예: Stack Frame.exe, cdecl.exe, stdcall.exe)

4. PE 파일 구조 (PE Format)

**PE(Portable Executable)** : Windows에서 사용되는 실행 파일 형식. Process·Memory·DLL 등 Windows 핵심 개념과 연결됩니다.

- **실행 파일 계열** : EXE, SCR

- **라이브러리 계열** : DLL, OCX

- **드라이버 계열** : SYS / **오브젝트 파일** : OBJ

NT Header 주요 필드

| **필드**            | **의미**                                      |
|---------------------|-----------------------------------------------|
| Magic               | 32bit면 10Bh, 64bit면 20Bh                    |
| AddressOfEntryPoint | **EP(최초 실행 코드)의 RVA 주소** — 매우 중요 |
| ImageBase           | PE 파일이 메모리에 매핑되는 시작 주소         |
| SectionAlignment    | **메모리**에서 섹션의 최소 단위               |
| FileAlignment       | **파일**에서 섹션의 최소 단위                 |

**IAT(Import Address Table)** : PE가 사용하는 외부 DLL 함수들의 실제 주소가 기록되는 테이블. PE 로더가 **GetProcAddress**로 함수 주소를 찾아 IAT에 기록합니다(Import Lookup Table의 Hint/Name으로 함수 식별).

> **💡 EntryPoint와 IAT가 분석의 출발점**
> **AddressOfEntryPoint**는 프로그램이 최초로 실행되는 코드 주소라 분석의 시작점이고, **IAT**를 보면 이 파일이 어떤 API(네트워크·파일·레지스트리 등)를 쓰는지 파악돼 악성 행위를 추정할 수 있습니다. **Code Cave**는 실행 파일의 빈 공간에 코드를 삽입해 실행 흐름을 가로채는 기법입니다.

5. 런타임 패커 (Run-Time Packer)

**런타임 패커** : 실행 파일을 압축·암호화해 원본 코드를 숨기는 도구(대표적으로 **UPX**). 악성코드가 백신 탐지와 정적 분석을 회피하려고 자주 사용합니다.

- 실행 시 메모리에서 스스로 압축을 풀고(unpack) 원본 코드를 복원한 뒤 실행

- 분석하려면 압축이 풀린 시점의 **OEP(Original Entry Point)**를 찾아 덤프하고 **IAT를 복원**

> **💡 언패킹의 목표: OEP + IAT 복원**
> 패킹된 파일은 겉코드만 보여 정적 분석이 막힙니다. 디버거로 실행하며 언패킹 루틴이 끝나고 **원본 진입점(OEP)**으로 점프하는 순간을 잡아 메모리를 덤프하고, 깨진 **IAT를 복원**하면 원본에 가까운 분석 대상이 됩니다. UPX는 upx -d로 간단히 풀리지만, 변형 패커는 수동 언패킹이 필요합니다.

6. 안티 디버깅 (Anti-Debugging)

**안티 디버깅** : 악성코드가 **자신이 디버거로 분석되고 있는지 탐지**해 동작을 바꾸거나 종료하는 기법. 분석가는 이를 우회(bypass)해야 합니다.

> 안티 디버깅은 결국 **디버깅 흔적(플래그·DebugPort·실행 지연)**을 확인하는 것입니다. 분석가는 해당 플래그를 0으로 패치하거나 API 리턴값을 조작해 우회합니다. rdtsc처럼 시간을 재는 기법은 모든 안티디버깅을 적용하기 전에 시작 시간을 저장해 두고, 나중에 경과 시간이 비정상적으로 크면 디버깅 중으로 판단합니다.

7. 분석 도구와 실전 분석

주요 분석 도구

| **도구** | **용도** |
|----|----|
| IDA (Free) | **디스어셈블러** — 정적 분석의 표준 |
| x64dbg / OllyDbg | **디버거** — 동적 분석(메모리·레지스터 추적) |
| Process Monitor | 실행 중 **레지스트리·파일·네트워크·스레드** 행위 관찰(Sysinternals) |
| Packet Storm 등 | 악성코드 **샘플 수집** 저장소 |

**실전 분석 흐름** : ① 샘플 확보 → ② 정적 분석(PE 헤더·IAT·문자열) → ③ 필요 시 언패킹 → ④ 동적 분석(Process Monitor로 행위 관찰, 디버거로 코드 추적) → ⑤ 안티디버깅 우회 → ⑥ 핵심 로직·통신(C2) 파악.

실습 예: 취약점 샘플(VLC 0.9.3, CVE-2008-4654), 랜섬웨어 샘플 분석 시 **현재 작동 가능 여부 · Kill Switch · 복호화 가능성** 등을 점검.

> **💡 동적 분석은 반드시 격리 환경에서**
> 실제 악성 샘플을 실행하는 동적 분석은 **가상머신·격리 네트워크(샌드박스)**에서만 수행해야 합니다. Process Monitor로 파일·레지스트리·네트워크 변화를 기록하면 악성 행위의 흔적(IOC)을 빠르게 파악할 수 있습니다. WannaCry처럼 특정 도메인 접속 여부로 동작을 멈추는 **Kill Switch**가 있는 경우도 있어 통신 로직 분석이 중요합니다.

> **💡 전체 요약**
> 악성코드는 **유형·역사**를 알고, **리버싱(정적·동적)**으로 분석한다. 분석의 기반은 **어셈블리·레지스터·스택 프레임·PE 구조(EP·IAT)**이며, 악성코드는 **패커·안티디버깅**으로 분석을 방해하므로 언패킹·우회 기술이 필요하다. 실전은 **격리 환경에서 도구(IDA·디버거·Process Monitor)**로 행위와 통신을 파악하는 것으로 마무리된다.
