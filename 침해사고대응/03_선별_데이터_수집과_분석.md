# 03. 선별 데이터 수집과 분석

출처: 로컬 `LECTURE NOTES/(PLB#3) 선별 데이터 수집과 분석.pdf`, 41쪽.

## 1. 선별 수집의 목적 (p.4-13)

전체 이미징에 필요한 시간·용량·운영 영향을 줄이면서 공격자의 행위를 설명할 자료를 확보한다. 서비스 중단이 어려운 서버에서 유용하지만, 미수집 영역이나 삭제 데이터가 필요하면 전체 이미징을 추가 검토한다. 선별 수집을 했다는 사실만으로 전체 사고를 설명할 수 있는 것은 아니다.

| 조사 목적 | 주요 아티팩트 | 확인할 내용 |
|---|---|---|
| 실행 | Prefetch, Amcache, UserAssist·BAM 등 레지스트리, 이벤트, WER | 프로그램·명령 실행 흔적 |
| 지속 | Run·서비스·TaskCache, 예약 작업, WMI, BITS | 재실행·접근 유지 방법 |
| 유입 | 브라우저, Zone ID, 메일, 원격 접속·로그온, 웹 로그 | 다운로드·접속·최초 진입 |
| 전파 | 보안·TerminalServices·PowerShell 이벤트, 공유·원격 서비스 | 다른 호스트 접근 |
| 행위 흐름 | MFT, LogFile, USN, LNK·Jumplist, SRUM | 파일 변경·접근·자원 사용의 시간 관계 |

아티팩트 해석은 의미를 구별해야 한다. 파일이 존재했다는 증거, 실행 흔적, 사용자 접근 흔적은 서로 다르다. Amcache 항목 하나나 LNK 하나로 모든 실행 사실을 확정하지 않고 다른 자료와 대조한다.

## 2. KAPE 구조 (p.15-30)

| 구성 | 역할 |
|---|---|
| `gkape.exe` / `kape.exe` | GUI / CLI 실행 프로그램 |
| `Targets/*.tkape` | 무엇을 수집할지 정의 |
| `Modules/*.mkape` | 어떤 도구와 옵션으로 처리할지 정의 |
| `Modules/bin/` | 처리에 사용하는 실행 도구 |
| `_kape.cli` | 교안에서 설명하는 배치 실행 설정 |

**Target은 수집, Module은 처리**가 핵심 구분이다. Target은 경로·재귀 여부·디렉터리 재생성과 다른 Target 참조를 정의한다. Module은 실행 파일·명령행·출력 형식을 정의한다. Module 파일이 있어도 필요한 써드파티 바이너리가 없으면 처리되지 않는다.

주요 Target 필드는 `Description`, `Targets`, `Name`, `Category`, `Path`, `IsDirectory`, `Recursive`, `AlwaysAddToQueue`다. `AlwaysAddToQueue`는 존재 확인과 큐 등록 방식을 바꾸는 설정이다. 교안은 파일시스템 메타데이터, Chrome, 통합 Target 예시로 구성 방법을 설명한다.

주요 Module 필드는 `Processors`, `Executable`, `CommandLine`, `ExportFormat`이다. `%sourceDirectory%`와 `%destinationDirectory%`로 입력과 출력을 연결한다. LECmd 예시에서는 LNK를 CSV·HTML 등으로 내보낸다.

## 3. 실습 A: Target 작성과 선별 수집 (p.32-34)

1. 실행·지속·유입·전파 확인에 필요한 자료를 고른다.
2. 배포된 Target 정의를 참고해 실습용 `.tkape`를 작성한다.
3. 원본 경로, 새 수집 폴더, 처리 결과 폴더를 구분한다.
4. GUI 또는 CLI에서 Target을 선택해 수집한다.
5. 수집 로그와 파일 목록을 확인하고 누락·오류를 기록한다.
6. 필요한 Module만 선택해 처리하고 생성된 CSV를 확인한다.

교안 명령의 주요 옵션:

| 옵션 | 의미 |
|---|---|
| `--tsource` | 수집 원본 |
| `--tdest` | 수집 결과 저장 위치 |
| `--target` | 적용할 Target |
| `--vss` | 볼륨 섀도 복사본 수집 |
| `--vhdx` | VHDX 컨테이너 이름 |
| `--tflush` | 수집 전에 대상 출력 폴더를 비우는 옵션 |

교안에는 `--tflush` 예시가 있지만 기존 결과 보존이 필요하면 그대로 복사하지 않는다. 원본과 출력이 겹치지 않는 새 디렉터리를 사용하는 편이 명확하다. 설치 버전의 Target 이름과 옵션을 확인한 후 실행한다.

## 4. artifactcollector (p.35-38)

교안은 파일·디렉터리·레지스트리·명령 출력·WMI 등을 수집하는 다른 방법으로 artifactcollector를 소개한다. YAML 정의와 포함 바이너리로 수집 범위를 확장하며, 교안의 결과 형식은 SQLite 기반 `.forensicstore`와 로그다. 로컬에 해당 수집 결과가 있다는 근거는 이번 확인에서 확보하지 않았다.

## 5. 실습 B: 아티팩트 분석과 타임라인 (p.40-41)

교안은 전체 시간순 구성 또는 실행 → 지속 → 유입·전파 순서의 분석 후 시간순 결합을 제시한다.

1. 각 결과의 시간대·시간 필드 의미·도구 버전을 기록한다.
2. 실행 후보의 이름·경로·시각을 Prefetch 및 관련 자료에서 찾는다.
3. 같은 경로·이름이 서비스·예약 작업·Run 키에 있는지 확인한다.
4. 다운로드·로그온·원격 접근 흔적으로 유입과 전파를 조사한다.
5. MFT·USN에서 생성·이름 변경·삭제를 대조한다.
6. 시간순 표에 증거 파일과 필드를 붙여 판단 근거를 남긴다.

| 시간(시간대 명시) | 관찰 행위 | 원본/필드 | 해석 | 추가 확인 |
|---|---|---|---|---|
| 실제 분석 후 입력 | 실행·생성·접속 등 | 파일과 레코드 위치 | 근거에 기반한 가설 | 교차 검증 자료 |

이 표는 작성 양식이며 완료된 사고 타임라인이 아니다. 수집 시각, 파일시스템 시각, 이벤트 발생 시각을 같은 의미로 취급하지 않는다.

## 6. 로컬 도구와 데이터 연결

| 로컬 도구 | 연결할 자료 | 목적 |
|---|---|---|
| PECmd | `ARTIFACT/PREFETCH` | Prefetch 처리 |
| AmcacheParser | `ARTIFACT/AMCACHE` | Amcache 처리 |
| RECmd / RegRipper | `ARTIFACT/REGISTRY` | 레지스트리 분석 |
| EvtxECmd | `ARTIFACT/EVENTLOG` | 이벤트 로그 처리 |
| LECmd / JLECmd | `ARTIFACT/LNK`, `JUMPLIST` | 접근 흔적 처리 |
| MFTECmd | `ARTIFACT/METADATA` | 파일시스템 메타데이터 처리 |
| TimelineExplorer | `DATA/MFT.csv` 등 | CSV 필터·시간순 탐색 |

`ARTIFACT`에는 자료가 있고 `DATA/MFT.csv`에는 357,100개 데이터 행이 있다. 다만 전체 도구의 실행 완료, 악성 행위 결론, 최종 타임라인은 별도로 검증되지 않았다.
