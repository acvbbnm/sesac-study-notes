## Session 01 — 웹 기초와 실습 환경 구축

### 학습 목표
- URL, HTTP, HTTPS, Cookie/Session 구조 이해
- Docker로 WebGoat/WebWolf 실습 환경 구축
- Burp Suite 기본 사용법
- CIA Triad와 OWASP Top 10 변천사(2017/2021/2025) 이해

### 웹 프로토콜 핵심
| 구성요소 | 내용 |
|---|---|
| URL 구조 | `scheme://host:port/path?query#fragment` |
| HTTP Request | Request Line + Headers + Body |
| HTTP Response | Status Line + Headers + Body |
| HTTP 특징 | Stateless(무상태) — 그래서 Cookie/Session으로 상태 유지 |
| Status Code | 2xx 성공 / 3xx 리다이렉트 / 4xx 클라이언트 오류 / 5xx 서버 오류 |
| HTTPS | HTTP + TLS/SSL(443), TLS Handshake로 암호화 채널 수립 → 스니핑 방지 |
| Cookie/Session | 로그인 → 서버가 Session 생성 → `Set-Cookie`로 세션ID 발급 → 이후 요청마다 Cookie 동봉 |
| 3-Tier 아키텍처 | Presentation(클라이언트) - Application(WAS) - Data(DBMS) |

### 실습 환경 구축 (Docker)
```bash
docker run -it --name webgoat -p 8080:8080 -p 9090:9090 ubuntu
apt update && apt install -y git vim openjdk-17-jdk
git clone -b v2023.3 https://github.com/WebGoat/WebGoat.git
# application-webgoat.properties: webgoat.host=0.0.0.0
# application-webwolf.properties: webwolf.host=0.0.0.0
./mvnw clean install
./mvnw spring-boot:run
```
- WebGoat: `http://localhost:8080/WebGoat` (취약점 실습)
- WebWolf: `http://localhost:9090/WebWolf` (공격자 서버 역할 — 파일 업로드, 콜백 수신 등)

### Burp Suite
- Community Edition 무료 기능: Proxy, Repeater, Intruder(속도 제한), Scope
- 포트 충돌 시: Burp Proxy Listener를 8888로 바꾸고 WebGoat는 8080 유지
- HTTPS 인터셉트: Burp CA 인증서를 브라우저에 설치해야 함
- 핵심 흐름: Intercept(요청 가로채기) → 수정 → Forward(전달)

### CIA Triad
- **C**onfidentiality(기밀성), **I**ntegrity(무결성), **A**vailability(가용성) — 모든 보안 취약점은 이 셋 중 하나 이상을 침해

## Session 02 — A01 Broken Access Control · A02 Cryptographic Failures

### A01. Broken Access Control (CWE-639, CWE-284, CWE-352)

**Horizontal vs Vertical 권한 상승**
- Horizontal(수평): 같은 등급 내 남의 데이터 접근 (예: 다른 사용자 프로필 조회)
- Vertical(수직): 낮은 권한이 관리자 기능 접근

**IDOR (Insecure Direct Object Reference)**
```
GET /profile?userId=1001   # 내 데이터
GET /profile?userId=1002   # 파라미터만 바꾸면 남의 데이터 조회
```
- 취약 코드 패턴: `userId != null && !userId.equals(authUserId)` → 조건이 반대로 되어 있으면 아무나 통과
- 수정: 세션의 `authUserId`와 요청 `userId`가 **같을 때만** 허용하도록 조건 반전

**Missing Function-Level Access Control**
- 화면(GET)에서는 관리자 버튼을 안 보여주지만, 실제 처리(POST)에서 `isAdmin()` 검사를 안 함
- Burp로 화면에 없는 관리자 API를 직접 호출하면 우회 가능

**Encoding ≠ Security**
- Base64는 암호화가 아니라 인코딩(디코딩하면 바로 원문) — `Cookie: auth=base64(id:pw)` 형태는 사실상 평문

**방어 체크리스트**
- Default Deny(기본 차단), Object별 소유권 검증, Method별 권한 분리, Session 기반 판단(클라이언트 쿠키 신뢰 금지)

### A02. Cryptographic Failures (CWE-259, CWE-327)

**세 가지 구분**
| 구분 | 목적 | 예시 | 되돌리기 |
|---|---|---|---|
| Encoding | 표현 형식 변환 | Base64, URL Encoding | 항상 가능(비밀 아님) |
| Encryption | 기밀성 보호 | AES, RSA | 키 있으면 가능 |
| Hashing | 무결성/검증 | SHA-256, bcrypt | 불가능(단방향) |

**해시 취약점**
- MD5, SHA-1은 충돌(Collision) 취약 — 예: SHAttered(2017, Google이 SHA-1 충돌 실증)
- Rainbow Table 공격: 사전에 계산된 해시-원문 매핑표로 역산
- **대응**: Salt(무작위 값) 추가 후 해시 + bcrypt/Argon2 같은 느린 해시 함수 사용

**대칭키 vs 비대칭키**
- 대칭(AES): 같은 키로 암/복호화, 빠름, 키 배송 문제
- 비대칭(RSA): 공개키로 암호화·개인키로 복호화, 느림, 키 배송 문제 해결
- 하이브리드: 데이터는 대칭키(DEK)로, 그 대칭키는 비대칭키(KEK)로 암호화 — HTTPS/TLS가 이 방식

**기타**
- HTTP Basic Auth = `Base64(id:pw)`를 헤더에 담는 것 → HTTPS 없으면 그대로 노출
- XOR은 대칭 성질(A⊕B⊕B=A)이 있어 단순 스트림 암호의 기본 원리

**체크리스트**: 강력한 알고리즘(AES/RSA/SHA-256↑) 사용, 키 관리(KMS), TLS 1.2 이상 강제

## Session 03 — A03 Injection · A05 Security Misconfiguration

### A03. SQL Injection (CWE-89)

**3가지 유형**
| 유형 | 방식 | 예시 |
|---|---|---|
| String/Numeric | 문자열 결합 쿼리에 `' OR '1'='1` 삽입 | `WHERE id='' OR '1'='1'` → 조건이 항상 참 |
| Chaining/UNION | `;` 또는 `UNION SELECT`로 임의 쿼리·테이블 결합 | `union select userid,password,... from user_system_data--` |
| Blind | 화면에 결과가 안 보여도 참/거짓 반응 차이로 데이터 추출 | Error-based / Time-based / Content-based |

**Blind SQLi 데이터 추출 3단계**: ① 길이 확인(`length(password)<30`) → ② 한 글자씩 substring → ③ `ascii()`로 문자 비교(Burp Intruder로 32~126 브루트포스)

**우회 기법**: 주석(`/**/`)으로 필터 우회, 대소문자 혼용(`seSELECTlect`)으로 블랙리스트 우회, `ORDER BY`절도 Blind SQLi 가능

**방어**: **Prepared Statement**(`?` 바인딩으로 쿼리와 데이터 분리) 또는 ORM의 `#{}` 바인딩(`${}`는 문자열 치환이라 여전히 취약)

### A03. Cross-Site Scripting (CWE-79)

| 유형 | 특징 |
|---|---|
| Reflected | URL 파라미터가 응답 HTML에 그대로 반영 (1회성, 링크 클릭 유도) |
| Stored | DB에 스크립트가 저장되어 조회할 때마다 실행 (가장 위험) |
| DOM-based | 서버 응답과 무관하게 JS가 URL/DOM을 직접 조작해 실행 |

**방어**: HTML Entity 인코딩(`<`→`&lt;` 등), 출력 컨텍스트(HTML/속성/URL/JS)별로 다른 인코딩 적용, Spring `HtmlUtils.htmlEscape()` 등 활용

### A03. Path Traversal (CWE-22)

- `../`로 상위 디렉터리 이동 → `/etc/passwd` 등 임의 파일 접근
- 우회: `....//`, URL 인코딩(`%2e%2e%2f`)으로 블랙리스트 필터 우회
- **Zip Slip**: 압축 해제 시 파일명에 `../`가 있으면 압축 해제 경로 밖에 파일 생성 가능
- **방어**: 단순 문자열 필터(`contains("..")`) 대신 `getCanonicalPath()`/`toRealPath()`로 실제 경로 계산 후 base 경로 안에 있는지 검증

### A05. Security Misconfiguration → XXE (CWE-611, CWE-16)

- XML 파서가 외부 엔티티(External Entity) 참조를 허용하면 로컬 파일 읽기(`file:///`) 또는 SSRF 가능
```xml
<!DOCTYPE webhacking [
<!ENTITY attack SYSTEM "file:///etc/passwd">
]>
```
- **Blind XXE**: 결과가 화면에 안 보이면 외부 DTD + 파라미터 엔티티로 데이터를 공격자 서버(WebWolf)로 유출(exfiltration)
- **방어**: `disallow-doctype-decl=true`, `setXIncludeAware(false)`, External Entity 비활성화

## Session 04 — A07 Authentication · A08 Integrity · A09 Logging · A10 CSRF/SSRF · AI 보안

### A07. Identification and Authentication Failures

**대표 사고 사례**: PayPal 2FA 우회(2016) — 2단계 인증 자체보다 "복구 절차"가 약점이었던 사례

**Host Header 공격**: 비밀번호 재설정 링크를 만들 때 서버가 요청의 `Host` 헤더를 그대로 신뢰하면, 공격자가 Host를 조작해 재설정 링크를 자신의 서버로 유도 가능

**JWT (JSON Web Token)**
```
Header.Payload.Signature   (예: eyJhbGc....eyJzdWI....signature)
```
- Header: 알고리즘 정보 / Payload: Claim(사용자 정보) / Signature: 위변조 방지
- **공격 포인트**
  - `alg: none` 공격 — Signature 검증 자체를 생략시켜 Payload(예: `admin:true`) 위조
  - Weak Secret — HMAC 서명 키가 약하면 오프라인 브루트포스로 Secret 탈취 후 토큰 위조
  - `.parse()` vs `.parseClaimsJws()` — 후자를 안 쓰면 서명 검증이 누락될 수 있음(코드 패치 포인트)
- Session(Stateful, 서버 저장) vs JWT(Stateless, 클라이언트 보관) 비교

**비밀번호 정책**: 최소 10자 이상, 사전 단어·패턴 차단 (`testtest`류는 즉시 크랙, `webhacking123#`류는 훨씬 오래 걸림)

**체크리스트**: 2FA는 Host/Origin 검증까지 포함, Reset 링크는 Base URL 고정 + 짧은 만료 + 1회용 Token

### A08. Software and Data Integrity Failures (CWE-502)

- **역직렬화(Deserialization)** 취약점: `ObjectInputStream.readObject()`가 신뢰할 수 없는 입력을 그대로 객체로 복원하면, 객체의 `readObject()` 안에 숨겨둔 코드가 실행됨 → **RCE**
```java
// 공격 페이로드 생성 측
VulnerableTaskHolder data = new VulnerableTaskHolder("attack", "sleep 5");
// readObject() 내부에서 Runtime.getRuntime().exec(taskAction) 실행됨
```
- **Gadget Chain**: 이미 클래스패스에 있는 여러 클래스를 연결해 임의 코드 실행 경로를 구성하는 기법
- **방어**: 신뢰할 수 없는 소스의 역직렬화 금지, JSON 등 안전한 포맷 사용, 클래스 화이트리스트 필터링

### A09. Security Logging and Alerting Failures (CWE-117, CWE-532, CWE-778)

- **Log Injection**: 사용자 입력에 개행문자(`%0a`)를 넣어 로그 조작
```
Login failed for username:test%0aLogin passed for username:admin
→ 로그가 두 줄로 쪼개져 마치 "admin 로그인 성공"처럼 보이게 조작
```
- **민감정보 로그 노출**: 비밀번호를 Base64로만 인코딩해 로그에 남기면 디코더로 즉시 복원 가능 — 애초에 로그에 남기면 안 됨
- **절대 로그에 남기면 안 되는 것**: 비밀번호, 세션 ID, Access Token, 카드번호 등
- SIEM/SOAR 연계 파이프라인(수집→정규화→탐지→경보→대응)의 필요성

### A10. CSRF & SSRF

| | CSRF | SSRF |
|---|---|---|
| 정의 | 사용자의 인증된 세션을 이용해 의도치 않은 요청을 강제로 보내게 함 | 서버가 공격자가 지정한 URL로 대신 요청을 보내게 함 |
| 피해 대상 | 사용자의 브라우저/PC | 서버 자신 및 내부망 |
| 방어 | CSRF Token(요청마다 검증), Referer 검증 | 요청 URL Allowlist, 내부 IP 대역 차단 |

**CSRF 공격 예시**
```html
<form id="csrf-review" action="http://target/WebGoat/csrf/review" method="POST">
  <input name="reviewText" value="공격 문구">
</form>
<script>document.getElementById("csrf-review").submit();</script>
```
- JSON API도 `enctype="text/plain"` form으로 우회 가능(Content-Type 검증 미흡 시)
- 방어 적용 시 Token 없는 요청은 `403 Forbidden`

**SSRF 예시**: 이미지 URL 파라미터에 외부 URL을 넣어 서버가 대신 요청하게 함 → 내부망 스캔이나 클라우드 메타데이터(`169.254.169.254`) 탈취로 이어질 수 있음(Lab3 실습과 동일 맥락)

### Beyond OWASP — AI 보안 (LLM Top 10)

- **Prompt Injection**(LLM01)이 가장 대표적 위협
  - Direct: 사용자가 직접 시스템 프롬프트를 무시하도록 유도
  - Indirect: 외부 문서/웹페이지 등에 악성 지시문을 숨겨 AI가 크롤링/요약 중 실행
- 기타 LLM Top 10: 민감정보 유출(LLM02), 출력값이 XSS로 이어짐(LLM05), 과도한 权한 위임(LLM06), 로깅/모니터링 부재(LLM08)
- 전통적 웹 보안 원칙(입력 검증, 최소 권한, 로깅)이 AI 시스템에도 그대로 적용되어야 함
