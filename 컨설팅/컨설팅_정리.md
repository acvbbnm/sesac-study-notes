### 1-3. ISMS-P / ISO27001 개요
- **ISMS(정보보호 관리체계)**: 지속적인 보안관리를 위해 필요한 조직, 정책, 절차를 관리·운영하는 체계
- **ISMS-P**: ISMS + 개인정보보호까지 포함한 한국형 인증제도(KISA/한국인터넷진흥원 운영)
- **인증기준 구성 (총 102개, 최신 기준)**
  | 영역 | 분야 수 | 항목 수 |
  |---|---|---|
  | 1. 관리체계 수립 및 운영 | 4개 분야 | 16개 |
  | 2. 보호대책 요구사항 | 12개 분야 | 64개 |
  | 3. 개인정보 처리단계별 요구사항 | 5개 분야 | 22개(문서상 21로도 표기) |
- **ISO27001(2022)**: Annex A 총 93개 통제(조직 37 + 인적 8 + 물리 14 + 기술 34), vs 구버전은 114개 통제/4개 영역
- PDCA(Plan-Do-Check-Act) 사이클이 관리체계 운영의 기본 원리

### 1-4. 컨설팅 방법론 — 12단계 프로세스
```
1. 프로젝트 착수(WBS 수립)  →  2. 자산 식별/분류  →  3. 위험 분석
→ 4. 정책/문서 검토  →  5. 인터뷰(현황 파악)  →  6. Gap 분석
→ 7. 기술적 취약점 진단  →  8. 결과 종합/위험도 산정  →  9. 개선계획(Remediation) 수립
→ 10. 보고서 작성  →  11. 경영진 보고  →  12. 사후관리/이행점검
```
- **WBS 예시**: Day0(착수) → Day1(자산/인터뷰) → 이후 진단/분석/보고서 순으로 날짜별 일정표 작성
- **인터뷰 절차**: 사전 이메일(일시/장소/참석자/목적 명시) → 인터뷰 진행(5단계: 소개→질문→기록→확인→마무리) → 결과 정리

### 1-5. 자산 분류 및 위험도 평가
- **자산 중요도**: 기밀성/무결성/가용성 3요소를 각 1~3등급(H/M/L)으로 평가 후 합산
- **위험도 산정 공식**
  ```
  위험도(Risk) = 자산가치(Asset Value) × 위협(Threat) × 취약점(Vulnerability)
  ```
  (문서 내 표현은 버전에 따라 곱셈 매트릭스형과 덧셈형이 혼재 — 실습에서는 **3×3×3 매트릭스**(L=1/M=2/H=3)로 계산, 결과값 1~27을 DoA(Degree of Acceptance, 수용가능위험) 기준선과 비교)
- **위험 대응 전략(ISO31000 기반)**: 회피(Avoidance) / 감소(Mitigation) / 전가(Transfer) / 수용(Acceptance)
- **위험관리 프로세스(ISO31000)**: ① Context Establishment(상황수립) → ② Risk Assessment(식별→분석→평가) → ③ Risk Treatment(처리) → ④ Monitoring and Review(모니터링/검토), 전 과정에 Communication(의사소통) 병행

### 1-6. GAP 분석 방법론
- **정의**: 현재 수준(As-Is)과 인증기준/정책이 요구하는 수준(To-Be) 사이의 차이(Gap)를 찾아내는 활동
- **3단계**: Phase 1 준비(Preparation) → Phase 2 수행(Conducting, 문서검토+인터뷰) → Phase 3 분석(Analyzing, 결과 정리)
- **KISA ISMS-P 인증기준 문항 단위로 Y(충족)/N(미충족)/P(부분충족) 판정** → 항목별 결함(Gap) 도출 → 개선계획(조치예정일 포함) 수립

### 1-7. 기술적 취약점 진단 — 채점 방식
- 판정: **Y=1점, N=0점, P(부분충족)=0.5점**
- 적용률(%) = (충족 항목 합계 ÷ 전체 항목 수) × 100
- 등급 구간
  | 점수 구간 | 등급 |
  |---|---|
  | 0~25 | 매우 취약 |
  | 26~45 | 취약 |
  | 46~70 | 보통 |
  | 71~90 | 양호 |
  | 91~100 | 매우 양호 |

### 1-8. 기술적 취약점 점검 체크리스트 (부록)
교재 후반부에 **클라우드/네트워크/서버(Unix·Windows) 대상 상세 점검 항목 코드 목록**이 수록되어 있습니다 (KISA 주요정보통신기반시설 취약점 점검 가이드와 유사한 체계).

| 코드 | 대상 | 개수 | 주요 내용 |
|---|---|---|---|
| **C-01~C-34** | AWS 클라우드 | 34개 | IAM 계정/정책 관리, Key Pair 관리, Admin Console 보안, MFA 설정, NAT/보안그룹(ANY 차단), S3 버킷 접근제어·암호화, RDS/EBS 암호화, CloudTrail·CloudWatch 로깅, VPC 설계 |
| **S-01~S-25** | 네트워크 장비 | 25개 | Default 계정/패스워드 변경, Session Timeout, ACL, SNMP Community String, NTP, DMZ 구성, UTM EoS 여부 |
| **U-01~U-54** | Unix/Linux 서버 | 54개 | root 원격접속 제한, PATH 환경변수, /etc/passwd·/etc/shadow 권한, SUID/SGID, world-writable 파일, 계정 잠금정책(PASS_MAX_DAYS 등) |
| **W-xx** | Windows 서버 | (일부 수록) | Administrators 그룹, Remote Desktop Users, IIS 보안 설정 |

→ 이 부분은 앞서 정리한 SIEM/침해사고대응 실습에서 다룬 KISA 취약점 점검 항목(W-04 계정 잠금, W-17 하드디스크 공유 제거 등)과 **동일 계열의 체크리스트**입니다.

- **AWS**: CloudFront+WAF → ALB → EC2(42대) / RDS(6대) / Redis / S3, DW용 별도 구간, CloudTrail 연동

| 1. 관리체계 수립 및 운영 | 1.1~1.4, 총 45개 확인사항(16개 항목의 세부 질문 단위) |
| 2. 보호대책 요구사항 | 2.1~2.12, 총 200개 확인사항(64개 항목의 세부 질문 단위) |

**컬럼 구조** (관리체계/보호대책 시트 공통)
```
분야 | 항목(예: 1.1.1) | 상세내용(인증기준 원문) | 주요 확인사항(질문형)
| 운영여부(Y/N/P) | 적용여부 | 운영현황(또는 미선택 사유) | 관련 문서(정책 조항번호)
```
- 예: `1.1.1 경영진의 참여` → "정보보호 및 개인정보보호 관리체계의 수립 및 운영활동 전반에 경영진의 참여가 이루어질 수 있도록 보고 및 의사결정 등의 책임과 역할을 문서화하고 있는가?" → 운영여부에 Y/N/P 판정 기입 → 근거 문서(첨부1의 조항 번호) 기재
- 판정 결과는 "0. 평가결과" 시트에 자동 집계되어 분야별 적용률(%)이 산출되는 구조

**실습 흐름**: 첨부1(정책) + 시나리오(회사 현황) + 첨부2(자산목록)를 근거로 → 첨부3의 각 확인사항에 Y/N/P를 판정 → 미충족(N) 항목에 대해 교재의 개선계획 양식(조치예정일 포함)으로 Remediation Plan 작성

## 전체 자료 간 연결 구조 한눈에 보기

```
[교재] 방법론(GAP분석/위험분석/기술진단) 학습
   ↓
[시나리오 PDF] 나인전자 현황 파악 (인프라, 조직, 취약 포인트 힌트)
   ↓
[첨부1 정책] "To-Be" 기준(회사 자체 규정) 확인
   ↓
[첨부2 자산대장] 점검 대상(서버 34대 등) 식별
   ↓
[첨부3 GAP분석 시트] 문항별 Y/N/P 판정 → 적용률 산출 → 결함(Gap) 도출
   ↓
개선계획 수립 → 최종 보고서 작성
```
