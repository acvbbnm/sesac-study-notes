# 09. 강의 노트 — 서비스 보안 실무

> 강사 실시간 강의 내용을 주제별로 정리. Unix 서비스 관리·접근통제·패치·로그 진단 실무.  
> 관련 진단 항목(U-27, U-28, U-36, U-39~42, U-45~48, U-59~66)과 연계.

---

## 1. r-command (r 계열 서비스)

`r` 계열 서비스(rlogin, rsh, rexec)는 **인증 없이 원격 명령 실행**이 가능해 매우 위험하다.

**r-command가 동작하는 조건**
1. **xinetd 데몬이 구동 중**이어야 하고
2. **`/etc/xinetd.d/` 하단에 r-command 데몬(rlogin, rsh, rexec)이 존재**해야 함

**관련 점검 명령어**
```bash
# /dev 하위의 일반 파일 탐색 (rootkit 위장 파일 등 점검, U-26)
find /dev -type f -exec ls -al {} \;
```

> 진단 항목: **U-27**($HOME/.rhosts, hosts.equiv 사용 금지), **U-36**(r 계열 서비스 비활성화)

## 2. 서버 접근 통제 (ACL)

특정 호스트만 대상 서버에 접근 가능하도록 **ACL(Access Control List)** 을 설정하는 것.

| 파일 | 역할 |
|------|------|
| `/etc/hosts.deny` | 전체 차단 (기본 Deny) |
| `/etc/hosts.allow` | WhiteList — 허용할 hostname / IP Address 등록 |

> **원칙**: hosts.deny에서 전체 차단 → hosts.allow에 허용 대상만 등록 (Whitelist 방식)  
> 진단 항목: **U-28**(접속 IP 및 포트 제한)

### 방화벽

정해놓은 규칙(Rule)을 기반으로 실시간 인입되는 네트워크 접근을 차단.

| 값 | 정책 |
|:--:|------|
| 1 | All Deny (전체 차단) |
| 0 | All Allow (전체 허용) |

| 구분 | 목적 |
|------|------|
| **내부 방화벽** | Private Network 내 접근 통제 |
| **외부 방화벽** | Public(DMZ) Network 접근 통제 |

### 서버 접근제어 솔루션

1. **웹 관리콘솔** — 개인 계정(가상 계정)으로 로그인
2. **SSH/RDP** → `su` → root (직접 root 접속이 아닌 단계적 권한 상승)

## 3. 공유 서비스 (FTP vs NFS)

| 구분 | 내용 |
|------|------|
| **공통점** | 무조건 **네트워크 통신을 기반**으로 함 |
| **FTP** | 서버(host)에 **직접적인 네트워크 접근**을 통해 사용 |
| **NFS** | 각 서버의 파티션/디렉터리를 **네트워크 마운트 + 인증 절차**로 접근 허용 |

### 마운트(automount)의 종류

| 종류 | 설명 | 확인 |
|------|------|------|
| **네트워크 마운트** | `/etc/exports`에 서버 접근 정보·계정 인증 정보 추가 | `cat /etc/exports` |
| **로컬 파티션 마운트** | 로컬 디스크 파티션 마운트 | `df -h` |
| **디바이스 마운트** | 장치 마운트 | `findmnt -t` |

> 진단 항목: **U-35**(공유 익명 접근 제한), **U-39**(불필요 NFS 비활성화), **U-40**(NFS 접근 통제)

### 관련 점검 명령어
```bash
# 주요 디렉터리 소유자·권한 확인 (U-15, U-31)
ls -ald /root/ /home/adiosl/ /var/lib/mysql/ /home/cubrid/
```

## 4. RPC / NFS 관리 서비스

| 서비스 | 역할 |
|--------|------|
| **rpcbind** | RPC 서비스를 초기 실행 시 **주소체계(포트)를 부여하고 매핑**하는 역할 |
| **rpc.statd** | RPC 서비스 **구동 상태를 모니터링** (NFS 네트워크 마운트 잠금 상태 확인) |
| **rpc.lockd** | 잠금 처리된 네트워크 마운트 지점을 **잠금 해제** |

> 진단 항목: **U-41**(automountd 제거), **U-42**(불필요 RPC 비활성화)  
> (→ [08. RPC vs xinetd](./08_RPC_vs_xinetd_서비스개념.md) 참고)

## 5. 패치 관리 (Repository vs Source)

| 방식 | 설명 | 패치 검토 방법 |
|------|------|---------------|
| **Repository** | RPM이 모인 저장공간에서 패키지를 호출해 자동 설치 | RPM 저장 웹 애플리케이션에 접근해 Major/Minor 버전 직접 확인 |
| **Source** | 공식 홈페이지에서 직접 다운로드해 원하는 경로에 설치 | 공식 홈페이지 최신 패치 여부 확인 (예: 설치 7.0.1.10 → 패치 7.0.1.11) |

### 패치 검토 절차

1. **CVE 취약점 검토** — 설치된 Platform에 주요 CVE 취약점이 있는지 확인
   - 확인 경로: **NVD, CVE Details, KISA 보호나라**
   - 우선순위: RCE, 권한 상승, 코드 인젝션 등 **CVSS 3.0 기준 9.0 이상**
2. **EOS 검토** — 설치된 Platform이 EOS(End Of Service)가 되었는지 확인

> 진단 항목: **U-64**(주기적 보안 패치 및 벤더 권고사항 적용)

## 6. 메일 서비스 (Mail Daemon)

**대표 데몬**: 1. sendmail  2. postfix

### 메일 서버 개요
- 메일 서버에는 **MX 서버(메일 수발신)** 가 존재
  - 수발신에는 각각 **수신 QUEUE / 발신 QUEUE** 존재
- 메일 수발신 서버에 각각 연결된 **사용자 사서함** 존재

### 메일 수발신 경로
```
[수신] 발송자 메일 발송 → MX 서버 수신 → 수신 QUEUE 인입 → 내부 솔루션 이상징후 탐지 → 메시지 전달
[발신] 발신자 메일 발송 → MX 서버 발신 → 발신 QUEUE 인입 → 메시지 발송
```

### 메일 서비스를 안전하게 사용하는 방법
1. 메시지 QUEUE를 **일반 사용자가 DROP 할 수 없도록** 차단
2. 일반 사용자가 **릴레이 설정을 할 수 없도록** 차단하거나 **관리자 IP만 등록**
3. **EXPN, VRFY 명령어를 사용할 수 없도록** 차단

> 진단 항목: **U-45**(메일 버전 점검), **U-46**(일반 사용자 메일 실행 방지), **U-47**(스팸 릴레이 제한), **U-48**(expn/vrfy 제한)

## 7. 전용 계정 원칙 (root로 서비스 구동 금지)

**root 계정을 Platform(FTP, SMTP, DNS, WEB/WAS/DBMS) 계정으로 사용하지 않아야 하는 이유**

1. root 권한이 필요한 일반 사용자 계정이 **Wheel 그룹에 다수 포함**되어 있기 때문
2. 각 Platform(FTP, SMTP, DNS, WEB/WAS/DBMS)은 **전용 계정으로 구동·사용**해야 함

> 서비스가 침해되어도 피해 범위를 해당 서비스 계정으로 한정(권한 최소화).  
> 관련: **U-06**(su 제한), **U-11**(사용자 Shell 점검)

### 로그인이 필요한 서비스 및 데몬
1. ssh  2. telnet  3. ftp  4. smtp  5. dns

## 9. 시각 동기화 (NTP)

**NTP 서버 사용 목적**  
서버 시간을 사용자가 수동으로 변경하거나 **외부자 공격으로 시간이 변경되는 경우**, NTP 서버에 연결·동기화하여 변경 시에도 동일한 시간으로 적용받기 위함.

- **핵심**: 저장되는 시스템 로그의 시간을 동일하게 적용 → 로그 신뢰성 확보
- 진단 항목: **U-65**(NTP 및 시각 동기화 설정)

## 10. 로그 관리 (rsyslog)

### 로그 설정 확인
```bash
# authpriv(인증 로그) 설정 확인 (주석 제외)
cat /etc/rsyslog.conf | grep -C11 authpriv | grep -v "#"
# 출력 예: $IncludeConfig /etc/rsyslog.d/*.conf
```

### 안전하게 로그를 보관·관리하는 방법
1. 로그 보관 **최소 기간(1년)** 확보
2. 로그를 서버 내에만 두지 않고 **별도 저장장치(스토리지, 로그서버)에 보관**
3. 저장된 로그를 **주기적으로 검토** 후 이상징후를 상급자에게 보고하는 절차 필요
4. 별도 저장·서버 보관 로그는 **담당자 포함 모든 사용자의 변경 권한을 제거**

> 진단 항목: **U-66**(정책에 따른 시스템 로깅 설정), **U-67**(로그 디렉터리 소유자·권한)  
> (→ [07. 계층별 로그 정리](./07_계층별_로그_정리.md) 참고)

## 11. EOS 서버 마이그레이션 권고 (실무 조치문 예시)

> 현재 운영 중인 대상 서버에는 웹 애플리케이션 Source 및 관련 Module이 구동·운영 중인 상태로, 실제 보관이 필요한 데이터(업로드 파일, SourceCode, Platform 설정 파일 등)를 먼저 **백업**한 후 패치가 가능한 **LTS OS를 구축**한다. 단, OS 구축 시 기존 구동 중인 데몬이 동일하게 구성되도록 **사전에 구동 데몬과 오픈 포트를 리스트업**하고, 구축 후 **테스트 데이터로 검증**한다. 테스트에 문제가 없을 경우 기존 데이터를 **Migration**한다.

**마이그레이션 절차 요약**
```
① 데이터 백업 (업로드 파일 / SourceCode / 설정 파일)
② 구동 데몬 + 오픈 포트 리스트업
③ LTS OS 신규 구축 (동일 데몬 구성)
④ 테스트 데이터로 검증
⑤ 문제 없으면 실데이터 Migration
```

> EOS(→ [06. 환경분석 실전 예시](./06_환경분석_실전예시_CentOS6.9.md))의 CentOS 6.9 같은 지원 종료 OS에 대한 현실적 대응 방안.
