# 00. 취약점 진단 개요 & 방법론

> 교안: 시스템 취약점 분석 실무 과정 교안 (2026)  
> 참조: 주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드 (KISA, 2026)

---

## 1. 취약점 진단 vs 모의해킹

| 구분 | 취약점 진단 | 모의해킹 |
|------|------------|----------|
| **정의** | IT 운영환경 취약점 진단 및 보호대책 수립으로 정보보호 수준 향상 | 실제 해킹과 동일한 공격으로 실제적 보안 취약점 확인·제거 방안 제시 |
| **범위** | 웹·소스코드 진단, 서버 OS·DBMS·WEB·WAS·NETWORK·보안장비 진단 | 내/외부 시스템 모의해킹, APT 진단(내부 정보 유출) |
| **산출물** | 보호대책 및 개선과제 제시 | 진단 대상 및 개선과제 제시 |

## 2. 취약점 진단 방법론 (4단계)

```
① 사전협의 단계
   ├─ 프로젝트 요청 / 담당자 미팅 (유선·오프라인)
   ├─ 진단 기준 선정 (기반시설 / 금융취약점분석평가)
   ├─ 진단 대상 선정 (OS, Middleware 등)
   └─ 진단 기간 선정 (진단 수 대비 인력)

② 정보수집 단계
   ├─ 진단 정보 요청
   ├─ 보안 담당자 인터뷰
   └─ 시스템 담당자 인터뷰

③ 취약점 진단 단계
   ├─ 진단 수행
   ├─ 오픈 포트 분석
   ├─ 데몬 분석
   ├─ 계정 분석
   └─ 진단 대상 최종 FIX

④ 보고서 작성 및 프로젝트 종료 단계
   ├─ 결과 보고서 작성
   ├─ 결과 보고서 리뷰
   ├─ 산출물 제출
   ├─ 데이터 클렌징
   └─ 프로젝트 종료
```


### 단계별 상세

**① 사전협의 단계**  
진단 범위와 규칙을 확정하는 단계. 무엇을·언제·어떤 기준으로 진단할지 합의한다.
- **진단 기준 선정**: 「주요정보통신기반시설 기술적 취약점 분석·평가」(기반시설) 또는 「금융 취약점 분석·평가」 등 적용할 표준 선택
- **진단 대상 선정**: OS, DBMS, WEB/WAS, 네트워크·보안장비 등 실제 점검할 자산 목록 확정
- **진단 기간 선정**: 진단 대상 수 대비 투입 인력·일정 산정

**② 정보수집 단계**  
진단에 필요한 정보를 수집하고 담당자와 소통하는 단계.
- **진단 정보 요청**: 자산 목록, 계정 정보, 접근 권한(SSH 계정 등) 확보
- **인터뷰**: 보안 담당자·시스템 담당자 인터뷰로 운영 정책·예외 사항 파악 (자동 점검 불가 항목은 인터뷰로 판정)

**③ 취약점 진단 단계**  
실제 시스템에 접근하여 점검을 수행하는 핵심 단계.
- **환경분석**: 오픈 포트 분석 → 데몬 분석 → 계정 분석 (→ [01. SYSTEM 환경분석](./01_SYSTEM_환경분석.md))
- **항목 점검**: U/W/WEB 항목별로 양호/취약/인터뷰 판정
- **최종 FIX**: 발견된 취약점에 대한 조치 방안 확정

**④ 보고서 작성 및 종료 단계**  
결과를 문서화하고 프로젝트를 마무리하는 단계.
- **결과 보고서 작성**: 항목별 [현황] + [대응방안] 기술 (→ [05. 결과보고서 작성 가이드](./05_결과보고서_작성_가이드.md))
- **리뷰·산출물 제출**: 고객사 검토
- **데이터 클렌징**: 진단 과정에서 생성·수집한 계정 정보, 로그, 임시 파일 등을 안전하게 삭제 (진단자가 취득한 민감정보 유출 방지)

## 3. 진단 대상별 항목 체계 (KISA 상세가이드 기준)

주요정보통신기반시설 기술적 취약점 분석·평가는 12개 대상으로 분류:

| 대상 | 주요 분류 |
|------|----------|
| **Unix 서버** | 계정 / 파일·디렉터리 / 서비스 / 패치 / 로그 관리 (U-01~U-67) |
| **Windows 서버** | 계정 / 서비스 / 패치 / 로그 / 보안 관리 (W-01~W-64) |
| **보안 장비** | 계정 / 접근 / 패치 / 로그 / 기능 관리 |
| **네트워크 장비** | - |
| **제어 시스템** | - |
| **PC** | 계정 / 접근 / 패치 / 보안 관리 |
| **DBMS** | 계정 관리 등 |
| **WEB (Apache 등)** | 계정 / 서비스 / 보안 설정 / 패치·로그 (WEB-01~WEB-26) |
| **클라우드** | 계정 / 권한 / 가상 리소스 / 운영 관리 |

**항목 중요도**: 상 / 중 / 하 3단계

> ※ 판단 기준은 권고 사항이며, 각 기반시설의 정책·운용 상황을 고려하여 진단 수행자가 최종 결정.  
> ※ 취약 판단을 받아도 합당한 보안 조치·근거가 있으면 양호로 판단 가능.  
> ※ 문의: ciip@kisa.or.kr (한국인터넷진흥원)

## 4. 주요 용어

| 용어 | 설명 |
|------|------|
| **주요정보통신기반시설** | 국가·사회적으로 중요한 정보통신시설(정보통신기반 보호법 대상). 매년 취약점 분석·평가 의무 |
| **양호 / 취약 / 인터뷰** | 진단 판정 결과. 인터뷰=자동 점검 불가로 담당자 확인이 필요한 항목 |
| **정탐 / 오탐** | 실제 취약점(정탐) vs 취약점이 아닌데 취약으로 나온 것(오탐). 진단자가 검증 |
| **중요도(상/중/하)** | 항목이 시스템 보안에 미치는 영향도. 조치 우선순위 기준 |
| **EOS(End of Service)** | 벤더 지원·보안 패치 종료. EOS 자산은 그 자체로 취약 |
| **CERT** | 침해사고대응팀. 진단 중 침해 흔적 발견 시 협조 |

## 5. 진단 시 유의사항

- **운영 영향 최소화**: 진단은 운영 중인 시스템에 수행되므로 부하·장애를 유발하는 점검(무차별 대입 등)은 담당자 협의 후 진행
- **판단 기준의 상대성**: KISA 판단 기준은 권고 사항. 취약 판정이어도 보완 통제·근거가 있으면 양호로 조정 가능 (수행자 최종 판단)
- **민감정보 보호**: 진단 중 취득한 계정·설정 정보는 진단 종료 후 데이터 클렌징으로 삭제
- **최신 기준 적용**: 점검 항목·판단 기준은 매년 갱신되므로 해당 연도 가이드 확인 (본 문서는 2026년 기준)
